# MicroFlow CLI 命令体系设计

版本：v1.0（设计基线草案）
日期：2026-10-25
状态：设计基线草案。本设计是《平台标准设计》§16 与《技术选型》TS-18 接入面的操作化收敛：只规定命令体系的结构、命名、协议与兼容判定，不引入新业务语义；与基线设计冲突时以基线设计为准。实现状态由实施计划（T14/T15）管理，本设计的修订不等于实现完成。

## 1. 定位与范围

### 1.1 定位

CLI 是框架能力的**协议投影**：每个命令只是框架公开 Python API（或等价语言 API）的薄包装，不承载业务语义。命令体系依据平台标准 §16 列举的能力清单收敛——算子发现与契约查询、相关上下文读取、编排校验、测试执行、执行记录检查、版本差异查询，外加模板生成（§16）与影响查询（TS-18）。

CLI 面向三类使用者：外部 VibeCoding 工具（主使用者，进程调用 + JSON 消费）、宿主与运维脚本、框架开发者。CLI 不集成任何特定工具、模型或交互协议（§16）；工具侧如需 MCP 等专有协议，在框架外以适配层包装 CLI，不进入本体系。

### 1.2 与其他接入面的边界

- **本 CLI 是开发与工具回路接口**：本地编译、校验、演练、影响分析、脚手架。凡是需要绑定耐久提供者、运行中服务或生产权限的运维控制（取消、暂停、未知确认、迁移等，T14）由宿主部署的控制面承载；控制面应复用本设计的信封、退出码与诊断纪律（协议兼容），但不纳入本命令集。
- **前端命令面**（《前端框架完整设计方案》§14 结构化命令）是 Dart API 形态的编排创作面，归属前端工具生态；本 CLI 面向后端执行框架的跨语言接入。两者共享"结构化命令、显式校验、可判定结果"的通用纪律。前端命令面的能力投影已按本设计兼容契约第 5 条落地：`microflow_authoring` 包提供 `mfAuthoringCapabilities()`（协议 `mf-authoring-capabilities-v1`），工具经探测获取命令目录。

### 1.3 规范用语

沿用平台标准 §1.3（必须/应/建议/可以/禁止）。

## 2. 兼容契约

以下八条构成"功能兼容"的定义，任何语言实现的 CLI 必须全部满足；一致性由第 5 章的测试套件判定。

1. **统一信封**。stdout 必须输出且只输出一个 JSON 对象：`protocol` 字段固定 `microflow-cli-v1`，其余为该命令的结果键（现有 `check`/`run`/`impact` 等已采用此形态，新命令沿用，不引入统一包装键）；`sort_keys` 确定性序列化。stderr 仅供人类提示，不承载诊断语义——诊断只出现在 stdout JSON 内。
2. **统一退出码**。`0` = 请求完成且结果为肯定或中性；`1` = 请求完成，但被验证对象的结果为否定（如 `run` 业务终态 FAILED、`test` 存在失败用例）；`2` = 请求本身无法完成（用法错误、编译失败、文件不可用、未知引用等，附诊断）。退出码语义跨实现一致，工具据此分流而不必解析全部输出。
3. **统一诊断码**。诊断码原样透传框架错误码；同一语义的诊断码跨实现一致（如 `UNKNOWN_OPERATOR`、`CYCLE_DETECTED`），实现可增加实现特有码但禁止重定义共享码。`diagnostics` 命令输出码目录，工具经探测解释码而非硬编码猜测。
4. **显式边界旗标**。凡触发本地编译或执行的命令必须显式 `--ephemeral`，缺失即拒绝（现有行为，扩展为全体系规则）；纯静态命令（`capabilities`/`diagnostics`/`policy-schema`/`policy-check`/`scaffold`）禁止接受该旗标，避免语义漂移。
5. **能力探测替代硬编码**。`capabilities` 命令输出实现标识、版本与命令目录（含每个命令的参数与结果键说明）。工具应先探测再使用，不假设命令存在——这是跨实现兼容的动态机制，配合静态的第 2、3 条。
6. **诚实边界**。只暴露已实现命令；未实现能力不得以占位命令形式出现。`capabilities` 如实声明，与平台标准"实现状态分别管理"的纪律一致。
7. **确定性输出**。同一输入产生字节级一致的输出（排序构造、无墙钟噪声、无随机顺序）；时间戳字段仅来自真实事件，禁止伪造（§14.1.1 纪律延伸到 CLI 层）。
8. **容量预算**。列表类输出遵循显式预算；超限以诊断失败而非截断。v1 项目级 CLI 输出不设分页，预算超限报错并提示缩小查询范围（定向查询命令即为缩小手段）。

## 3. 命令体系

命名约定：多词命令用 kebab-case；除 `scaffold` 外不引入二级子命令，保持工具侧解析简单。命令按工具回路分组：读 → 构造 → 验 → 演练与影响 → 观察。

### A. 发现与读取

| 命令 | 状态 | 目的与设计出处 |
|---|---|---|
| `capabilities` | **已实现** | 实现标识、版本、命令目录与输出键说明（兼容契约第 5 条） |
| `diagnostics` | **已实现** | 诊断码注册表：码、语义、稳定级别（兼容契约第 3 条；`microflow-diagnostics-v1`） |
| `describe <files...>` | **已实现** | 显式可信文件 → 版本化注册表 JSON |
| `operators <project> --ephemeral` | **已实现** | 算子目录：ref、契约、能力声明、默认策略摘要、静态引用计数（§16 算子发现；引用计数来自 impact 索引） |
| `schema <project> <name> --ephemeral` | **已实现** | 单个契约 schema 的版本化定义（§16 契约查询） |
| `context <project> <operator-ref> --ephemeral` | 规划 | 局部上下文：实现摘要、输入输出 schema、直接上下游（来自 impact）、能力与默认策略、相关测试引用、边界与遗漏声明（§16；读取范围有界） |
| `policy-schema` | **已实现** | 策略字段、默认值与合并规则 |

### B. 构造

| 命令 | 状态 | 目的与设计出处 |
|---|---|---|
| `scaffold operator <name> [--with-fallback] [--proxy metrix,log] [--into DIR]` | 规划 | 生成主方法、可选代理、注册片段、schema 与测试骨架；代理按需生成，避免无意义样板（§16 模板生成） |
| `scaffold flow <id>` | 规划 | 生成流程配置骨架：id、schema 引用、最小节点与输出映射 |

### C. 校验与验证

| 命令 | 状态 | 目的与设计出处 |
|---|---|---|
| `check <project> --ephemeral` | **已实现** | 编译与静态校验，输出候选诊断 |
| `policy-check <config-file>` | **已实现** | 校验部分策略配置层（包装 `validate_policy`），供宿主页面与工具预检 |
| `test <project> --ephemeral` | 规划 | 隔离执行算子契约测试与项目声明的回归输入输出对，输出结构化用例结果（§16 测试执行；"AI 生成的测试预期必须有业务规则或已确认样例来源"的检查在此落点） |

### D. 演练与影响

| 命令 | 状态 | 目的与设计出处 |
|---|---|---|
| `run <project> <flow> <input> --ephemeral` | **已实现** | 本地同步执行，输出标准 Output 与节点记录 |
| `impact <project> --ephemeral [--operator REF] [--flow ID]` | **已实现** | 静态影响反向索引与上游闭包（`microflow-impact-index-v1`） |
| `preview <project> --against <baseline> --ephemeral` | 规划 | 变更预览：影响算子、子图引用链、契约兼容判定（PROVED/UNKNOWN/INCOMPATIBLE）、恢复兼容性、建议回归范围（§16 变更预览；在 impact 之上叠加契约与恢复维度） |
| `diff <project-a> <project-b> --ephemeral` | 规划 | 版本差异查询：算子集、schema、流程结构与 release_id 的结构化差异（§16 版本差异） |

### E. 观察

| 命令 | 状态 | 目的与设计出处 |
|---|---|---|
| `query <project> (--run ID \| --trace ID)` | 规划（依赖 T10/T14） | 执行记录检查。本地演练记录随 `run` 结果返回，本命令在耐久执行接入后经宿主提供者查询；v1 不提供内存假查询 |

合计 17 个命令，构成封闭集合；扩容须修订本设计并同步 `capabilities` 与一致性测试。

## 4. 兼容判定：CLI 一致性测试套件

跨实现"功能兼容"由测试判定，不由文档声明判定（镜像 TS-22 对持久化提供者的契约测试纪律）：

- 仓库维护一套**实现无关的 CLI 一致性夹具**：固定输入项目、固定调用参数、每命令的输出断言（结果键存在性、协议字段、退出码、确定性——同输入两次调用字节一致）与诊断码断言；
- 任何语言实现的 CLI 必须在该套件下全部通过，方可声明 `microflow-cli-v1` 兼容；`capabilities` 输出的命令目录与实际通过的一致性子集必须相符；
- 共享诊断码的语义断言进入套件；实现特有码只需登记不需断言。

## 5. 安全与边界

- **信任边界不变**：`describe`/`scaffold` 涉及的注册代码执行沿用现有协议——只加载显式列出的可信文件，注册入口不得执行业务或连接资源（§8）；CLI 扩容不改变"注册入口是可执行 Python 代码"的信任模型。
- **scaffold 只写候选文件**：输出限定在 `--into` 显式目录内，不触碰注册表或既有源文件；生成物经 `describe`/`check` 走同一天验证门禁，纯配置创建不降低任何门禁。
- **修改审计归版本管理**：CLI 不复制审计与回滚层；文件变更由项目的版本管理（git）承担，框架保证的是"每次命令产出可判定结果"，与前端命令面的修订审计（§14）分属两个生态的不同机制。
- **权限**：CLI 沿用执行主体的全部权限，不因自动化获得额外权限（§3）。

## 6. 实施映射与版本策略

- **先行切片**（不依赖未完成任务）：`capabilities`、`diagnostics`、`policy-check`、`schema`、`operators`——全部是现有 API 的薄包装。**已落地（2026-10-25，Python 侧）**，验证记录见实施计划 §20。
- **随 T15**：`context`、`test`、`preview`、`diff`、`scaffold`（模板与局部上下文、影响预览同源）；
- **随 T14/T10**：`query`（执行记录与可靠事件接入后）；
- **版本与废弃**：命令废弃在 `capabilities` 中声明 `deprecated` 并在 stderr 提示，保留期跨至少一个信封协议小版本；命令删除须修订本设计；
- **验收归属**：各命令的验收场景并入 T14/T15/T16 的 A01～A35 归属与一致性套件，不另设独立验收体系。
