## 1. 定位

MicroFlow Frontend 是与 MicroFlow 后端流程框架平行的前端开发框架。它面向 Vibe Coding，将前端产品表示为可组合、可验证、可版本化的结构模型，并将模型编译或运行到 Web、桌面和移动端。

框架与实现语言无关。项目模型、规范化 IR、交互与绑定语法、全部契约和诊断码都是语言无关的声明资源：Renderer 可以用任何语言实现，宿主实现组件可以用任何语言编写。实现语言只在实现描述符中作为声明性元数据出现，核心协议不解释、不依赖它；兼容性判断、版本解析和一致性基线也只依赖契约本身，不依赖实现语言。

框架定位为前端产品的底层构建与运行基础，不负责具体业务规则和业务组件实现。框架负责项目模型、组件/图层/页面/产品编排、规范化 IR、静态检查、编译、解释运行、发布快照、运行数据采集、诊断数据上报，以及多版本配置的加载、校验、兼容性检查和运行时冻结。

上层产品负责业务领域模型、业务规则、业务组件、业务数据适配器，并通过配置编排组件、图层、页面和产品。上层不得通过配置绕过 Schema、权限、版本和能力检查。

框架不依赖 RPC、HTTP、数据库、特定后端或特定云平台。后端连接、文件访问、设备能力和第三方服务都属于可选的宿主适配能力。没有后端时，框架仍能构建完整的静态页面、本地应用、交互原型和纯客户端产品。

框架解决的问题是：

- 用稳定的结构描述产品，而不是让 AI 在文件之间猜测关系；
- 用元组件组合组件，用组件组合图层，用图层组合页面，用页面组合产品；
- 让 AI、可视化编辑器和人工代码修改共享同一份项目模型；
- 在 Web 和客户端之间复用产品结构，同时允许平台差异；
- 对布局、依赖、导航、状态和平台能力进行静态检查；
- 让草稿、发布版本和运行中的产品具有明确边界。

框架不试图替代 React、Vue、Flutter 或原生 UI 工具包，也不替代上层业务组件库。它定义产品模型、组合协议、编译边界、数据采集协议和版本化配置协议，再由 Renderer 将模型落到目标平台。

## 2. 核心分层

产品由五个主要层级组成：

```text
元组件 → 组件 → 图层 → 页面 → 产品
```

### 2.1 元组件

元组件是最小可复用的 UI 或交互能力，例如 Text、Icon、Image、Button、Input、Stack、Grid、Scroll、Modal 和 List。

元组件不绑定业务名称，但必须具有明确的属性、插槽、事件、状态、布局能力和平台能力声明。

### 2.2 组件

组件是具有语义的可复用模块，由元组件或其他组件组合而成。例如 LoginForm、ProductCard、Sidebar、DataTable、SearchPanel 和 EmptyState。组件实现可以是在模型中组合（§6），也可以是注册的宿主实现（§23）；两者的公开契约纪律完全一致。

组件可以公开：

- 输入属性；
- 内容插槽；
- 输出事件；
- 内部状态；
- 可替换的主题令牌；
- 平台变体；
- 可调用的交互动作。

组件必须隐藏内部结构，页面只能依赖组件的公开契约。这样修改组件内部布局时，不会让所有页面跟着修改。

### 2.3 图层

图层是页面中的结构区域，同时表达视觉层级、布局职责和交互边界。典型图层包括 AppShellLayer、HeaderLayer、NavigationLayer、ContentLayer、PanelLayer、OverlayLayer 和 ModalLayer。

图层不是简单的 z-index。图层定义可以声明：

- 约束区域；
- 子组件集合；
- 对其他图层的依赖；
- 进入和离开动画；
- 响应式策略；
- 是否固定、滚动或覆盖；
- 在某个平台是否隐藏或替换。

### 2.4 页面

页面是可被导航、渲染和恢复的产品单位。页面包含页面参数、图层树、页面状态、页面事件、生命周期和错误边界。

### 2.5 产品

产品包含页面集合、导航图、主题、资源、产品级状态、应用入口、平台目标和发布配置。

页面之间不是树，而是有向图。菜单可以是树状投影，但真实导航必须支持返回、条件跳转、弹窗、Tab、深链接和外部入口。

### 2.6 定义与实例

元组件、组件、图层和页面在项目模型中以"定义"存在：定义是静态、可复用、拥有稳定 `id` 的声明资源（§4.2）。运行时沿使用点把定义实例化为"实例"：

```text
定义（静态资源）                实例（活动态）
组件/图层/页面契约              页面实例、图层实例、节点实例
拥有 definition id             拥有 page_instance_id、component_instance_id（§24.2）
项目模型和引用索引的归属对象     运行时、遥测和诊断的归属对象
```

规则：

- 复用发生在定义层：同一组件定义可以在同一页面被多次实例化，也可以跨页面复用；同一图层定义可以出现在多个页面的图层树中；
- 每个实例都是独立对象：实例拥有自己的身份、参数解析、数据获取结果和实例状态；实例状态随页面实例创建和销毁（§11），不同实例之间不共享实例状态；
- 绑定声明在定义引用处，作用到实例：页面结构树在引用组件或图层时声明的参数、样式位覆盖和事件绑定，由运行时解析后作用于具体实例；同一页面中同名组件的多次使用必须解析为互不影响的独立实例；
- 数据值属于实例：后端数据通过页面参数（§8）和外部适配器（§10 第 6 类，配合 §40 Data Contract）在实例边界内获取；同一页面定义配合不同路由参数得到携带不同数据的不同实例；
- 事件绑定（§39）声明时使用定义 id，执行时必须解析到当前实例上下文；诊断与遥测使用实例 id 关联用户行为（§22.3、§24.2）；
- 实例不能反向修改定义：运行实例不得改写项目模型（§13.2），任何工具或 AI 不得把实例快照当作静态定义写回项目模型。

### 2.7 配置构造闭环

框架的核心能力是纯配置构造：在不修改、不执行任何代码修订的前提下，通过项目模型创建新页面等产品结构。构造能力是一个封闭集合：

```text
仅凭配置可构造（引用已注册资源）              必须代码修订才可引入
─────────────────────────────────            ──────────────────────
页面定义（图层树、状态声明、生命周期引用）      元组件实现（§17，§23.12 kind: primitive）
图层定义与布局约束                            宿主实现组件（§23，kind: component）
模型组合组件（§6，配置即可沉淀新组件）          Local Function（§10.1，kind: function）
导航边与 guards                               外部适配器（§40，kind: adapter）
绑定映射与交互流程                             宿主能力扩展（§17.1，kind: capability）
i18n 文案、主题覆盖、样式片引用                Renderer 扩展与平台差异实现
```

规则：

- 页面创建只允许引用已注册的元组件、组件、图层、动作和 Data Contract；引用未注册资源是静态错误，配置侧不存在隐式代码执行通道（§17）；
- 模型组合组件同样配置可建（§6），复用沉淀不强制退回代码；纯配置无法表达需求（新逻辑、新能力）时，唯一出路是代码修订及其显式注册，不得在配置侧绕行；
- 页面模板是项目模型中的版本化资源（§4）：记录一组带参数的图层树、状态与绑定骨架；`create_page_from_template` 按参数实例化生成独立页面定义，模板修订不追溯改写已创建页面；
- 纯配置创建不降低任何门禁：新页面走同一校验、可访问性、i18n 完整性和引用检查（§18.1）；模型结构变化产生新的发布快照（§16），不存在"免发布"或"绕过门禁"的配置通道；
- 实例语义遵循 §2.6：同一页面模板的多次实例化产生互不影响的不同定义与实例；
- 内容资产（投放类文案、图片、公告引用）是配置级资源：随冻结的 `config_version` 变化而更新，不触发新发布快照（§16 快照边界）；承载内容的结构性容器仍只能引用已注册组件；内容位曝光按 §24.2 标准事件族登记，保证运营数据跨实现可比，事件归属承接 §2.8 的容器实例；文案归属 i18n 还是内容资产按 §42.7 的唯一判定规则执行，双声明是静态错误。

### 2.8 容器信息契约与纪律

组件、图层、页面和产品都是信息承载容器。容器的公开契约在结构（插槽，§23.9）、样式（公开样式位，§36.5）、布局能力（§23.2）之外，必须声明**信息面**：

- `info.provides`：本容器装配后可供下游使用的信息清单；每项声明信息 `id`、来源（引用 Data Contract、页面参数或状态层级）和作用域（容器实例内或生命周期内）；
- `info.consumes`：本容器依赖的上游信息；每项声明引用与 `required` 标记。

规则：

- `consumes` 必须可解析到某个上游容器的 `provides` 或其可见作用域内的状态层级成员；解析失败是静态错误，禁止「来历不明」的幽灵依赖；
- `provides` 的信息形状必须引用或内联合法 Schema（优先复用对应 Data Contract 的 `output` Schema，§40）；形状变更产生 §4.3 反向索引可传播的影响分析项；
- `provides` 的装配时点沿用既有生命周期与绑定动作语义（§8、§39），不新增执行机制；信息契约是对既有数据装配的声明化；
- 信息按容器层级持有：组件级信息不进入图层级，图层级信息不上浮到页面级，除非在上游契约中显式声明供给；全局级（Session/Product）不承载单一容器私有信息（§11）；
- 派生信息不作为第二事实来源（§11）；容器实例是运营事件与诊断的默认归属单元（§24.2）；
- 容器之间受控的第三条信息通道是供给/依赖引用：供给容器在其契约中声明 `provides` 后，子树内的绑定可引用 `provided.<id>.<path>`（§37.2）；显式属性传递与状态提升仍是第一通道，不因此淘汰。

### 2.9 代码、数据、配置三平面分离

框架的全部资源与值按承载物归属三个平面。平面边界是双向、可校验的硬边界，不是风格建议：

```text
代码平面：实现资源。宿主实现组件、元组件实现、Local Function、数据适配器、
          宿主能力与 Renderer 实现；只能经 §23 统一资源注册协议进入框架。
数据平面：运行值。实例状态、页面参数解析结果、适配器返回数据、遥测事件、
          Debug 与恢复快照；归属运行实例（§2.6），不进入项目模型与发布快照。
配置平面：声明值。`config_version` 承载的默认配置、内容资产、运营变体与
          实验上下文、主题选择（§4.5）；经加载管线校验后冻结到实例；
          创作形态位于 §15 的 config/ 目录。
```

规则：

- **归属唯一**：每个资源与值恰好归属一个平面。结构树只能引用结构、样式与绑定资源，不得内联实现代码、命令式逻辑或运行时数据值；结构/布局/样式/逻辑的章内拆分（§36.1）与字面量禁令（§36.4、§42.2）在本边界下继续生效，同一违例按更严格者判定；
- **平面间交互只走已声明通道**：代码经注册契约暴露公开契约面（§23.2）；数据经页面参数、Data Contract 与绑定作用域（§8、§40、§37.2）进入实例；配置经加载管线与受控交叉清单（见下）作用于实例；未经声明通道的平面间引用是静态或运行错误；
- **双向约束**：配置不得携带或执行代码（§2.7、§17），不得写入未验证数据（§24.4）；代码不得绕过配置通道干预运行实例（§4.5）；运行数据不得回写项目模型，工具与 AI 不得把实例快照当作静态定义（§2.6、§13.2）；
- **受控交叉集中登记**：实验与运营变体允许配置选择已声明的属性、布局方案、交互顺序与主题（§24.4、§31、§31.1），这是三平面分离的唯一显式豁免。豁免面必须逐条登记于产品级**受控交叉清单**：清单是版本化资源（§4.2），拥有稳定 `id` 与 `schema_version`，每条声明允许配置改写的资源面、允许的配置来源（实验或运营变体）与取值上限，摘要随发布快照携带（§16）；未列入清单的配置改写在静态校验中拒绝（`mf.exp.variant-out-of-scope`）。清单登记不改变 §24.4 的其余校验、冻结与恢复归属规则。

违例判定矩阵（诊断码登记于 §41 注册表，含义与版本由注册表解释）：

| 违例 | 平面方向 | 判定阶段 | 诊断码 |
|---|---|---|---|
| 结构/样式资源内联可执行逻辑或命令式片段 | 代码 → 模型/配置 | 静态 | `mf.schema.inline-logic` |
| 未经声明入口到达的实现被注入执行 | 代码 → 运行时 | 运行 | `mf.reg.unregistered-impl` |
| 配置载荷携带可执行逻辑或未验证数据 | 配置 → 代码/数据 | 静态 + 运行 | `mf.data.config-unverified` |
| 实验/运营变体改写未登记资源面 | 配置 → 代码面 | 静态 | `mf.exp.variant-out-of-scope` |
| 实例状态或运行数据写回项目模型 | 数据 → 模型 | 工具静态 + 运行 | `mf.state.writeback-denied` |
| 凭据或原始直接标识进入模型、契约、事件、快照 | 数据 → 模型/配置 | 静态 | `mf.sec.credential-in-model` |

三平面分离检查并入 §18.1 与 §22.4 质量门禁。§12.1 的 `allowed_differences` 纪律约束 Renderer 平台差异，与本节受控交叉清单相互独立、分别登记，二者不得互相替代。

## 4. 项目模型

项目模型是所有工具的唯一事实来源。编辑器、AI 和编译器都通过模型操作，不直接通过文本搜索猜测产品结构。

```text
Project
├── manifest
├── design_system
├── primitives
├── components
├── layers
├── pages
├── templates
├── navigation
├── interactions
├── data_models
├── i18n
├── telemetry
├── experiments
├── assets
├── platform_profiles
├── tests
└── release
```

### 4.1 Manifest

Manifest 描述项目 ID、模型版本、目标平台、入口页面、默认主题、工具链版本和能力要求。

### 4.2 资源身份

每个元组件、组件、图层、页面、动作和资源拥有稳定的 `id`。名称可以修改，ID 不随重命名变化。

每个对象还包含：

- `kind`：对象类型；
- `schema_version`：结构版本；
- `revision`：对象修订；
- `source`：来源文件或生成来源；
- `description`：供人和 AI 使用的语义说明；
- `tags`：检索和分类标签；
- `dependencies`：显式依赖；
- `capabilities`：平台能力要求。

### 4.3 可追踪引用

对象之间的引用使用稳定 ID，编译器生成反向索引：

```text
component → used_by layers/pages
page → reachable_from routes
asset → used_by components
interaction → reads/writes states
```

AI 修改前必须能查询影响范围；删除对象前必须经过引用检查。

### 4.4 观测与实验身份

日志事件、运营事件、性能样本和实验配置引用都属于项目模型中的版本化资源。每条事件和配置必须关联 `project_id`、`release_id`、`renderer_version`、`environment` 和 `schema_version`。用户身份、设备身份和实验分流身份必须分开建模，不能用原始账号、设备序列号或凭据作为公开事件字段。实验分流身份和分流结果由外部实验控制方提供，框架只负责校验、应用、冻结和上报。

### 4.5 配置版本与运行时冻结

配置是框架加载和运行上层产品的输入，不是框架内部的隐式全局状态。每份配置至少包含 `config_id`、`config_version`、`schema_version`、`effective_at`、`expires_at`、`target_platform`、`compatibility` 和内容摘要。加载流程必须执行：

```text
发现版本 → 校验 Schema → 校验平台能力 → 校验兼容范围 → 选择版本 → 冻结运行上下文 → 记录并上报结果
```

页面或产品配置发生变化时，只影响新建的运行实例；已运行实例继续使用已冻结的配置版本，除非显式声明支持迁移。配置缺失、过期、不兼容或加载失败时，使用发布快照中声明的默认配置，并上报可诊断的降级原因。

运行时产生的所有出站请求（配置拉取、外部适配器调用、遥测上报）必须携带版本签名：`release_id`、`renderer_version`、`environment`、能力绑定摘要，以及实例已冻结的配置版本和实验分配标识。版本签名是上层进行版本路由、兼容门禁、灰度发布和实验数据拆分的依据；框架只负责携带与冻结版本签名，不依据版本签名作出实验或版本选择决策。配置请求允许上层按版本签名返回不同的 `config_version`；返回结果仍必须通过本章加载流程校验，通过后冻结到实例。

配置还承载资源级的运行期控制声明：停用某个注册组件的引用、下线某个页面入口等操作只能通过带 `config_version` 的声明进入，经校验后只影响新建实例，必须携带原因并上报。这为运营场景提供协议内的紧急止血手段，不留下绕过协议的操作旁路（§24.4 的实验停用同理）。

### 4.6 类型方言

全部契约（§5、§23、§37、§39、§40、§42）中引用或内联的 Schema 使用统一的类型方言：

```text
原语类型：string、number、boolean、enum
复合类型：array、object、$ref（引用）
约束子集：required、items、properties、values、default
```

规则：

- 方言是语言无关的声明资源，核心协议不解释任何实现语言的类型系统；各实现把方言映射到本语言类型系统后执行运行期校验（如 §40.3 输出校验）；
- 方言版本在 manifest 声明，并随发布快照冻结；`$ref` 只能解析到发布快照内的方言资源，悬空引用是静态错误；
- 方言版本是 §38.2 一致性比较的前提之一：两个 Renderer 不支持同一方言版本时，比较结果无效，必须先对齐声明；
- 方言表现力不足时按 §37.3 同样的方式用新版本扩展，禁止各实现私增类型语义。

## 5. 元组件契约

元组件契约应采用平台无关的描述方式：

```json
{
  "id": "button",
  "kind": "primitive",
  "props": {
    "label": {"type": "string"},
    "variant": {"type": "enum", "values": ["primary", "secondary", "danger"]},
    "disabled": {"type": "boolean"}
  },
  "slots": {},
  "events": {
    "press": {"payload": "void"}
  },
  "states": ["enabled", "disabled", "busy", "focused"],
  "layout": {
    "display": ["inline", "block"],
    "sizing": ["hug", "fill", "fixed"]
  },
  "accessibility": {
    "role": "button",
    "requires_label": true
  }
}
```

契约必须支持：

- 类型检查；
- 默认值；
- 可选和必填属性；
- 插槽类型；
- 事件载荷类型；
- 状态集合；
- 布局能力；
- 可访问性要求；
- 主题令牌；
- 样式面声明（§36.5）；
- 平台能力和降级策略。

元组件不能直接依赖业务对象。业务语义应由上层组件通过属性、数据映射和事件适配提供。

## 6. 组件组合模型

组件由树状节点组成，节点可以引用元组件或其他组件：

```json
{
  "id": "login-form",
  "kind": "component",
  "props": ["title", "submitText"],
  "events": ["submit", "cancel"],
  "tree": {
    "type": "Card",
    "children": [
      {"type": "Text", "bind": "title"},
      {"slot": "fields"},
      {"type": "Button", "bind": "submitText", "on": "press → submit"}
    ]
  }
}
```

组件必须区分：

- **结构**：组件有哪些子节点；
- **样式**：组件如何呈现；
- **数据**：组件读取哪些输入；
- **状态**：组件内部保存什么；
- **行为**：组件产生哪些事件；
- **平台变体**：不同平台如何替换实现。

组件树是纯结构描述。样式只能通过第 36 章的 Token、主题和样式片接入，不得内联平台样式语言；布局约束只能按第 7 章声明的挂载点表达；事件与操作的绑定使用第 39 章的绑定映射或相同的内嵌 Schema，不得引入第三种绑定形式。

组件内部可以使用本地状态，但不能偷偷修改外部页面或产品状态。外部变化必须通过事件和公开绑定完成。

## 7. 图层与布局系统

布局采用约束模型，不把某一个平台的 CSS 或坐标系统暴露为核心协议。

### 7.1 布局能力集

基础布局能力包括：

- Stack：横向或纵向排列；
- Grid：网格排列；
- Overlay：覆盖排列；
- Split：可调整分栏；
- Scroll：滚动区域；
- Anchor：相对锚定；
- Constraint：最小、最大、固定和填充尺寸；
- Responsive：断点、容器查询和平台条件。

布局能力集默认封闭（本章列举的能力）。核心布局能力（Stack、Grid、Overlay、Scroll、Anchor、Constraint、Split）的求解语义由 §7.3 规范固定，不由各实现自行解释。新增布局能力只能通过 §23 的布局能力注册进入（§23.12 kind: layout）：注册时必须同时交付与 §7.3 同构的约束求解规则描述、布局编译器检查规则、各目标 Renderer 的映射实现和降级策略；缺少检查规则的布局能力不得注册，也不参与约束求解。未注册的非标准布局需求只能以组件行为实现，且必须在 platform profile 中声明其不参与约束求解，由布局编译器在目标平台给出降级诊断。

### 7.2 约束声明与挂载点

布局约束应能表达：

```text
width: fill
maxWidth: 640
padding: space.4
mobile: stack(vertical)
tablet: split(2)
desktop: split(3)
```

占位类约束（width、height、padding、gap 等）属于布局；外观属性属于第 36 章。归属歧义的属性（例如边框宽度）由对应元组件契约逐个声明归属，未声明的属性是静态错误。

布局约束的挂载点有且只有两个：图层的区域约束和节点的自身约束。尺寸声明只使用本章词表：hug（尺寸由内容度量决定）、fill（分配剩余空间）、fixed（固定值）、min/max（上下界修饰符）和间距 Token；引入词表之外的尺寸语义是静态错误。

### 7.3 布局求解语义（形式化）

布局求解是纯函数，输入与输出固定：

```text
solve(约束集, 内容度量, 可用空间) → 规范化矩形集
```

通用解析规则：

- 节点自身约束解析为有界的尺寸需求 `{min_w, max_w, min_h, max_h, grow_w, grow_h}`：`fixed` 生成 min=max=声明值；`fill` 生成 grow=true，min 取内容度量或 0；`min/max` 修饰符生成上下界；`hug` 表示尺寸由内容度量决定，不参与空间分配；
- 可用空间自根向下传递：父容器先扣除自身 padding（space Token）与 gap，再把剩余空间分配给子节点；内容度量由元组件契约（§5）声明并保持确定性；
- 求解输出是规范化矩形集（逻辑单位 x/y/w/h）；同一输入在解释模式与编译模式、不同 Renderer 上必须产生相同输出；布局基线用例使用固定尺寸的合成元组件，排除内容度量差异（§44.3）。

核心容器的分配规则固定如下：

- **Stack**：子节点按声明顺序沿主轴排列。分配规则：(1) hug 子节点按内容度量占位；(2) 剩余主轴空间先满足全部 fill 子节点的 min，不满足时按声明顺序分配、其余取 0，并记录溢出诊断；(3) 其余空间在 fill 子节点之间均分，且不得低于各自 min。交叉轴上：fill 取容器交叉尺寸，hug 取内容度量，fixed 取声明值；
- **Grid**：轨道列表由 fixed、fill、auto 轨道组成；auto 轨道取其跨内内容度量的最大值，剩余空间由 fill 轨道均分；子项必须声明显式坐标或使用确定性自动流顺序（声明顺序），两者混用产生歧义是静态错误；跨行/列 span 不得超过轨道数；
- **Overlay**：子节点按声明顺序叠放，声明顺序即确定性的 z 序；每个子节点独立以容器为可用空间求解；Anchor 偏移只相对容器边缘解析，不得引用兄弟节点，锚定不得形成循环依赖；
- **Scroll**：沿滚动轴为子节点提供无界可用空间，其余轴按普通容器规则求解；
- **Split**：按声明比例分配；运行期拖拽属于宿主交互，静态求解按 fill 轨道规则执行。

以下冲突与不可满足情形是静态错误，由布局编译器在构建期拒绝：同一节点同轴同时声明 fill 与 fixed；fixed 尺寸超出某个已声明条件下的可用空间；锚定或空间分配形成循环依赖；同轴存在冲突的定位规则。

### 7.4 条件布局

条件布局（断点、容器查询和平台条件）是"条件 → 布局方案"的声明式映射：条件谓词使用第 37 章的引用与比较子集，方案只能是 §7.1 布局能力的声明式组合。同一目标的多个条件按声明顺序求值，首个命中的方案生效，未声明排序的命中歧义是静态错误；每个条件布局必须声明条件全不命中时的默认方案，缺失默认方案是静态错误。布局表达式与交互语法一样版本化管理，禁止内嵌命令式布局逻辑。

### 7.5 布局编译器检查与页面级规则

布局编译器负责发现：

- 无法满足的尺寸约束；
- 循环依赖；
- 互相冲突的定位规则；
- 平台不支持的布局能力；
- 在目标窗口下可能溢出的内容。

检查不通过产生 mf.layout 诊断（§41）；声明了降级策略的平台差异按声明执行并记录，禁止静默省略。

图层需要声明滚动和覆盖关系。不能让每个组件自行决定页面滚动，否则页面会出现多个不可控滚动容器。

页面未声明图层树时，编译器视为仅存在一个隐式 ContentLayer（占用页面的内容区域），该隐式图层同样参与布局、滚动与覆盖检查；页面首次声明任一显式图层后，隐式图层不再生成。这保证简单页面的纯配置创建零图层成本，复杂页面渐进采用图层结构（§2.7）。

## 8. 页面模型

```json
{
  "id": "dashboard-page",
  "kind": "page",
  "route": "/dashboard",
  "parameters": {},
  "shell": "app-shell",
  "layers": ["header-layer", "sidebar-layer", "content-layer"],
  "state": ["selectedPeriod", "isFilterOpen"],
  "lifecycle": {
    "onEnter": "loadDashboard",
    "onLeave": "saveDraft"
  },
  "errorBoundary": "dashboard-error",
  "platformVariants": {
    "mobile": "dashboard-mobile-page"
  }
}
```

页面必须定义：

- 路由标识和参数；
- 页面壳和图层顺序；
- 页面级状态；
- 生命周期事件；
- 空、加载、错误和成功状态；
- 页面级快捷操作；
- 可访问性标题和焦点入口；
- 平台变体；
- 可被哪些页面导航到。

页面不应直接承载不可复用的复杂业务逻辑。复杂逻辑应提取为交互流程或组件动作。

## 9. 产品和导航模型

导航模型使用有向图：

```text
NavigationGraph
├── nodes: pages, dialogs, external entries
├── edges: push, replace, modal, tab, back
├── guards: conditions and access rules
├── parameters: typed route parameters
└── fallback: missing/denied/error targets
```

导航检查包括：

- 路由 ID 唯一；
- 参数类型一致；
- 入口可达；
- 不存在孤立页面；
- 返回路径有定义；
- 权限拒绝有 fallback；
- 深链接可恢复；
- 页面变体存在或有降级策略。

菜单是导航图的一个投影，不是导航图本身。

## 10. 交互模型

交互使用受限事件图，不鼓励在模板中写任意脚本：

```text
事件 → 前置条件 → 状态变更 → 副作用 → 后续事件
```

示例：

```text
submit.press
  → validate(form)
  → set(submitting, true)
  → execute(local action)
  → set(submitting, false)
  → navigate(success)
```

上述记法是示意，不是可解析语法。动作链、绑定和条件表达式统一使用第 37 章的形式化语法并按语法版本管理；"点击行为 → 具体操作"的绑定统一通过第 39 章的绑定映射或同构的内嵌 Schema 声明。实现不得私增语法或引入第二个表达式语言。

动作类别不包含采集或上报动作：数据日志与遥测事件由运行时按 §24.7 的零侵入机制自动产生，业务逻辑中不得出现采集调用，错误分支也不得依赖日志上报作为处理手段。

动作分为：

1. **UI Action**：显示、隐藏、聚焦、滚动、动画；
2. **State Action**：读写组件、页面、会话或本地持久状态；
3. **Navigation Action**：push、replace、modal、back；
4. **Local Function**：在本地执行的纯计算；
5. **Host Capability**：文件、摄像头、通知、剪贴板等宿主能力；
6. **External Adapter**：可选的 API、文件或服务适配，不进入核心依赖；调用必须持有 Data Contract（§40）。

所有动作都要声明输入、输出、错误和取消语义。运行时不把“请求超时”自动当成“操作未执行”。

### 10.1 动作契约（Action Contract）Schema

全部六类动作的公共契约面固定为以下最小 Schema。带副作用的动作（function、capability、adapter）注册时必须交付本契约；ui、state、navigation 动作的输入输出与错误语义由运行时内置，并纳入 §37.4 静态检查：

```json
{
  "id": "local.calc-tax",
  "kind": "function",
  "input": {"properties": {"amount": {"type": "number"}}, "required": ["amount"]},
  "output": {"type": "number"},
  "errors": ["calc.overflow"],
  "timeout_ms": 3000,
  "idempotency": {"kind": "read"},
  "cancellation": {"policy": "cancel-previous"},
  "unknown_result": {"state": "unknown", "resolution": "surface"}
}
```

规则：

- `idempotency.kind` 只能是 `read`、`idempotent-write`、`non-idempotent`；写动作必须声明幂等键与 `commit_boundary`，与 Data Contract（§40.2）和 Business Fact（§24.1 第 4 类）对齐；
- `cancellation.policy` 只能是 `cancel-previous`、`supersede`、`queue`、`reject-new`，并与 §39 绑定条目的并发策略声明一致，两者冲突是静态错误；
- `unknown_result.resolution` 只能是 `query`（通过显式查询动作收敛）或 `surface`（保持 unknown 并暴露给用户）；未声明 `unknown_result` 的动作超时后进入 unknown，不当作失败自动重试（§22.1）；
- 契约随动作注册进入版本化资源（§4.2、§23.12），校验并入 §18.1 与 §39.3 静态检查。

## 11. 状态模型

状态按所有权和生命周期分层：

```text
Component State
Page State
Session State
Product State
Persistent Local State
Derived State
```

规则如下：

- 组件状态不能被任意页面修改；
- 页面状态随页面实例创建和销毁；
- 会话状态由产品运行时拥有；
- 持久状态必须声明版本和迁移规则；
- 派生状态不能作为第二份事实来源；
- 异步状态必须区分 idle、loading、success、empty、error 和 cancelled；
- 进程挂起和恢复不能依赖内存对象仍然存在。

框架核心不强制某个状态库。Renderer 可以把模型映射到 React、Flutter、Compose 或原生状态机制。

## 12. Web 与客户端适配

核心模型保持平台无关，Renderer 处理平台差异：

```text
Shared Model
├── Web Renderer
│   ├── browser navigation
│   ├── DOM/accessibility
│   └── responsive layout
├── Mobile Renderer
│   ├── native lifecycle
│   ├── system back
│   └── device capabilities
└── Desktop Renderer
    ├── window lifecycle
    ├── keyboard/menu
    └── filesystem integration
```

平台差异通过三种方式表达：

- 同一组件的属性适配；
- 同一组件的平台实现替换；
- 页面或图层的平台变体。

不能把所有平台压缩成最低共同能力。能力不足时，编译器应拒绝、替换或使用明确声明的降级实现。

### 12.1 Renderer Contract Schema

每个 Renderer 必须交付以下最小契约声明，作为 §28、§33 一致性测试与 §38.2 分级验收的输入：

```json
{
  "renderer_id": "web-dom",
  "platform": "web",
  "consistency": {
    "async_states": ["idle", "loading", "success", "empty", "error", "cancelled"],
    "event_dispatch": "declaration-order-deterministic",
    "navigation": ["push", "replace", "modal", "tab", "back", "deeplink"],
    "error_boundary": "declared-scope-only",
    "accessibility": ["role", "label", "focus-order", "lang", "contrast"]
  },
  "layout_solver": {"core": ["stack", "grid", "overlay", "scroll", "anchor", "constraint", "split"], "syntax_version": "1.0"},
  "instance_identifiers": ["page_instance_id", "component_instance_id", "render_revision"],
  "allowed_differences": [
    {"area": "motion", "difference": "timing-and-easing-mapping", "user_visible": true, "degradation": "reduced-motion-group"}
  ],
  "capability_degradation": {"on_unsupported": "declared-alternative-or-error"}
}
```

规则：

- `allowed_differences` 必须逐条枚举且每条带降级声明；§7.1 的布局降级、§36.5 的样式面降级与 §36.7 的动效替代必须出现在该清单中，未枚举的运行期差异按一致性缺陷处理；
- `consistency` 各项是 §33 一致性测试的判据来源，不得引用测试外的主观描述；
- 契约版本化并随发布快照冻结（§16）。

## 13. 编译器和运行时

### 13.1 编译阶段

编译器执行：

1. 解析项目模型；
2. 校验 Schema；
3. 建立对象索引；
4. 检查组件和页面引用；
5. 检查布局约束；
6. 检查导航图；
7. 检查交互事件图；
8. 检查平台能力；
9. 生成规范化 IR；
10. 输出目标平台 manifest、代码和资源清单。

### 13.2 运行阶段

运行时负责：

- 创建产品实例；
- 管理页面栈和导航；
- 管理状态生命周期；
- 分发事件；
- 执行动作；
- 调用宿主适配器；
- 处理加载、错误、取消和恢复；
- 输出结构化运行诊断。

运行时不能修改项目定义。运行中的实例使用发布时固定的模型和策略。

运行时可以产生观测事件，也可以读取外部下发的配置和实验上下文，但不能直接修改实验配置或项目模型。事件通过版本化 Telemetry Contract 进入受控的采集队列；采集器故障不能阻断核心用户流程，除非该事件属于明确声明的可靠业务事实。框架不负责实验分流、样本选择、指标计算、实验启停和实验结论。

运行时加载配置时必须使用声明的配置版本，完成 Schema、平台能力、有效期和兼容范围检查后，将有效配置摘要冻结到运行实例。配置加载失败时使用发布快照中的默认配置并上报降级原因；配置刷新不静默修改已运行实例。

### 13.3 解释执行和代码生成

首版建议同时保留两种模式：

- **解释模式**：适合 Vibe Coding 预览、调试和快速迭代；
- **编译模式**：生成目标平台代码和静态资源，适合发布。

两种模式必须使用同一个 IR，避免预览行为和发布行为分叉。

## 14. 面向 Vibe Coding 的设计

Vibe Coding 的第一类对象不是文件，而是项目模型中的资源。

框架不提供可视化编辑器，也不把编辑器内置为框架组件。框架提供的是底层编排与接入能力：项目模型读写、结构化命令、局部上下文查询、影响分析、差异预览、修改审计和回滚。任何可视化编辑器（画布、图层树、组件面板、属性面板、交互编辑器）都必须作为这些协议的上层客户端实现，并通过同一套一致性回归验证（§18.3）证明自己是合格的项目模型客户端，不得自建平行事实来源。

AI 操作应使用结构化命令：

```text
create_component
update_component
insert_layer
replace_page_variant
connect_navigation
add_interaction
create_page
create_page_from_template
register_component
register_resource
rename_resource
inspect_impact
validate_project
```

命令面覆盖 §23.11 的全部注册资源类别：`register_component` 注册宿主实现组件（kind: component），`register_resource` 按 kind 注册元组件、数据适配器、布局能力、样式资产、本地函数（kind: function）与宿主能力（kind: capability）；`inspect_impact`、`validate_project` 对全部资源类别生效。

每次 AI 修改都应产生：

- 修改目标；
- 修改前后摘要；
- 影响对象；
- 验证结果；
- 未解决问题；
- 可回滚修订。

AI 上下文按任务裁剪：

```text
当前页面
→ 当前图层
→ 目标组件
→ 相关状态
→ 相关交互
→ 被影响的导航和资源
```

不把整个项目所有源代码无条件塞给模型。模型可以通过索引查询页面、组件、引用、依赖和可用能力。

AI 生成的文本代码只能通过受控入口进入项目模型；不能让任意字符串直接绕过 Schema、权限和编译检查。

```text
│   └── themes/
```

`config/` 存放配置平面资源的创作形态（§2.9）：发布快照内声明的默认配置（§4.5）、内容资产、运营变体与实验上下文的本地版本。每份配置携带 `config_id`、`config_version`、`schema_version` 与内容摘要（§4.5）；默认配置随发布快照冻结，动态下发配置以本目录版本为可追溯源头，创作、校验与下发不使用两套口径。

## 16. 发布和版本

项目采用草稿、验证、发布和运行四种状态：

```text
Draft → Validated → Published → Running
```

发布产物包含：

- 完整项目模型摘要；
- IR 版本；
- Renderer 版本；
- 资源摘要；
- 平台能力要求；
- 主题和配置摘要；
- i18n 资源摘要（§42）；
- 迁移信息；
- 诊断规则版本。

页面编辑只产生新修订，不改变已运行实例。运行实例固定 `release_id`。回滚只影响新启动实例，除非明确执行运行实例迁移。

发布必须是不可变快照。资源、组件和页面不能在发布后被原地修改，否则无法复现构建结果。

版本差异的表达必须与快照边界一致：同一发布快照内，通过冻结不同 `config_version` 与主题表达可变行为；需要改变 IR、Renderer、资源或模型结构的差异必须产生新的发布快照和新的 `release_id`，不得通过配置差异偷换实现。

### 16.1 Recovery Contract Schema

恢复与迁移规则必须是显式契约，运行时按契约执行恢复（§22.1）：

```json
{
  "id": "recovery-default",
  "kind": "recovery-contract",
  "schema_version": "1.0",
  "snapshot": {
    "route": true,
    "parameters": true,
    "page_state": true,
    "session_state": "declared-only",
    "pending_actions": true,
    "state_revision": true,
    "snapshot_version": "1.0"
  },
  "revalidation": {
    "permission": "recheck",
    "release_binding": "must-match-or-migrate",
    "data_freshness": "per-contract-staleness"
  },
  "unknown_side_effects": {"on_restore": "surface-as-unknown", "auto_retry": false},
  "migration": {"on_release_change": "explicit-only", "migrators": []},
  "expiration": {"max_age_s": 86400, "on_expired": "fresh-start"}
}
```

规则：

- `snapshot` 中布尔项声明该类内容是否进入恢复快照；`session_state` 只能取 `declared-only`（仅显式声明持久化的会话状态）；
- `unknown_side_effects.auto_retry` 固定为 false：未知结果的副作用不得自动重试（§22.1、§44.3 基线 27）；
- 迁移器按 §22.3 版本迁移纪律登记；契约缺失时运行时禁止执行恢复，进入全新启动并上报诊断。

## 17. 扩展机制

扩展分为：

- Primitive Extension：注册新增元组件（§23.12 kind: primitive）；
- Component Extension：注册可复用组件（§23.12 kind: component）；
- Layout Extension：注册新增布局能力（§7、§23.12，须附检查规则与降级策略）；
- Adapter Extension：注册数据适配器（§40、§23.12 kind: adapter）；
- Style Asset Extension：注册 Token 集、主题与样式片（§36、§23.12 kind: style-asset）；
- Renderer Extension：新增平台实现；
- Host Extension：新增设备或系统能力；
- Compiler Extension：新增编译目标或优化；
- Tool Extension：新增编辑器、CLI 或 AI 工具。

扩展必须提供：

- 稳定 ID；
- Schema；
- 能力声明；
- 版本；
- 兼容范围；
- 预览实现；
- 运行实现；
- 测试和降级策略。

核心框架不动态执行任意项目目录中的代码。可信扩展通过显式注册进入构建环境，运行时能力通过宿主注入。扩展与上层宿主组件的注册协议由 §23 组件注册契约统一定义。

### 17.1 Capability Contract Schema

宿主能力（§10 第 5 类）通过以下最小契约注册与校验：

```json
{
  "id": "capability.camera.capture",
  "kind": "capability",
  "states": ["available", "permission_denied", "temporarily_unavailable", "unsupported", "unknown_result"],
  "input": {"properties": {"options": {"type": "object"}}, "required": []},
  "output": {"type": "object"},
  "errors": ["cap.permission-denied", "cap.unavailable"],
  "permissions": ["camera.use"],
  "availability": {"kind": "runtime-detect"},
  "degradation": {
    "on_unavailable": {"strategy": "alternative", "target": "capability.file.pick"},
    "on_denied": {"strategy": "error-boundary", "target": "camera-error"}
  }
}
```

规则：

- `states` 必须包含 §22.1 的五个可判定状态，禁止只声明成功路径；
- `degradation` 必须为每个非成功状态声明策略：`alternative`（指向已注册的替代能力）、`error-boundary`（指向已声明的错误边界）或 `disable`（功能入口禁用并告知）；缺失降级声明的能力不得注册（§23.12）；
- 能力调用的取消与未知结果语义遵循 Action Contract（§10.1）；能力实现按 §23.3 双注册通道进入。

### 17.2 扩展类别差异面

| 扩展类别 | 差异面 | 交付要求 |
|---|---|---|
| Primitive / Component / Adapter / Layout / Style-asset / Function / Capability | 统一资源注册协议差异面（§23.12） | 注册清单、契约、版本与兼容、测试 |
| Renderer | platform profile、能力矩阵、§12.1 契约声明、一致性测试证据 | 通过 §44.3 基线后方可声明分级（§38.2） |
| Host（实现装载器与能力） | 装载器 descriptor Schema、注入入口声明（§23.3）、§17.1 能力契约 | 注入一致性校验与审计（§32） |
| Compiler | 目标平台清单、IR 版本兼容声明、产物清单格式 | 增量与缓存键规则（§22.2） |
| Tool（编辑器 / CLI / Agent） | 使用的结构化命令面（§14）、上下文查询与影响分析调用方式 | 通过同一 §18.3 一致性回归，不得自建平行事实来源 |

## 18. 验证和质量机制

### 18.1 静态验证

- Schema 和类型检查；
- 组件插槽检查；
- 布局约束检查；
- 路由和参数检查；
- 不可达页面检查；
- 交互循环和未处理错误检查；
- 平台能力检查；
- 资源引用检查；
- 资源注册契约与实现一致性检查（§23，覆盖组件、元组件、适配器与布局能力；含布局能力、依赖、插槽与生命周期声明，§23.9、§23.10、§23.11、§23.12）；
- Data Contract Schema 与适配器引用检查（§40）；
- i18n message 引用与 locale 完整性检查（§42）；
- 容器信息契约检查：`consumes` 解析可达、`provides` 形状合法、幽灵依赖报错（§2.8）；
- 布局约束求解检查：冲突、循环、不可满足与条件布局默认方案（§7.3、§7.4）；
- 动作契约检查：并发策略、幂等、超时与 unknown 收敛声明完整（§10.1、§39.3）；
- 动效面检查：动效编排只引用已声明动效面与 motion Token（§36.5）；
- 性能预算声明检查：必报指标全部有预算条目与测量条件（§22.2）；
- 运营标准事件族字段与互斥归属校验；投影依赖的标准事件类已登记，`feature_ref`、`page_definition_id` 引用存在（§24.2）；
- 受控交叉清单检查：实验与运营变体声明改写的资源面均已登记，未登记改写是静态错误（§2.9、§24.4）；
- 三平面分离检查：模型资源内联可执行逻辑或运行时数据、配置载荷携带代码或未验证数据、运行数据回写项目模型（§2.9）；
- 文案通道判定检查：同一内容位同时声明 i18n message 与内容资产来源是静态错误（§42.7）；
- 可访问性必填项检查。

### 18.2 运行验证

- 页面初始化和销毁；
- 前进、后退和深链接；
- 状态恢复；
- 加载、空、错误和取消状态；
- 窗口尺寸和屏幕旋转；
- 布局求解在断点切换与窗口变化下的确定性及降级诊断（§7.3-§7.5）；
- 减少动效偏好下的动效替代与记录（§36.7）；
- 平台能力不可用；
- 资源加载失败；
- 版本迁移和回滚。

### 18.3 Vibe Coding 回归

同一项目模型应验证：

- AI 修改后对象 ID 不丢失；
- 未修改页面不产生无关差异；
- 组件修改能正确报告影响页面；
- 解释模式和编译模式行为一致；
- 发布结果可重复生成；
- 删除资源不能留下隐式引用。

### 18.4 质量属性契约

高可用、高性能和高可维护性不能只作为实现目标，必须成为模型、Renderer、Host 和发布工具共同遵守的契约。

框架增加以下最小契约；每项契约的最小可校验 Schema 见括注章节，"只有文字纪律而无 Schema"的契约视为未定义，不得进入发布清单（§27）：

- **Data Contract**（§40.2）：数据源、输入输出 Schema、加载、缓存、变更、权限和陈旧策略；
- **Action Contract**（§10.1）：动作输入输出、幂等、超时、取消、失败、未知结果和提交边界；
- **Capability Contract**（§17.1）：宿主能力的可用、拒绝、暂不可用、不支持和结果未知状态；
- **Renderer Contract**（§12.1）：各平台必须一致的状态、事件、导航、错误和可访问性行为，以及允许差异；
- **Recovery Contract**（§16.1）：路由、参数、页面状态、待处理动作和发布版本的恢复与迁移规则；
- **Performance Contract**（§22.2）：模型检查、增量编译、启动、导航、交互、内存和资源体积预算。
- **Telemetry Contract**（§24.2）：事件名称、Schema、身份边界、采样、隐私分类、队列、重试、丢弃和保留策略；
- **Experiment Contract**（§31）：外部实验控制方提供的实验键、配置版本、分流结果、稳定性标识、实验组和曝光要求；框架负责校验、应用、冻结和上报，不负责分流和实验决策。

上层业务组件和业务规则不属于上述核心契约的实现范围；它们必须通过公开组件契约、数据适配器、交互动作和版本化配置接入框架。

上述契约必须有版本、Schema、诊断码和兼容范围。缺少契约的扩展只能作为实验能力，不能进入可发布快照。

## 19. 推荐实施顺序

实施阶段是交付顺序，不是能力裁剪：§20 的框架基线是最小完整核心能力集，不存在更小的合规子集；中间产物只能按 §38.2 如实声明已达分级，不得作为"裁剪版框架"交付。

### 阶段一：模型、契约和验证核心

实现 Project、Primitive、Component、Layer、Page、Navigation、Interaction 的 Schema、ID、规范化序列化、引用索引、版本迁移和静态验证器；同时固化 Data Contract（§40）、Action Contract、Capability Contract 和 Recovery Contract，以及组件注册契约（§23）、统一诊断码注册表（§41）和 i18n 资源模型（§42）。主题 Token、主题、样式片（§36）、交互与绑定语法（§37）和绑定映射（§39）的 Schema、解析与静态检查同属本阶段交付物。

交付一个命令行工具：

```text
microflow-ui check
microflow-ui inspect
microflow-ui impact
microflow-ui normalize
```

命令集与 §23.8 的接入工作流一一对应：项目与资源初始化、注册清单登记、校验、影响分析和发布演练都必须有对应命令；命令面随阶段扩展，但不提供绕过 §14 结构化命令的平行通道，每个命令的输出必须是项目模型中的版本化资源。

### 阶段二：解释运行时

实现规范化 IR、页面实例、组件树渲染、状态、导航、事件分发、动作取消、重复提交处理、错误边界和基础恢复。先选择一个 Renderer，建议优先 Web。

### 阶段三：Vibe Coding 接口

实现结构化编辑命令、局部上下文查询、影响分析、差异预览、回滚、AI 修改审计、观测 Schema 查询和外部配置/实验上下文校验。

### 阶段四：编译器

将同一 IR 编译为 Web 产物，加入增量编译、内容寻址缓存、路由代码分割、资源清单和观测/实验版本清单，确保解释预览与编译产物保持行为一致。

### 阶段五：客户端 Renderer

在 IR 稳定后接入 Flutter、React Native、Compose 或原生 Renderer。平台差异通过能力声明和变体处理。

### 阶段六：上层工具接入面

框架不实现可视化编辑器。本阶段交付编辑器类上层工具所需的接入面：项目模型读写、结构化命令、局部上下文查询、影响分析、差异预览、修改审计和回滚协议（§14、§17）的完整实现与契约测试。画布、图层树、组件面板、属性面板、导航图和实时预览由上层或第三方基于这些协议建设，并以其能否作为合格的项目模型客户端通过一致性回归验证为准。

每个阶段必须有对应的性能基准、故障注入和 Renderer 一致性测试，不把内存替身或单次预览结果视为生产能力证据。

## 20. 框架基线范围

本框架不定义 MVP 或可裁剪子集：下列基线本身就是前端开发的最基本、最核心能力，各项互为整体（模型驱动校验、编译、运行、注册、观测与版本化的闭环）。任何低于基线的产物只能按 §38.2 如实声明其一致性分级，不得称为 MicroFlow Frontend 的裁剪实现。

框架基线包含：

- 元组件和组件树；
- 启动元组件集 Tier A 与能力降级声明（§38）；
- 主题 Token、主题和基础样式片（§36）；
- 交互与绑定语法 v1 的解析和静态检查（§37）；
- 绑定映射与六类操作的最小集（§39）；
- Stack、Grid、Overlay 三类布局；
- 隐式默认图层与显式图层的共存规则（§7）；
- 页面和页面导航；
- 页面模板与 create_page、create_page_from_template 配置构造命令（§2.7、§14）；
- 页面、组件和会话状态；
- 基础交互动作；
- 最小统一资源注册契约：公共注册纪律、组件清单、元组件与数据适配器差异面、布局能力与依赖声明、构建期注册与宿主注入、契约一致性校验、确定性版本解析（§23、§23.11、§23.12）；
- 注册组件的结构传递、宿主生命周期契约与对应的静态检查（§23.9、§23.10）；
- Data Contract 最小集：输入输出 Schema、超时、幂等、缓存与陈旧策略（§40）；
- 统一诊断码注册表与命名空间（§41）；
- i18n 最小集：locale 注册表、message 资源、格式化子集、回退与缺失诊断（§42）；
- 文案通道判定与 i18n/内容资产互斥校验（§42.7）；
- 最小 Data Contract、Action Contract 和 Recovery Contract；
- 加载、空、错误状态；
- Web Renderer；
- JSON 或等价结构化项目模型；
- `check`、`inspect`、`impact` 和 `build` 命令；
- 解释预览和编译产物；
- 发布快照和回滚；
- 增量构建、路由级代码分割和基础性能预算；
- 基础可访问性校验和宿主能力降级诊断；
- 容器信息契约最小集与 `consumes` 可解析检查（§2.8）；
- 三平面分离检查与受控交叉清单校验（§2.9）；
- 内容位曝光与活动归因标准事件族的最小字段规范（§24.2）；
- 最小 Telemetry Contract、可靠队列和本地失败降级；
- 追踪上下文传播声明与前后端运行标识关联的最小集（§24.8）；
- 发布健康度标准投影（§43.1）；
- 版本化配置加载、Schema/能力/兼容性校验、运行时冻结、默认配置降级和配置结果上报；
- 外部实验分流结果、曝光事件、配置版本和外部停用状态的接入与校验。

基线暂不固定：

- RPC 或 API 协议；
- 数据库和后端服务；
- 具体状态管理库；
- 具体 Web UI 库；
- 具体移动端工具包；
- 可视化编辑器实现（框架不提供编辑器，只提供上层工具接入协议）；
- 任意脚本执行；
- 翻译管理平台与机器翻译集成；
- 订阅式查询与告警平台实现（§43.2 只定义协议，不内置实现）；
- 全自动跨平台像素级一致。

基线还必须明确不承诺：跨主机高可用、外部业务资源的全局恰好一次、任意宿主能力的自动恢复，以及没有实际部署和故障演练证据的生产级可用性。

## 21. 基础设计结论

MicroFlow Frontend 的核心抽象不是“前端调用后端”，而是：

```text
元组件
  ↓
组件
  ↓
图层
  ↓
页面
  ↓
产品
  ↓
目标平台产物
```

它的核心资产不是某个 React 项目或 Flutter 项目，而是可查询、可组合、可验证、可版本化的前端产品模型。

后端 MicroFlow 负责业务流程和执行协议；前端 MicroFlow 负责产品界面和交互结构。两者可以集成，但任何一方都不应成为另一方的运行前提，也不应依赖对方的实现语言；集成只通过显式协议（如追踪关联，§24.8）完成。

这套设计的第一目标不是提供更多 UI 控件，而是让 Vibe Coding 具备可靠的结构边界、影响分析、局部上下文和可重复生成能力。

## 22. 高可用、高性能与高可维护性增强设计

### 22.1 高可用

前端可用性按“资源可获取、应用可启动、页面可导航、核心动作可执行、外部依赖可降级、实例可恢复、版本可回退”分层定义。每一层都必须声明成功条件、超时、降级目标和诊断码。

运行实例固定 `release_id`、`renderer_version`、`capability_binding` 和 `policy_digest`。页面恢复快照至少包含路由、参数、页面状态、会话状态、待处理动作、最后确认的状态修订和快照版本。恢复时必须重新校验权限、版本和数据新鲜度；无法确认的副作用只能进入 `unknown`，不能当作失败后自动重试。

Host Capability 必须返回 `available`、`permission_denied`、`temporarily_unavailable`、`unsupported` 或 `unknown_result` 等可判定状态。能力不足时，运行时只能使用声明过的降级实现或进入明确错误边界。

发布系统必须保证模型、IR、Renderer、资源和配置来自同一不可变快照；灰度、回滚和资源清理都以快照引用关系为依据。高可用声明必须通过目标平台的启动、恢复、依赖故障、资源失败和回滚演练验证。

### 22.2 高性能

模型编辑和构建采用增量策略。对象 ID、规范化内容摘要和反向索引共同形成缓存键；修改资源时，只重新验证、编译和打包受影响的闭包。解释模式运行规范化 IR，不直接重复解析原始项目文件。

Web Renderer 必须支持路由级代码分割、按需加载、资源优先级、列表虚拟化、静态子树复用和受控状态订阅。客户端 Renderer 必须声明冷启动、页面切换、内存、后台恢复和大列表预算。布局编译器在编译期解决可静态解决的约束，运行期只处理必须动态计算的约束。

首版性能指标至少包括：增量检查时间、增量构建时间、冷启动时间、页面导航 P95、交互反馈 P95、典型页面内存峰值和发布产物体积。指标必须记录目标设备、数据规模和网络条件。

Performance Contract 以预算条目为最小 Schema，预算是发布门禁的输入（§22.4）：

```json
{
  "metric_id": "perf.navigation.p95",
  "budget": {"value": 300, "unit": "ms"},
  "percentile": 95,
  "condition": {"device_class": "mid-tier-2020", "data_scale": "list-1000", "network": "4g"},
  "stage": "runtime",
  "blocking_release": true,
  "measurement": {"instrument": "runtime-interceptor", "aggregation": "release.health"}
}
```

规则：

- 必报指标（增量检查、增量构建、冷启动、导航 P95、交互反馈 P95、内存峰值、产物体积）每项都必须有预算条目；缺预算的指标不进入发布健康度（§43.1）；
- `condition` 必须显式记录目标设备、数据规模和网络条件；跨条件比较预算结果无效；
- `blocking_release` 为 true 的预算超标时发布门禁失败，并产生 `mf.perf.budget-exceeded` 诊断（§41）。

### 22.3 高可维护性

对象放置必须遵循职责规则：视觉结构放入组件，页面生命周期逻辑放入页面，跨页面流程放入交互，纯计算放入 Local Function，设备和系统访问放入 Host Capability，业务数据访问放入 External Adapter，平台差异放入 Renderer Variant。

Schema、IR、Renderer、Host 和扩展采用兼容矩阵管理。每次破坏性变更必须提供迁移器、诊断和回滚条件；扩展必须有锁定版本、依赖范围、能力声明、测试和废弃策略。

生成代码不作为模型事实来源。手写扩展只能通过稳定契约引用生成结果，生成器必须提供确定性序列化、清晰的覆盖边界和失败时保留上一版产物的策略。

维护期诊断统一关联 `release_id`、`renderer_version`、`page_instance_id`、`layer_instance_id`、`component_instance_id`、`interaction_id`、`action_request_id` 和 `state_revision`，以便从用户动作追踪到状态、宿主调用和最终渲染结果。

### 22.4 必须通过的质量门禁

- Schema、规范化、迁移和引用索引检查通过；
- 解释模式与编译模式通过行为一致性测试；
- 所有 Renderer 通过核心状态、导航、错误、取消和可访问性一致性测试；
- 外部能力不可用时按照契约降级或失败；
- 发布快照可重复构建并可回滚；
- 增量构建不会重新生成无关页面；
- 恢复不会重复提交未知结果的副作用；
- 资源注册契约与实现一致性验证通过（§23，全类别）；
- i18n 完整性、回退与镜像检查通过（§42）；
- 性能指标达到目标设备和数据规模下的预算；
- 故障注入结果、诊断链路和剩余风险均有记录。

## 23. 组件注册契约

### 23.1 定位

框架负责编排，上层业务组件通过注册进入框架。注册是显式、声明式、版本化的一等协议，回答"代码实现的业务组件如何进入项目模型并被编排"：

- 上层组件可以两种形态存在：**模型组合组件**（§6，由元组件在模型中组合而成）和**宿主实现组件**（代码实现，通过本章契约注册）；两者可以在同一组件树、同一页面中混用，编排语义完全一致；
- 注册只登记契约与实现指向，不把实现代码并入框架；框架不依赖任何注册方的代码结构、语言和构建方式，注册协议本身不包含语言语义；
- 注册不能绕过 Schema、权限、版本和能力检查（§1）；未注册的组件引用是静态错误；
- 注册协议本身版本化，与 §37 语法版本、§4.5 配置版本共同构成兼容边界。

### 23.2 注册清单

注册清单是项目模型中的版本化资源（§4.2），登记宿主实现组件的契约与实现指向：

```json
{
  "id": "note-editor",
  "kind": "component",
  "implementation": {
    "kind": "host",
    "loader": "host-loader-default",
    "descriptor": {"entry": "extensions/note-editor", "export": "NoteEditor", "language": "typescript"}
  },
  "contract": {
    "props": {"value": {"type": "string"}, "readOnly": {"type": "boolean"}},
    "slots": [],
    "events": {"change": {"payload": "string"}, "save": {"payload": "void"}},
    "states": ["empty", "ready", "busy"],
    "layout": {"display": ["block"], "sizing": ["hug", "fill"]},
    "exposed_styles": ["background", "radius"],
    "platform_variants": {"mobile": "note-editor-native"},
    "accessibility": {"role": "textbox", "requires_label": true}
  },
  "dependencies": [],
  "version": "1.1.0",
  "compatibility": {"renderer": ">=1.0 <2.0", "syntax_version": "1.0"},
  "capabilities": [],
  "tests": "tests/components/note-editor"
}
```

规则：

- `implementation.kind` 为 `host` 的组件定义必须携带完整注册清单；模型组合组件（§6）不携带 `implementation`；
- 实现编址与语言无关：`implementation.loader` 指向已注册的实现装载器（Host Extension，§17），由装载器定义实现的编址、装载和注入方式；`descriptor` 对核心协议不透明，由装载器按其声明的 Schema 校验；
- 语言信息（如 `descriptor.language`）只是声明性元数据：核心协议不解释它，不参与类型检查、兼容判断、版本解析和一致性基线；兼容边界只由 `contract`、`version` 和 `compatibility` 构成；
- `contract` 必须满足与 §5、§2.2 相同的契约纪律：属性、插槽、事件、状态、公开样式位（§36.5）、平台变体和可访问性要求缺一不可；
- `contract` 必须声明布局能力（§7 的 sizing/display 能力子集）：布局编译器对宿主组件执行与其他节点相同的约束检查，未声明布局能力的宿主组件不能进入需要约束求解的位置；
- `dependencies` 声明运行期依赖的其他注册组件、宿主能力和资源（§4.2）；未声明的依赖在解析失败时按 §23.5 处理，禁止隐式发现；
- 注册清单声明 `version` 与 `compatibility`，编译器和运行时据此执行兼容检查（§23.4）；版本解析算法见 §23.4，必须确定性且跨实现一致。

### 23.3 注册时机与通道

注册分两个通道，两者执行同一 Schema 校验与兼容检查：

1. **构建期注册**：注册清单作为模型资源进入项目模型，编译器校验契约、引用和兼容范围，并为每个目标 Renderer 生成绑定产物；
2. **运行期宿主注入**：解释模式或宿主平台在启动时通过注册入口注入实现；入口的调用形态由实现装载器定义（例如 `register(manifest, implementation)`），核心协议只规定入口语义与校验要求。注入的契约摘要必须与注册清单一致；实现与声明不符（缺失事件、多出属性、类型不匹配）是运行错误，进入明确错误边界并上报诊断码，禁止静默降级。

运行期注入的组件只能使用注册清单中已声明的能力；注入不能修改项目模型（§13.2），只能把实现挂接到已登记的定义上。

注入通道有明确的信任边界：注入入口必须在 platform profile 中显式声明，采用入口允许清单或实现签名要求；注入主体、目标和结果进入审计（§32）。核心运行时不从任意项目目录动态加载或执行代码（§17 边界不变），未通过声明入口到达的实现按未注册处理，产生 `mf.reg` 诊断并进入错误边界，禁止静默接纳。

### 23.4 版本与兼容

- 注册组件按 §22.3 的兼容矩阵管理：契约变更必须声明版本，破坏性变更必须提供迁移器和诊断码（§41）；
- 同一组件 id 的多个版本可以并存，解析必须确定且跨实现一致：页面引用可以显式固定版本；未固定时，若恰有一个满足 `compatibility` 的版本则使用该版本；存在多个满足版本时必须由引用处显式消歧，未消歧的歧义是静态错误；解析结果随引用进入发布快照，不在运行期重解析；
- Renderer 升级时，编译器检查所有注册组件的兼容范围；不满足兼容的引用必须替换变体或拒绝构建。

### 23.5 Renderer 解析与编排边界

- 模型节点引用注册组件 id 时，Renderer 从注册表解析实现；解析失败时使用声明过的替代实现或进入错误边界，禁止静默缺失；
- 框架只通过公开契约编排注册组件：属性按引用传入，事件按绑定接出（§39）；框架不进入组件内部结构，注册组件也不得反向调用框架内部接口；
- 注册组件自动获得实例身份（`component_instance_id`），纳入 §24.7 的零侵入采集和 §22.3 的诊断关联链，无需业务代码埋点；
- 注册组件的平台变体按 §12 处理，能力不足时按声明降级。

### 23.6 废弃、注销与发现

- 废弃是显式声明：清单标注废弃版本、替代组件和移除版本；废弃组件继续通过校验但产生警告；
- 注销前必须通过引用检查（§4.3）；存在悬空引用的注销是静态错误；注销保留墓碑记录，历史发布快照不受影响；
- 注册表提供发现查询：列出已注册组件、契约摘要、可用版本和影响范围，供 AI、编辑器和编译器使用（§14 结构化命令 `register_component`、`register_resource`、`inspect_impact`）。

### 23.7 静态检查与门禁

- 未注册引用、契约缺失、类型不匹配、兼容范围不满足、注销后悬空引用均为静态错误；
- 注册组件必须提供契约一致性测试：实现行为与声明契约一致（§33 测试层）；
- 布局能力、依赖、插槽与生命周期声明的缺失或越界是静态错误（§23.2、§23.9、§23.10）；
- 上述检查并入 §18.1 与 §22.4 质量门禁。

### 23.8 上层产品接入工作流

标准接入工作流是"指导前端开发"的落点，所有步骤都有对应的结构化命令与校验：

```text
1. 创建项目与 manifest（§4.1）
2. 声明设计基线：Token、主题、样式片（§36）与 i18n 资源（§42）
3. 注册并组合资源：以 `register_resource`（§23.11）注册元组件、数据适配器、样式资产或宿主实现组件（§23.2），或以模型组合组件（§6）沉淀复用
4. 编排图层、页面、导航与绑定（§7-§9、§39）
5. 声明数据契约与外部适配器（§40）
6. 校验与影响分析：microflow-ui check / inspect / impact（§19）
7. 解释预览（§13.3）
8. 编译、发布快照与回滚演练（§16、§33）
9. 观测、实验与发布健康度跟踪（§24、§43）
10. 结论回流下一版修订（§43.3）
```

每一步的产物都是项目模型中的版本化资源；工作流可以在任意步骤回退到先前修订，不产生隐式状态。

### 23.9 结构与插槽传递

宿主实现组件与模型组合组件在同一节点树中混用时，结构边界由插槽协议定义：

- 引用宿主组件的节点可以为其已声明的插槽（§23.2 `contract.slots`）提供模型组合子树；插槽内容在引用处声明，实例化后属于该实例（§2.6）；
- 传递的是规范化节点描述，不是可变的对象图：运行时把插槽子树按当前 Renderer 的节点渲染协议交给宿主实现，由宿主实现在其契约声明的挂载点呈现；
- 宿主实现不得读取插槽子树的内部状态，不得反向修改子树或项目模型（§13.2），不得绕过契约向子树注入未声明的事件或样式；
- 插槽子树的事件按 §39 绑定解析，归属其声明对象；宿主实现不得代为分发未声明的事件；
- 为未声明插槽提供内容，或在未声明挂载点注入结构，都是静态或运行错误。

### 23.10 宿主实现生命周期

宿主实现与运行时之间的生命周期是契约，不是隐式约定：

- 契约可以声明生命周期钩子：创建、挂载、可见性变化、挂起、恢复、卸载和销毁；未声明的钩子运行时不调用，实现不得依赖未声明钩子被调用；
- 生命周期钩子属于 §24.7 的拦截边界：运行时在钩子边界产生事件并执行错误边界处理；宿主实现不得在钩子内直接调用采集，也不得把钩子用作绕过错误边界的通道；
- 挂起与恢复遵循 §22.1：不依赖内存对象存活，恢复时按 Recovery Contract（§18.4）重新校验；销毁语义必须确定，避免实例泄漏；
- 钩子声明纳入 §23.7 静态检查与 §18.2 运行验证。

### 23.11 统一资源注册协议

本章协议是**统一资源注册协议**：组件（§23.2）是第一大已注册类别；元组件、数据适配器、布局能力、样式资产、本地函数（kind: function，契约见 §10.1）与宿主能力（kind: capability，契约见 §17.1）同样作为注册资源进入框架——业务层开发，注册后经 §2.7 配置构造进入编排。公共纪律对所有类别一致，各类别只声明差异面（§23.12）：

- **版本化注册清单**：`id`、`kind`、`revision`、`description`、`dependencies`、`capabilities`、`tests`、`version`、`compatibility`、`deprecation`（字段纪律同 §4.2、§23.2）；
- **双注册通道**：构建期注册与运行期宿主注入，含注入入口允许清单与签名要求、注入一致性校验和明确错误边界（§23.3）；该纪律对全部带实现的类别适用；
- **确定性版本解析**：多版本并存、显式固定与消歧、解析结果进入发布快照（§23.4）；
- **发现与影响分析**：注册发现、引用影响查询（§23.6、§4.3、§14 `register_resource`、`inspect_impact`）；
- **废弃、注销与墓碑**：§23.6 规则对全部类别适用；
- **静态检查与门禁**：§23.7 并入 §18.1、§22.4；
- **未注册引用是静态错误**（§2.7）：对全部 kind 生效。

### 23.12 注册资源类别差异面

| kind | 清单差异面 | 特殊规则 |
|---|---|---|
| component | §23.2 原文契约（props/slots/events/states/layout/exposed_styles/platform_variants/accessibility） | 结构传递与宿主生命周期见 §23.9、§23.10 |
| primitive | 以 §5 全量契约作为清单校验标准；必须声明样式面（§36.5）、布局能力（§7 sizing/display 子集）和可访问性要求；须同时提供预览实现与运行实现（§17） | 宿主实现按 §23.3 注入并执行注入一致性校验；不满足 §5 契约纪律不得注册 |
| adapter | 差异面为 input/output/errors/idempotency/trace 摘要（§40.2）；不得携带 UI 类字段（slots、exposed_styles、platform_variants），出现是静态错误；通过登记的 Data Contract id 关联契约（§40） | 来源类别必须由宿主适配器注册声明（§40.2）；关联的契约未登记是静态错误 |
| layout | 必须同时交付：与 §7.3 同构的形式化求解规则描述、布局编译器检查规则、各目标 Renderer 映射实现和降级策略 | 缺检查规则的布局能力不得注册、不参与约束求解（§7）；未注册新布局需求只能以组件行为实现并在 platform profile 声明 |
| style-asset | token-set / theme / style 资源按 §36 Schema 校验 | 声明式资源，不携带实现、不适用注入通道；继承版本化、影响查询与发布摘要规则（§36.8） |
| function | 差异面为 Action Contract（§10.1）：input/output/errors/timeout_ms/idempotency/cancellation/unknown_result | 只能由 Local Function 代码实现；双注册通道适用（§23.3）；实现与契约不一致是静态或运行错误（§23.7）；未注册函数引用是静态错误（§37.2） |
| capability | 差异面为 Capability Contract（§17.1）：states/permissions/availability/degradation | 双注册通道适用（§23.3）；非成功状态必须有降级声明，缺失不得注册；状态可判定性遵循 §22.1 |

差异面字段不属于可选声明：注册清单按 kind 校验，清单包含差异面之外未登记的 kind 专属字段时产生 `mf.reg.unknown-field` 诊断（§41）。

## 24. 观测、运营分析与多版本实验

### 24.1 事件分类

前端事件分为四类：

1. **Diagnostic Log**：用于错误、异常、状态冲突、资源失败和宿主能力失败；
2. **Operational Event**：用于页面访问、功能使用、流程完成、漏斗和业务运营分析；
3. **Performance Sample**：用于启动、导航、交互、网络、资源和渲染性能；
4. **Business Fact**：需要可靠确认的业务事实，例如订单提交成功或文件写入完成。

四类事件必须有不同的可靠性、重试、隐私、保留和查询策略。普通日志或运营事件丢失不能阻断用户流程；Business Fact 必须使用明确的提交确认和去重身份，不能用普通日志代替。

用户主动反馈（评分、意见、报障）属于 Operational Event 的标准事件族（§24.2）；报障工单可携带的诊断引用身份（`trace_id`、`page_instance_id`）由 §29 定义输出规格。框架不内置工单或反馈平台，只保证这些身份字段在事件与 Debug 快照中可达、可关联。

### 24.2 Telemetry Contract

事件定义至少包含：

```json
{
  "event_id": {"type": "string", "required": true, "note": "uuid，幂等去重身份"},
  "event_name": {"type": "string", "required": true, "note": "已登记事件类（§24.1）"},
  "schema_version": {"type": "string", "required": true},
  "occurred_at": {"type": "string", "required": true, "note": "ISO-8601 UTC，客户端观察时间"},
  "release_id": {"type": "string", "required": true},
  "renderer_version": {"type": "string", "required": true},
  "environment": {"type": "enum", "values": ["dev", "preview", "production"], "required": true},
  "session_id": {"type": "string", "required": true, "note": "不透明会话身份"},
  "page_instance_id": {"type": "string", "required": true},
  "layer_instance_id": {"type": "string"},
  "route": {"type": "string", "required": true},
  "component_instance_id": {"type": "string"},
  "interaction_id": {"type": "string"},
  "action_request_id": {"type": "string"},
  "trace_id": {"type": "string", "required": true},
  "experiment_assignments": {"type": "array", "items": {"$ref": "assignment_ref"}},
  "identity": {"type": "object", "note": "身份字段，见下方身份规范"},
  "payload": {"type": "object", "note": "按事件类 Payload Schema 校验"},
  "privacy_class": {"type": "enum", "values": ["operational", "sensitive", "restricted"], "required": true},
  "sampling_policy": {"type": "object", "required": true},
  "client_sent_at": {"type": "string", "note": "与 occurred_at 区分，供时间失真诊断"}
}
```

事件 Schema 必须限制字段、类型、大小、嵌套深度和高基数字段。密码、令牌、原始文件内容、完整表单内容和未经授权的个人信息不得进入事件。需要分析的用户标识必须使用受控的匿名化或哈希身份，并声明保留期限和访问范围。

采集器采用有界内存队列和持久化可选队列。事件上报支持批量、压缩、退避、取消和断网缓存；队列达到预算后按事件优先级丢弃，并记录丢弃计数。日志上报故障不能导致页面主线程阻塞或业务动作失败。

每个事件必须携带 `trace_id`、`release_id` 和页面实例关联信息，使问题能够从用户动作追踪到交互、状态修订、宿主调用和错误边界。诊断数据要区分客户端观察时间和服务端接收时间，不能用接收时间替代事件发生时间。

身份字段是信封的一部分，按 §4.4 分开建模、按 §32 最小化：

```text
identity:
  user_ref          受控哈希用户身份（可空；由身份服务颁发，禁止原始账号、手机号、邮箱）
  device_ref        受控哈希设备身份（可空，禁止原始设备序列号）
  exp_subject_ref   实验分流身份（仅实验与变体配置事件携带；与 user_ref 独立颁发）
  identity_version  身份方案版本（哈希算法与盐策略变更时递增）
```

规则：

- `identity.*` 全部为受控哈希或随机不透明标识，颁发、轮换与访问范围按 §4.4、§32 声明；任何事件不得携带原始凭据或直接标识；
- 事件信封是机器可校验 Schema：未登记字段、类型不匹配、required 缺失和 payload 超深/超大都是校验错误，进入 §30.1 的丢弃原因与数据质量指标（§24.3）。

以下**标准事件族**必须按统一字段口径登记，作为业务层做运营数据加工的跨实现可比输入（框架只定义字段与校验，不内置任何外部对接）：

- `ops.content.exposed`（内容位曝光）：`content_slot_id`、`content_asset_id`、`content_config_version`、`locale`；事件不得携带完整内容载荷（内容本体走 §2.7 内容资产配置通道）；
- `ops.feedback.submitted` / `ops.feedback.resolved`（用户反馈）：`feedback_type`、`feedback_target`（页面/组件 id）、关联 `trace_id`（可空）；
- `ops.campaign.attributed`（活动归因，非实验）：`campaign_id`、`source`、`attribution_time`；本族字段与 `experiment_assignments` 互斥，同一事件同时携带两种归属是校验错误。
- `ops.page.viewed`（页面访问）：`page_definition_id`（页面定义 id，§4.2）、`entry`（push / replace / modal / tab / back / deeplink / external，对应 §9 导航边类型）、`referrer_route`（可空）、`locale`；事件只能在页面实例真实创建且可见后产生，不得在导航意图阶段计数（与 §24.4 曝光语义一致）；
- `ops.page.left`（页面离开）：`page_definition_id`、`stay_ms`、`exit`（导航边类型或 `app-background`）；与 `ops.page.viewed` 通过同一 `page_instance_id` 关联，共同构成页面使用时长口径；
- `ops.feature.used`（功能使用）：`feature_ref`（项目模型中被触发的交互 id 或动作 id，§4.2）、`context_route`；同一绑定的重复触发按 `action_request_id` 区分，去重口径由消费方声明。

标准事件族附加规则：

- 标准事件族全部由运行时在拦截边界零埋点产生（§24.7）：页面族挂接导航拦截，功能使用族挂接动作执行拦截；业务代码出现任何标准族的手工上报是静态错误；
- 漏斗是版本化分析资源（§30.2）：步骤必须引用已登记的事件类（`ops.page.viewed`、`ops.feature.used` 或业务自定义已登记事件），漏斗资源显式声明步骤间窗口、去重身份与终止步骤；标准族只提供跨实现可比的事件输入，不内置漏斗语义；
- 留存以同一 `identity.user_ref`（受控哈希身份，本章前文）的跨日回访为口径，日界与口径的时区由分析资源显式声明，禁止实现私定；
- 进程终止导致 `left` 缺失时，事件面不补发伪造的 `left`，由分析侧声明估算口径并标记 `estimated: true`；
- 标准族事件同样受事件信封 Schema、隐私分类与采样策略约束；`feature_ref`、`page_definition_id` 引用不存在或未登记的资源是校验错误。

### 24.3 运营数据和问题分析

框架定义标准事件查询和导出协议，并据此向上层提供数据支持能力（事件 Schema 注册表、标准投影与基础聚合、数据质量指标）；框架不把具体分析平台写入核心依赖，也不内置任何外部平台对接。指标计算、显著性分析和实验结论由基于框架实现的业务层完成。事件投影至少支持：

- 页面和功能使用量（标准族 `ops.page.*`、`ops.feature.used` 为输入，§24.2）；
- 漏斗和转化率（漏斗为版本化分析资源，步骤引用已登记标准事件，§24.2、§30.2）；
- 错误率、崩溃率和错误聚类；
- 版本、平台、设备和网络条件分布；
- 性能 P50、P95、P99；
- 发布健康度标准投影（§43.1）；
- 实验组、配置版本和分流来源维度的数据筛选；
- 事件 Schema 版本和采集丢失率。

事件查询必须按时间、版本、平台、实验、页面和错误类型建立有界过滤，禁止默认返回无限明细。原始事件、聚合结果和诊断索引分别设置保留期限、容量预算和权限。

### 24.4 多版本配置和外部 AB 实验控制

框架支持多版本配置的读取、Schema 校验、兼容性检查、运行时冻结和结果上报。实验分流由外部实验平台、配置中心或运营系统完成，外部控制方至少提供：

```text
experiment_id
config_version
target_scope
assignment_id
assignment_source
variants
exposure_event
start_at
end_at
compatibility
```

框架不实现 `allocation_rules`、样本选择、随机算法、互斥实验决策或指标计算。外部控制方负责根据稳定身份完成分流，并返回不可变的 `assignment_id`、实验组和配置版本。框架必须校验分流结果与目标平台、Schema、发布版本和有效期兼容，然后将分流结果写入运行上下文。曝光只有在目标页面或功能真实可见且可操作时才确认，不能在配置加载时提前计数。

外部配置和实验上下文必须经过 Schema、目标平台能力、默认变体、结束时间和兼容性检查。缺失配置、配置过期、版本不兼容或外部控制方不可用时，框架使用发布快照中声明的默认配置和默认变体，并记录降级原因。实验停用由外部控制方发布新状态或停用配置；框架负责接收、校验和应用，不自行作出实验决策。已确认的历史曝光归属不能改变。

实验不得绕过权限、数据校验、错误处理和安全边界。外部控制方只能选择框架已经声明并允许的属性、布局、交互顺序或策略；框架不得通过配置执行未注册代码、启用未声明能力或写入未验证的数据。允许改写的资源面必须登记于 §2.9 受控交叉清单；未登记的改写面在静态校验中拒绝。

实验与灰度的版本路由建立在版本签名（§4.5）之上：客户端请求携带自身版本标识，外部控制方按版本标识返回对应的 `config_version` 与实验分配，框架校验后冻结应用。框架在此过程中只提供两类输出：作为分析取数依据的版本化数据（§24.3）和作为路由与兼容判断依据的版本身份。分流、选择、启停和实验结论始终由上层完成；框架不保存、不实现任何实验策略。

### 24.5 实验与发布、恢复的关系

运行实例固定实验配置摘要和分流结果。页面恢复时继续使用原实验归属，除非实验协议明确允许重新分流；发布回滚必须同时校验实验配置版本和 Renderer 兼容性。实验配置变化产生新修订，新页面实例使用新版本，已运行实例不被静默改写。

实验结果必须同时记录应用版本、Renderer 版本、平台、数据 Schema 版本、外部 `assignment_id`、分流来源和实验配置版本，避免把版本变化误判为实验效果。指标计算、实验比较和实验结论由外部控制方完成。实验结束后，外部控制方负责保留实验墓碑和历史曝光索引；框架继续在事件中保留来源摘要，防止旧事件被错误归入新实验。

### 24.6 观测和实验质量门禁

- 事件 Schema、隐私分类、采样和保留策略通过检查；
- 普通采集故障不阻断核心页面和业务动作；
- Business Fact 支持去重、确认和未知结果查询；
- 事件能够关联到 release、页面实例、交互、状态修订和错误边界；
- 外部提供的 assignment 在运行实例内稳定且可追踪；
- 曝光事件只在真实曝光后产生；
- 缺失、过期和不兼容配置使用默认变体并记录原因；
- 外部停用状态能停止新曝光且不改写历史归属；
- 事件包含应用、Renderer、平台、assignment 和配置版本，供外部平台拆分指标；
- 采集队列的大小、延迟、丢弃和重试均有性能预算和诊断；
- 标准事件族（§24.2）由拦截边界零埋点产生，字段口径校验通过，投影（§24.3）与漏斗资源依赖的事件类均已登记；
- 业务逻辑与采集通道分离（§24.7），动作链和适配器实现中不存在直接采集调用，声明式注记全部通过引用与策略检查。

### 24.7 零侵入采集与声明式注记

采集必须与业务逻辑分离，通过声明决定"在哪个触点、上报什么、按什么策略"，通过框架机制决定"由谁产生、如何上报"：

- **业务逻辑零侵入**：动作链、组件内部实现、页面生命周期和适配器实现不得直接调用采集、上报或日志接口；普通错误处理不得依赖日志上报作为分支手段；
- **运行时是唯一发射点**：运行时以代理、拦截器或装饰器的组合方式包裹页面生命周期、导航、事件分发、动作执行、宿主能力调用和外部适配器调用，在拦截边界产生事件；实现方式由各 Renderer 自行选择，拦截边界集合由本章定义，不留绕行通道，外部适配器调用也必须经运行时代理执行；
- **声明式注记决定定向内容**：页面、交互绑定（§39）、外部适配器和宿主能力在模型中通过注记声明关联的事件引用（§24.1 已登记的事件类）与采样策略；注记只携带声明，不携带可执行逻辑；


```json
{
  "id": "adapter-order-create",
  "kind": "external-adapter",
  "data_contract": "order-create-v2",
  "telemetry": {
    "events": {
      "entry": "ops.checkout.submitted",
      "success": "ops.checkout.confirmed",
      "failure": "diag.checkout.adapter_failed"
    },
    "privacy_class": "operational",
    "sampling_policy": {"kind": "ratio", "value": 0.1}
  }
}
```

- **注记仍走完整采集管道**：注记声明的事件同样经过 §24.2 的事件 Schema 校验、身份字段注入、队列、预算和隐私检查，不因声明式来源绕过任何校验；
- **注记静态校验**：引用的事件必须已登记，采样与隐私策略必须通过检查；同一触点上多条注记必须有显式排序，覆盖歧义是静态错误；
- **唯一显式例外是 Business Fact**：可靠业务事实通过运行时声明的提交入口完成提交确认，调用方必须声明去重身份与确认语义（§24.1）；除该入口外，任何代码路径不得直接写入采集队列；
- **Debug 采集同理**：§29 的运行上下文读取、组件树快照和回放数据也由运行时在拦截边界产生，不要求业务代码埋点。

### 24.8 前后端追踪关联

外部适配器调用可能触达由外部执行侧（例如业务流程执行框架）承载的执行过程。为使缺陷分析和业务问题定位能跨越前端运行时与外部执行侧，追踪上下文传播是一等协议，而不是适配器实现的私有约定：

- Data Contract（§40）声明追踪传播：是否传播、方向（出站、回传或双向）和载体字段；声明传播的适配器调用由运行时注入追踪上下文，业务代码与适配器实现不得自行构造或改写追踪身份；
- 出站上下文至少包含 `trace_id`、`release_id`、页面实例标识和 `action_request_id`；外部执行侧返回的运行引用按不透明标识记录进诊断、事件（§24.2）和 Debug 快照（§29），框架不解释其内部结构，也不依赖其存在；
- Business Fact（§24.1 第 4 类）的确认结果必须关联外部执行侧运行引用；没有可关联运行引用的确认只能进入 `unknown` 语义（§22.1），不能当作成功；
- 追踪身份是标识不是凭据（§32）：上下文不得携带令牌、个人信息或可用于鉴权的内容；跨栈关联字段纳入事件 Schema 与隐私分类检查（§24.2）；
- 未声明传播的适配器调用不产生跨栈关联；声明了传播但外部执行侧未返回运行引用时，事件记录传播缺失原因，不视为调用失败；
- 跨栈追踪的诊断码使用 `mf.tele` 命名空间（§41）。

## 25. 观测与实验设计结论

日志、运营事件、性能样本、可靠业务事实和实验曝光都通过版本化契约进入前端运行时。框架负责数据和多版本配置的接收、校验、冻结、应用和上报；外部系统负责实验分流、运营控制、指标计算、实验启停和结论。采集系统不能阻断核心流程，可靠业务事实必须具备确认和去重语义，实验上下文必须可追踪且不改变历史归属。

## 26. 修订后的总设计结论

MicroFlow Frontend 仍以“元组件 → 组件 → 图层 → 页面 → 产品 → 目标平台产物”为核心抽象，但可发布的产品模型还必须同时携带数据、动作、能力、恢复、Renderer 和性能契约。

项目模型是事实来源，规范化 IR 是编译和运行的共同输入，发布快照是可复现和回滚的边界，Renderer 和 Host 只能通过已声明的契约扩展平台能力。上层业务组件通过组件注册契约（§23）进入编排，数据访问通过 Data Contract（§40）声明，多语言产品通过 i18n 资源模型（§42）表达，诊断通过统一注册表（§41）跨实现可比，前端与外部执行侧的问题定位通过追踪关联协议（§24.8）贯通。高可用、高性能和高可维护性必须由静态检查、运行验证、性能基准、故障演练和版本兼容共同证明，不能由模型分层本身推定。

## 27. 可实施能力边界

前面的模型和契约是框架的核心，但不能把“已定义”当成“已提供”。每项能力必须同时标记设计状态、运行时接口、宿主实现和验证证据。上层只能依赖已经注册并通过兼容检查的能力。

```text
Project Model / IR
  ├── Unified Resource Registration Contract（§23，差异面见 §23.11、§23.12）
  ├── Web Runtime Contract
  ├── Data Contract（§40）
  ├── Debug Contract
  ├── Telemetry Ingest Contract
  ├── Telemetry Query Contract
  ├── Cross-Stack Trace Contract（§24.8）
  ├── Subscription Contract（可选，§43.2）
  ├── Experiment / Variant Config Contract（§31、§31.1）
  ├── Business Finding Backflow Contract（§43.3）
  ├── Security and Privacy Contract
  ├── i18n Contract（§42）
  ├── Diagnostic Code Registry（§41）
  ├── Test and Verification Contract
  └── Build and Deployment Contract
```

**责任承载矩阵**：上表各契约的实现归属如下；框架交付物为「协议」或「协议 + 参考实现」，其余实现由承载方交付：

| 契约 | 框架交付 | 实现承载方 |
|---|---|---|
| 统一资源注册（§23） | 协议 + 静态检查 | 框架核心；注入通道按 §23.3 |
| Web Runtime Contract（§28） | 协议 | Renderer 实现 |
| Data Contract（§40） | 协议 | 业务层实现适配器 |
| Debug Contract（§29） | 协议 + Renderer 侧实现 | Renderer 落地；远程诊断服务由业务层承载 |
| Telemetry Ingest（§30.1） | 协议 + 客户端 SDK 参考实现 | Renderer 落地，接收端由业务层承载 |
| Query / Export（§30.2） | 协议（含本地参考实现可选） | 业务层承载服务实现 |
| Subscription（§43.2，可选） | 仅协议 | 业务层承载 |
| Experiment / Variant Config（§31、§31.1） | 协议 | 业务层通过 Provider 承载 |
| Security and Privacy（§32） | 协议与发布门禁 | 全体承载方共同满足 |
| i18n（§42） | 协议 | 框架核心校验，Renderer 映射 |
| Diagnostic Registry（§41） | 框架级注册表资源 | 框架核心维护 |
| Test / Build / Deploy（§33） | 协议 | 各承载方出具运行证据 |

核心框架只定义协议和生命周期，不内置具体日志平台、实验平台、数据库、身份服务或云厂商 SDK，也不与任何外部平台对接。每个协议都必须提供版本、Schema、稳定错误码、兼容范围、能力声明、降级策略和契约测试。未实现或未验证的协议不得在发布清单中标记为生产可用。各契约的最小 Schema 索引见 §18.4；只有文字纪律而无最小 Schema 的契约视为未定义，不得进入发布清单。

## 28. Web Runtime Contract

Web Renderer 必须把浏览器行为落实为可验证的运行时契约，而不是只提供组件渲染函数。契约至少包括：

- 浏览器支持矩阵、资源基路径和生产路由重写要求；
- `push`、`replace`、`back`、深链接、刷新、未知路由和权限拒绝行为；
- 页面实例创建、激活、挂起、恢复和销毁；
- SSR、静态生成或纯客户端模式的选择，以及序列化和 Hydration 边界；
- 浏览器专用 API 的能力检测、权限拒绝、暂不可用和不支持状态；
- 请求取消、超时、重试、缓存失效和用户切换时的数据隔离；
- 错误边界、资源失败、空状态、加载状态和可恢复入口；
- 文档标题、焦点入口、键盘导航、语义角色和可访问性失败诊断；
- Service Worker、离线缓存和更新接管策略（如果目标产品声明支持离线）；
- Web Vitals、资源体积、首屏和交互性能预算。

Renderer 必须输出确定性的运行时标识，包括 `page_instance_id`、`component_instance_id` 和 `render_revision`。解释模式和编译模式必须使用同一契约，并对导航、状态、错误、取消和可访问性行为执行一致性测试。

## 29. Debug Contract

Debug 能力分为本地开发、预览环境和生产受控诊断三个等级。所有等级都必须通过权限、环境和数据分类检查。

Debug API 至少支持：

- 按 `release_id`、页面实例和交互实例读取运行上下文；
- 读取组件树、图层树、页面状态和状态修订；
- 订阅导航、动作、状态变更、网络和宿主能力事件；
- 在已声明的检查点暂停、继续和读取快照；
- 查询请求的取消、重试、未知结果和最终确认状态；
- 使用 Source Map 将编译错误映射回源资源和模型对象；
- 对错误进行聚类、去重、关联和首次出现版本定位；
- 采集可选的用户流程回放数据，但必须遵守字段屏蔽、同意和保留策略；
- 远程诊断授权、过期、审计和强制撤销。

Debug 快照与发布快照、恢复快照是不同对象。快照必须限制大小、深度、保存时间和敏感字段；生产环境默认不允许任意暂停，也不能长期占用业务临界资源。暂停、继续、读取和导出都必须具有稳定请求 ID、权限主体、审计记录和幂等语义。

Debug 会话与快照的最小 Schema：

```json
{
  "debug_session": {
    "id": "dbg-...",
    "principal": "审计主体（§32）",
    "level": "local | preview | production-controlled",
    "scope": {"release_id": "...", "page_instance_id": "..."},
    "grants": ["read-context", "subscribe", "checkpoint-pause", "export"],
    "expires_at": "ISO-8601",
    "audit_ref": "..."
  },
  "snapshot": {
    "snapshot_id": "...",
    "size_budget": "字节预算",
    "depth_max": 8,
    "retention_s": 3600,
    "masked_fields": "按 privacy_class 屏蔽（§24.2、§40.5）"
  }
}
```

规则：`grants` 逐项授权，未授予的操作拒绝并审计；生产受控诊断的会话必须生效过期与强制撤销（本章前文纪律）。

## 30. Telemetry Ingest 与 Query Contract

### 30.1 接收契约

Telemetry SDK 属于框架侧客户端件（由 Renderer 落地）；接收端是数据交付的服务侧，由业务层按本协议承载实现。两者必须共同实现：

- 批量、压缩、退避、取消、断网缓存和有界队列；
- `event_id` 去重、顺序信息、客户端发生时间和服务端接收时间；
- Schema、大小、深度、高基数字段和隐私分类校验；
- 采样决策、丢弃原因、队列延迟和重试次数；
- 普通日志、运营事件、性能样本和 Business Fact 的不同可靠性等级；
- Business Fact 的提交确认、消费凭据、重复消费和未知结果查询；
- 采集故障不阻断核心页面，除非调用方声明该事件是可靠业务事实。

### 30.2 查询与导出契约

框架必须定义版本化查询和导出协议，实现形态由承载方交付（本地参考实现或业务层服务），至少支持：

```text
query_events(filter, group_by, measures, time_range, page_token)
get_event_schema(event_name, schema_version)
get_trace(trace_id)
export_events(filter, format, retention_scope, cursor)
get_data_quality(scope, time_range)
```

查询过滤器必须限制时间范围、版本、平台、页面、实验、错误类型和事件类型，禁止默认返回无限明细。响应必须包含 Schema 版本、数据截止时间、采样比例、丢失率、分页令牌和一致性级别。原始事件、聚合结果、诊断索引和回放数据分别配置保留期限、容量预算、访问角色和删除策略。

导出支持游标式增量同步：`cursor` 标识上次同步位点，响应携带缺口区间声明（缺失区间、原因与补齐水位）；迟到数据进入后续增量，禁止静默改写已交付数据。该语义与数据质量指标（丢失率、丢弃计数）共同构成业务层数据管道做缺口补偿的协议依据。

指标口径、漏斗步骤、留存窗口和聚合维度必须作为版本化分析资源登记。框架提供事件投影和基础聚合能力；统计显著性、实验结论和业务解释由外部分析或实验系统完成。漏斗步骤必须引用已登记的标准事件（§24.2）；留存以同一 `identity.user_ref` 的跨日回访为口径，时区与日界由分析资源声明，禁止实现私定。订阅式推送、实时告警和流式分析不属于本章查询契约，由 §43.2 的 Subscription Contract 承接。

## 31. Experiment Provider Contract

外部实验系统通过 Provider 接入，不能直接修改运行时内部状态。Provider 至少提供：

```text
resolve_assignment(experiment_id, subject_scope, release_context)
get_experiment_config(experiment_id, assignment_id)
record_exposure(exposure_event)
get_experiment_status(experiment_id)
```

返回值必须包含 `assignment_id`、实验组、配置版本、分流来源、有效期、目标平台、兼容范围和停用状态。框架负责 Schema、权限、平台能力、发布版本和有效期校验，并将有效结果冻结到运行实例。

Experiment Contract 的最小 Schema：

```json
{
  "experiment_id": "checkout-cta-v2",
  "config_version": "3",
  "target_scope": {"platforms": ["web"], "release_compatibility": ">=1.0 <2.0"},
  "variants": [{"id": "control", "is_default": true}, {"id": "treatment"}],
  "assignment": {
    "assignment_id": "opaque-stable-id",
    "assignment_source": "external-platform",
    "variant": "treatment",
    "frozen_at": "ISO-8601"
  },
  "exposure_event": "exp.checkout-cta-v2.exposed",
  "start_at": "ISO-8601",
  "end_at": "ISO-8601",
  "compatibility": {"syntax_version": "1.0", "config_schema_version": "1.0", "renderer": ">=1.0 <2.0"},
  "stop_state": {"stopped": false, "reason": null}
}
```

规则：

- `assignment.variant` 必须命中 `variants`，未命中是校验错误；缺省变体即 `is_default: true` 的条目（§24.4 降级规则）；
- `stop_state.stopped` 为 true 时只停止新曝光，不改写已确认的历史归属（§24.5）；
- 非实验的运营变体配置（§31.1）复用本 Schema 除 `assignment` 与 `exposure_event` 外的字段，不得携带 `assignment_id`。

曝光事件只能由页面或功能在真实可见且可操作后产生。Provider 不得通过配置启用未注册代码、未声明宿主能力、绕过权限或修改历史曝光。Provider 不可用、结果缺失、配置过期或版本不兼容时，框架使用发布快照中声明的默认变体并记录降级原因。

实验配置刷新默认只影响新建页面实例。页面恢复继续使用原分流归属，除非实验协议明确允许重新分流。停用只能停止新曝光，不能改写已确认的历史归属。

### 31.1 面向运营的变体配置（非实验）

实验契约的校验、冻结、恢复归属、停用与回滚校验规则同样适用于**非实验的运营变体配置**（面向人群的公告弹窗、活动资格、频控开关）：人群与规则计算由业务层完成，框架只校验目标平台、Schema、有效期与兼容范围，冻结应用并上报。该类配置不属于实验：不产生 `assignment_id`，不携带实验归属字段，可与 §24.2 的活动归因族并存；伪装成实验分配进入实验数据面是校验错误。

## 32. Security and Privacy Contract

安全和隐私必须成为发布门禁，而不是 Telemetry 的附加说明。契约至少包括：

- 身份认证、会话续期、权限拒绝和登出后的数据清理；
- CSP、Trusted Types、XSS 防护、第三方脚本清单和资源完整性；
- 浏览器端配置与服务端密钥的隔离，禁止把凭据写入模型、日志、快照或事件；
- 用户、设备、会话和实验身份的分离及最小化使用；
- 采集同意、敏感字段分类、字段屏蔽、哈希化、保留和删除；
- Debug、查询、导出、实验配置和远程控制的主体、角色、作用域和审计；
- 跨租户、跨项目、跨发布和跨实验的数据隔离；
- 第三方依赖、扩展和 Host Capability 的签名、版本锁定和撤销；
- 模型修订、发布、回滚、配置下发、注册清单变更和运行期注入的操作主体、角色、授权与审计：发布快照与审计记录绑定操作主体和授权依据（§16、§23.3）。

安全检查失败时不得通过默认配置或降级路径绕过。发布清单必须记录安全策略摘要、依赖摘要、隐私版本和审计策略版本。

安全策略摘要的最小 Schema（进入发布清单，§16）：

```json
{
  "security_policy_summary": {
    "csp": "策略摘要",
    "trusted_types": true,
    "third_party_scripts": [{"origin": "...", "integrity": "..."}],
    "dependency_digests": "...",
    "privacy_version": "...",
    "audit_policy_version": "...",
    "consent": {"telemetry": "required", "replay": "required"}
  }
}
```

## 33. 测试、构建与部署契约

每个 Renderer 和 Host 必须提供以下测试层：

- Schema、规范化、迁移、引用和静态诊断测试；
- 组件、页面、导航、状态、动作和错误边界测试；
- 浏览器端路由、深链接、刷新、恢复和权限场景测试；
- 端到端业务流程测试和关键页面视觉回归测试；
- 可访问性自动化测试及键盘、焦点和屏幕阅读器抽查；
- 解释模式与编译模式的一致性测试；
- 资源失败、离线、超时、重复提交、未知结果和版本回滚故障注入；
- Bundle、Web Vitals、内存、启动、导航和交互性能预算测试。

构建系统必须生成可追踪的产物清单、Source Map、依赖摘要、路由清单、Telemetry/Experiment Schema 清单和安全策略摘要。部署系统必须验证资源完整性、基路径、重写规则、配置兼容性、缓存策略和回滚条件。开发服务器成功不能替代生产预览或目标浏览器验证。

## 34. 优化后的实施顺序

在原有六个阶段基础上，实施顺序调整为：

1. 先完成 Project Model、IR、Schema、引用索引和最小 Data（§40）/Action/Recovery/Telemetry 契约，以及组件注册契约（§23）、诊断码注册表（§41）和 i18n 资源模型（§42）；
2. 完成 Web Runtime Contract 和一个可运行的 Web Renderer，先覆盖客户端渲染、路由、状态、错误和可访问性，并全量执行端到端一致性基线（§44.3）；
3. 同步完成 Telemetry SDK（Renderer 侧）、接收端服务接口（业务层按 §30.1 承载）、查询与导出协议（§30.2）和隐私校验，避免先产生不可查询的事件；
4. 完成 Debug Contract 的本地和预览能力，再接入受控生产诊断；
5. 以 Experiment Provider 接口接入外部分流和配置系统，验证曝光、冻结、恢复、停用和回滚；
6. 建立安全门禁、端到端测试、视觉回归、性能基准和生产预览；
7. 最后扩展编译器、移动/桌面 Renderer，并开放上层工具接入协议的完整验证（可视化编辑器本身由上层或第三方基于该协议建设）。

已存在的客户端 Renderer 实现（例如本仓库的 Flutter 实现）遵循同一套项目模型与契约，不因上述顺序描述而失去合规资格；其实际能力按 §38.2 分级如实声明，并以 §44.3 基线作为强制验收，未通过对应基线前不得声明更高分级或生产能力。顺序描述的是首个完整 Renderer 的建议路径，不是对既有实现的否定。

每个阶段的完成条件必须同时包含：协议实现、契约测试、故障注入、性能数据、隐私检查和实际运行证据。只有设计文件或内存替身通过，不能标记为生产能力。

## 35. 优化后的结论

MicroFlow Frontend 可以作为现代前端平台的底层模型和能力协议，但完整能力来自以下闭环：

```text
模型 → Schema/IR → Renderer/Host → 运行实例
                     ↓
          Debug / Telemetry / Experiment
                     ↓
        Query / Analysis / Release / Recovery
```

上层业务可以通过稳定的组件、数据、动作、能力、观测和实验接口构建产品；下层必须提供可查询、可审计、可恢复、可测试和可回滚的运行证据。当前仓库仍处于后端和本地运行时的实施阶段，Web Renderer、查询面、完整 Debug 和生产安全门禁完成前，不应宣称已经支持全部现代前端能力。

## 36. 样式与主题模型

### 36.1 关注点拆分

样式是与结构、布局、逻辑并列的独立关注点，必须单独建模、单独版本化、单独验证：

```text
结构（§6）：有什么、什么顺序、在谁的内容槽里
布局（§7）：占位、排列和空间
样式（本章）：外观呈现
逻辑（§10、§37、§39）：事件、状态和副作用
```

本章拆分的是模型内部关注点；模型、实现、运行值与配置之间的平面边界由 §2.9 三平面分离约束，两者正交，同一违例按更严格者判定。

边界规则：

- 结构树是纯结构描述，节点只能通过 `style` 引用接入样式，不内联颜色、字体、阴影等外观属性；
- 布局约束不承载外观；外观属性不承载布局；
- 逻辑不直接产生样式；运行期状态对样式的影响只能通过样式条件的 `state` 选择器表达；
- 跨关注点违例（结构树内联样式、样式片内嵌布局、动作链改写样式定义）都是静态错误。

属性归属歧义（例如边框宽度、最小尺寸）不作解释性判断：由对应元组件契约（§5）逐个声明归属，未声明归属的属性是静态错误。

### 36.2 主题令牌

Token 是命名的、平台无关的语义值。Token 集是项目模型中的版本化资源（§4.2），拥有稳定 `id`、`schema_version`、`revision` 和标签：

```json
{
  "id": "tokens-light",
  "kind": "token-set",
  "schema_version": "1.0",
  "tokens": {
    "color.base.blue.500": {"type": "color", "value": "#2563eb"},
    "color.action": {"type": "color", "ref": "color.base.blue.500"},
    "color.text.on-action": {"type": "color", "value": "#ffffff"},
    "color.bg.surface": {"type": "color", "value": "#ffffff"},
    "color.text.primary": {"type": "color", "value": "#111827"},
    "space.4": {"type": "dimension", "value": "16px"},
    "radius.md": {"type": "dimension", "value": "8px"},
    "font.body": {"type": "typography", "value": {"weight": 400, "scale": "md"}},
    "duration.fast": {"type": "motion", "value": "150ms"},
    "opacity.disabled": {"type": "opacity", "value": 0.4}
  }
}
```

规则：

- Token 类型固定为 `color`、`dimension`、`typography`、`effect`、`motion`、`opacity`、`breakpoint`；未声明类型和类型不匹配都是错误；
- Token 的值只能是字面量或同类型 `ref`；`ref` 形成有向图，循环引用是错误，未解析引用是错误；
- 语义 Token（如 `color.action`）承载业务语义，基础 Token（如 `color.base.*`）承载原始值；组件、图层、页面和样式片必须引用语义 Token，允许直接引用基础 Token 的位置只有语义 Token 定义和主题重定向；
- 字面量必须满足该类型的值域和格式约束，超出值域是错误；
- 平台差异由 Renderer 把 Token 映射到平台机制实现，Token 本身不内嵌平台语法。

Token 类型集的扩展与 §37.3 语法版本同构：新增类型必须建立新的类型方言版本（§4.6）、提供迁移器与基线用例集，禁止实现私增类型语义。

存量样式接入（CSS 或平台样式资产）在迁移期内允许本地开发双轨：目标形态必须是 Token / 样式片；进入发布快照仍受 §36.4 字面量禁令与 §22.4 门禁约束；双轨期必须在 manifest 中声明并带截止修订，超期未收敛的产物不得进入发布快照。

### 36.3 主题

主题是 Token 集之上的有界投影：在一个已声明的主题基上重定向部分 Token 的解析结果：

```json
{
  "id": "theme-dark",
  "kind": "theme",
  "extends": "theme-light",
  "overrides": {
    "color.bg.surface": {"ref": "color.base.gray.900"},
    "color.text.primary": {"ref": "color.base.gray.100"}
  }
}
```

规则：

- 主题只能重定向已存在的 Token，只能重定向到同类型且作用域可达的解析结果；不能新增 Token、不能改变类型、不能循环；
- 产品必须声明默认主题和可用主题集；每个可用主题必须能解析产品实际引用的全部语义 Token，解析不完整是静态错误；
- 运行实例在启动时冻结主题版本（§4.5 的配置冻结语义）；主题切换只影响新建实例，不静默改写已运行实例；
- 系统偏好（暗色、降低透明度、减少动效）作为外部输入，只允许选择已声明的主题或已声明的偏好组；选择失败时使用发布快照默认主题并上报降级原因。

### 36.4 样式片

样式片是可复用的命名样式单元，引用 Token 或承接其他样式片；结构树节点通过 `style` 引用接入：

```json
{
  "id": "style-button-primary",
  "kind": "style",
  "schema_version": "1.0",
  "base": {
    "background": {"ref": "color.action"},
    "foreground": {"ref": "color.text.on-action"},
    "radius": {"ref": "radius.md"},
    "transition": {"ref": "duration.fast"}
  },
  "variants": [
    {"when": {"state": "hover"}, "set": {"background": {"ref": "color.action-hover"}}},
    {"when": {"state": "disabled"}, "set": {"opacity": {"ref": "opacity.disabled"}}},
    {"when": {"platform": "mobile"}, "set": {"background": {"ref": "color.action-mobile"}}}
  ]
}
```

规则：

- 样式片可声明的外观面包括背景、前景、边框、圆角、阴影与高程、透明度、字体排印和动效时长或曲线；某个节点接受哪些外观面由其契约声明；
- 条件变体的选择器只允许 `state`、`platform` 和 `breakpoint`，取值必须是已声明枚举；同一条件命中多个 `set` 时必须有显式顺序，歧义命中是静态错误；
- 样式片之间通过 `extends` 承接，承接链不得循环；
- 样式值只能引用 Token；直接书写颜色、尺寸字面量的样式片不能进入发布快照，允许字面量的位置只有 Token 定义（§22.4 门禁）；
- 平台专属样式机制一律由 Renderer 的样式映射处理，样式片本身保持平台无关。

### 36.5 契约声明

- 元组件契约（§5）必须声明样式面：该元组件接受哪些外观面；对未声明样式面的引用是静态错误；
- 组件契约必须声明哪些内部样式位对外公开（与 §2.2 公开契约一致）；未公开样式位不可被外部覆盖；
- 图层引用样式片时，只能使用所在页面声明公开的图层外观面；
- 每个样式面必须声明目标平台无法表现该外观时的降级行为（忽略、替代或错误），由 Renderer Contract（§18.4）的允许差异条目覆盖；
- 进入/离开动画与转场动效属于节点必须声明的外观面：动效值只能引用 motion Token（§36.2），节点只能编排其契约声明过的动效面；未声明的动效编排是静态错误。动效映射由 Renderer 实现，不承诺跨平台像素一致（§20）。

### 36.6 覆盖链

覆盖必须显式、有限、可静态判定，不存在选择器引擎：

```text
Token < 组件默认样式片 < 页面覆盖 < 产品主题（低 → 高）
```

- 覆盖只能发生在链上已声明的层级，且只能覆盖公开样式位；
- 同一目标同一外观面的多个候选值由覆盖链唯一决定；覆盖链无法判定的冲突是静态错误，不做隐式合并；
- 通过修改组件隐藏结构（§2.2）来改变样式是被禁止的手段；需要重新呈现时使用组件变体（§6、§12）。

### 36.7 可访问性

- 前景/背景 Token 配对在每个可用主题下必须满足声明的对比度要求，逐主题执行检查；
- 焦点指示外观必须可主题化，但不能通过主题移除；
- 减少动效偏好映射到已声明的动效 Token 替代组，运行时应用替代值并记录，不静默禁用；
- 主题或样式片导致可访问性检查失败时，该主题不能进入发布快照。

### 36.8 检查与发布

- Token 引用闭合、类型匹配、循环检测和值域校验；
- 每个主题对产品引用 Token 的解析完整性检查；
- 样式片 Schema、条件枚举、承接链和冲突判定检查；
- 发布快照包含 Token 集、主题和样式片摘要（§16）；样式资源按对象修订递增，发布后不发生原地修改；
- 以上检查并入 §22.4 质量门禁。

## 37. 交互与绑定语法

### 37.1 目标

叙述性记法（如 `press → submit`、`validate(form)`）用于示意，不是可解析语法。为保证同一产品模型在不同实现上行为一致：

- 解释模式与编译模式使用同一解析器与同一中间表示（§13.3）；
- 实现不得私增语法或引入第二个表达式语言；扩展只能通过新语法版本进入（§37.3）；
- 解析失败必须报错并保留上下文，禁止静默丢弃、降级为空操作或猜测语义。

### 37.2 词条

```text
动作链     := 事件引用 "→" 动作 ("→" 动作)*
事件引用   := 对象标识 "." 事件名
动作       := 动作标识 "(" 实参 ("," 实参)* ")"
实参       := 字面量 | 引用 | 调用 | 分组
引用       := 作用域 "." 路径
作用域     := "prop" | "param" | "state" | "session" | "product" | "local" | "capability"
条件谓词   := 比较 | 逻辑组合 | 引用 | 调用
```

语义规则：

- 作用域对应组件输入属性（§6）、页面参数（§8）、状态层级（§11）、纯计算和宿主能力返回（§10）；路径成员必须是目标契约声明过的成员，未知成员是静态错误；
- 含 `provided` 作用域：供给容器在其契约中声明 `provides`（§2.8）后，其子树内的绑定可引用 `provided.<id>.<path>`；引用方必须在其契约中声明对应的 `consumes` 依赖后方可引用，未声明的供给不可见，解析失败是静态错误；供给可见范围限定于供给容器的子树实例边界，不进入全局作用域；
- 组件、页面和交互只允许引用自身可见的作用域；跨所有权可见性由状态权限（§11）和组件公开契约共同决定，不可见即静态错误；
- 跨所有权写状态（组件动作写页面状态、页面动作写组件内部状态）要求目标状态在动作所属契约中显式声明允许该写入，否则是静态错误；
- 可调用的函数只限已注册并声明输入输出和错误的 Local Function（§10 第 4 类）；
- 动作类别（§10 的六类）决定动作的目标合法性校验规则，类别不能在语法层混用伪装。

### 37.3 版本与兼容

- 语法版本在 manifest 和每个携带表达式的资源上声明；
- 破坏性变更必须新建语法版本并提供迁移器（§22.3）；运行实例固定其解析器版本与资源语法版本，恢复时不得用新版本静默解释旧表达式，无法解释的表达式进入明确错误边界；
- 每个语法版本必须附带基线用例集；Renderer 一致性测试（§33）必须全量执行基线用例集。

### 37.4 静态检查

- 引用的对象、事件、动作、状态和函数存在且类型一致；
- 动作链上的错误传播必须显式声明为冒泡、边界处理或吞掉并上报；未声明的错误传播是静态错误；
- 事件图循环必须声明终止条件；无终止条件的循环是静态错误（§18.1 交互循环检查的形式化）；
- 重复提交语义通过动作契约的幂等、取消和并发策略声明静态表达（§18.4 Action Contract）。

## 38. 启动元组件集与一致性分级

### 38.1 启动元组件集

为使不同语言实现产生可互换的产品模型，规范定义合规实现必须提供的最小元组件集：

```text
Tier A（必需）：Text、Icon、Image、Button、Input、Select、Checkbox、
              Stack、Scroll、Overlay、List、Modal
Tier B（客户端必备，允许替换实现）：Grid、Split、Anchor、Tabs、Drawer、Table
```

规则：

- 每个 Tier A 元组件必须满足 §5 完整契约、§36 样式面声明和可访问性要求；
- 实现提供的额外元组件按 §23.12 kind: primitive 注册（Primitive Extension，§17）；
- 某平台无法提供必需元组件时，必须按 §12 使用声明过的替代实现或产生明确错误，禁止静默缺失或空实现；
- Tier B 缺失时必须在 platform profile 声明，由编译器在目标平台校验引用并给出降级诊断（§13.1 第 8 步）。

### 38.2 Renderer 一致性分级

分级是可验证的声明，不是自我描述。发布清单（§16）标注实现已达分级，未验证不得标注：

```text
Level 0 模型与验证核心：项目模型 Schema、ID、规范化序列化、引用索引、
        静态验证器；Token/主题/样式片与交互语法的解析和检查（§4-§9、§36、§37）
Level 1 解释运行时：页面实例、组件树渲染、布局、状态生命周期、导航、
        事件分发、重复提交与取消、错误边界、基础恢复（§13.2）
Level 2 完整契约：Telemetry Ingest/Query、Debug、Experiment Provider、
        安全与隐私门禁、构建与部署验证（§29-§33）
```

- 升级必须满足该级全部条目并保留低级证据；
- 分级声明必须同时说明对 §44.3 基线 18-32 的覆盖：静态条目（19，及 22 的静态部分）按 Level 0 验收；布局求解、动效替代、绑定并发与恢复（18、20、21、23、26、27）按 Level 1 验收；性能门禁、Business Fact 与标准运营事件族（24、25、28、29）按 Level 2 验收；文案通道互斥与三平面分离静态违例（30、31）按 Level 0 验收；受控交叉校验（32）按 Level 2 验收；未覆盖条目按未达对应分级处理；
- Renderer 之间的一致性比较以 Level 0 模型一致性为前提：两个 Renderer 若不支持同一语法版本、同一类型方言版本（§4.6）或同一 Token/样式能力集，一致性比较结果无效，必须先对齐声明；
- 分级声明歧义或夸大在验收中按失败处理。

## 39. 绑定映射

### 39.1 定位

绑定映射是项目模型中的第一类版本化资源（§4），集中管理"用户行为 → 具体操作"的映射条目。每个条目（binding）拥有稳定 `id`，事件端是对象契约声明的事件（点击对应 `press` 事件，不限定于点击），操作端是声明过的操作：

```json
{
  "id": "map-checkout",
  "kind": "interaction-map",
  "schema_version": "1.0",
  "syntax_version": "1.0",
  "bindings": [
    {
      "id": "bind-cart-submit",
      "on": "checkout-button.press",
      "guard": {"gt": [{"ref": "state.cart.count"}, 0]},
      "actions": [
        {"kind": "adapter", "call": "order.create", "as": "created", "arguments": {"payload": {"ref": "state.cart.items"}}},
        {"kind": "navigation", "target": "order-confirm-page", "arguments": {"orderId": {"ref": "prev.orderId"}}}
      ],
      "errors": {"*": {"boundary": "checkout-error"}}
    }
  ]
}
```

规则：

- 事件引用必须指向已存在对象的契约事件；对象被删除时，编译器引用检查（§4.3）必须报告悬空绑定；
- 绑定可以声明在两个位置：跨页面流程和可复用映射放入绑定映射资源；页面和组件内部的少量 UI 绑定允许内嵌在对象声明中。两个位置使用同构 Schema 与同一语法（§37），编译器合并为完整事件图后统一校验；同一事件在同一层级重复绑定且无法显式排序是静态错误；
- 保护条件（`guard`）是结构化条件谓词，必须取布尔值；谓词不可解析或类型不是布尔是静态错误；`guard` 为假时该条目不执行且不是错误；候选绑定的评估顺序必须确定性；
- 操作端动作类别与 §10 六类动作一一对应：`ui`、`state`、`navigation`、`adapter`、`host`、`function`。`adapter` 动作是对已声明外部适配器的调用，接口调用因此成为一级操作类型；每个被调用的适配器必须持有 Data Contract（§40），调用未声明或未通过兼容检查的适配器是静态错误；
- 组件内部绑定可使用 `event` 动作，把内部元组件事件上升为所属组件契约声明的事件；`event` 不属于副作用类别，是组合语义的一部分，事件未在所属组件契约声明是静态错误；
- 动作结果传递：动作可声明 `as` 保存结果；后继动作通过 `prev` 引用上一个动作的结果，或引用已命名 `as` 的结果；引用不存在的结果或结果上不存在的成员是静态错误；
- 同一条目内的导航动作必须有显式分支条件，无条件的多导航是静态错误；`navigation` 目标必须是导航图中存在的节点（§9），权限拒绝的 fallback 随目标在导航图中声明；
- 条目必须声明重复触发与并发策略：取消旧请求、取代旧请求或排队，未声明时禁止接受重复触发；请求超时不当作"操作未执行"处理（§10），通过 `action_request_id` 进入诊断关联（§22.3）；
- 解释模式由运行时按绑定映射驱动事件图；编译模式从同一中间表示生成产物（§13.3），两种模式不允许行为分叉；已运行实例冻结绑定映射与语法版本（§16），条目修订只影响新建实例。

### 39.2 序列化等价

绑定中的引用、条件和动作链允许两种等价序列化：结构化 JSON（如本章示例）和 §37.2 的文本 DSL，两者必须解析到同一中间表示。实现不得使两种写法产生语义差异；规范化的导出形态以编译器输出为准。

### 39.3 静态检查

- 对象、事件、动作目标、适配器、页面和错误边界存在；
- `guard` 布尔性、实参类型匹配和结果引用存在性；
- 并发策略、错误处理与幂等声明完整；
- 绑定形成的循环链必须声明终止条件，否则是静态错误；
- 上述检查并入 §18.1 与 §22.4 质量门禁。

## 40. Data Contract

### 40.1 定位

Data Contract 是外部适配器调用的声明契约，是 §10 第 6 类 External Adapter、§39 `adapter` 动作和 §24.7 适配器注记的共同数据面基础。框架核心不内置数据访问；一切数据获取都通过已声明的外部适配器进行，并持有本契约。

### 40.2 契约 Schema

```json
{
  "id": "notes-list",
  "kind": "data-contract",
  "schema_version": "1.0",
  "source": {"kind": "http", "adapter": "adapter-notes-api"},
  "input": {"properties": {"query": {"type": "string"}}, "required": []},
  "output": {"type": "array", "items": {"$ref": "data_models/note"}},
  "errors": ["auth.denied", "network.timeout", "server.unknown"],
  "timeout_ms": 5000,
  "idempotency": {"kind": "read"},
  "cache": {"kind": "stale-while-revalidate", "ttl_s": 60, "max_entries": 100},
  "staleness": {"max_age_s": 300},
  "paging": {"kind": "cursor", "page_size_max": 100},
  "permissions": ["notes.read"],
  "privacy_class": "operational",
  "trace": {"propagate": ["outbound", "return"]}
}
```

规则：

- `source.kind` 只能使用宿主适配器已声明并注册的来源类别（HTTP、RPC、本地数据库、宿主文件等）；未声明的来源是静态错误；
- `input`/`output`/`errors` 必须引用或内联合法 Schema；错误必须是可判定的类型化错误码，与 §41 诊断码体系衔接；
- `idempotency` 声明读写语义与幂等键；写操作的确认语义与 Business Fact（§24.1 第 4 类）对齐；
- `trace` 声明追踪上下文传播（§24.8）：声明后由运行时注入与记录，适配器实现不得自行构造或改写追踪身份；未声明的契约不产生跨栈关联；
- 契约本身是版本化资源（§4.2），破坏性变更必须产生新版本并提供迁移器（§22.3）。

### 40.3 加载状态与结果语义

- 数据状态对齐 §11 异步状态：idle、loading、success、empty、error、cancelled 必须都可表达；
- 超时不当作"操作未执行"（§10）；未知结果只能进入 `unknown`，不能当作失败自动重试（§22.1）；
- 响应必须按 `output` Schema 校验；校验失败是类型化错误并上报诊断码，禁止静默截断或猜测字段。

### 40.4 缓存与陈旧

- 缓存键由契约 id、规范化输入摘要和身份作用域组成；用户切换时按 §28 执行数据隔离；
- 陈旧策略必须显式声明；超过 `staleness` 的数据展示时必须携带陈旧标记或触发刷新；
- 失效由显式事件驱动，不做隐式全局失效。

### 40.5 权限与隐私

- `permissions` 声明访问所需权限；权限拒绝是可判定状态并必须有 fallback（§9）；
- 凭据不得写入模型、契约、日志、快照或事件（§32）；载荷的隐私分类决定其进入诊断与回放数据时的屏蔽策略（§29）。

### 40.6 校验与门禁

- 静态：Schema 引用存在、适配器已注册、超时/幂等/缓存声明完整、隐私分类通过检查；
- 运行：响应校验、错误码分类、取消与超时行为、用户切换隔离（§18.2、§33 故障注入）；
- 上述检查并入 §18.1 与 §22.4 质量门禁。

## 41. 统一诊断码注册表

### 41.1 命名空间

全部静态错误、运行诊断和契约诊断使用统一命名空间：

```text
mf.<area>.<name>
```

`area` 固定为：`schema`、`ref`、`layout`、`route`、`interaction`、`binding`、`style`、`token`、`theme`、`reg`（注册）、`data`、`cap`（能力）、`nav`、`state`、`i18n`、`tele`（采集）、`exp`（实验）、`debug`、`sec`、`build`、`perf`。示例：

```text
mf.schema.unknown-field
mf.reg.contract-mismatch
mf.data.output-invalid
mf.i18n.missing-translation
mf.exp.assignment-incompatible
mf.layout.unsatisfiable
mf.perf.budget-exceeded
```

### 41.2 注册表资源

诊断码注册表是框架级版本化资源，不属于任何单个项目。每个条目包含：

```text
code、severity（error/warning/info）、stage（static/runtime）、
message_template、doc_ref、blocking_release（布尔）、
introduced_version、deprecated_version（可空）
```

### 41.3 规则

- 所有契约（§18.4、§23、§28-§33、§40、§42）声明和发射的诊断码必须已在注册表登记；发射未登记诊断码视为实现缺陷；
- 诊断码含义不可复用：废弃保留墓碑（§22.3），新语义必须使用新码；
- 发布清单中的"诊断规则版本"（§16）即注册表版本；同一 `release_id` 的诊断结果必须可用其登记版本精确解释；
- 注册表提供查询接口，供工具、AI 和外部分析平台解析码含义。

## 42. 国际化资源模型

### 42.1 资源模型

i18n 资源是项目模型中的版本化资源（§4 目录新增 `i18n/`）：

- **Locale 注册表**：声明默认 locale、支持 locale 列表和确定性回退链；locale 使用 BCP 47 标识；
- **Message 资源**：`message_id` 为稳定 id（§4.2），每个 locale 一个变体值；文案不属于样式（§36 Token 只承载外观，不承载文案）。

```json
{
  "id": "messages",
  "kind": "i18n-catalog",
  "schema_version": "1.0",
  "default_locale": "zh-CN",
  "supported_locales": ["zh-CN", "en"],
  "fallback": {"en": "zh-CN"},
  "messages": {
    "notes.title": {"zh-CN": "备忘", "en": "Notes"},
    "notes.count": {
      "zh-CN": "{count, plural, other {# 条笔记}}",
      "en": "{count, plural, one {# note} other {# notes}}"
    }
  }
}
```

### 42.2 引用方式

- 结构树文本节点通过 `t` 引用 message：`{"type": "Text", "t": "notes.title"}`；占位符实参通过 `t-args` 按 §37 引用表达式提供；
- 文本节点只能使用 `bind`（运行时值）或 `t`（message 引用）之一，同时使用是静态错误；
- 进入发布快照的产品文案必须引用 message 资源；允许字面量文案的位置只有原型演示，且必须显式标注豁免并产生警告。

### 42.3 格式化子集

- 占位符、复数和选择使用固定的 MessageFormat 子集；该子集按 §37.3 同样的方式版本化管理，不得私增语法；
- 占位符类型由 Message 资源声明，实参类型不匹配是静态错误；
- 数字、日期、相对时间格式化器是注册表资源，Renderer 映射到平台机制，格式化器本身不内嵌平台语法。

### 42.4 方向与布局

- 布局与样式一律使用逻辑方向（start/end），§7 布局能力和 §36 样式面不得内嵌物理左右；
- locale 决定解析方向（LTR/RTL）；镜像行为由 Renderer 实现，编译器执行镜像检查：使用物理方向属性是静态错误。

### 42.5 运行时与冻结

- locale 解析顺序固定：用户显式选择 → 宿主偏好 → 默认 locale；解析结果随实例冻结（§4.5），切换 locale 只影响新建实例，不静默改写已运行实例；
- 缺失翻译不是静默回退：按回退链解析并上报 `mf.i18n.missing-translation` 诊断；回退后的展示必须可从诊断数据区分；
- 已解析 locale 必须暴露给平台可访问性机制（如 HTML `lang`），并入 §28 Renderer Contract。

### 42.6 检查与发布

- 每个 locale 对产品引用 message 的解析完整性检查（与 §36.8 主题完整性检查同构）；
- message 引用存在性、占位符类型、复数类别合法性检查；
- 翻译覆盖率进入数据质量投影（§30.2）；伪本地化和 RTL 冒烟纳入 §33 测试层；
- 发布快照包含 i18n 资源摘要（§16）；以上检查并入 §18.1 与 §22.4 质量门禁。

### 42.7 文案通道判定

文案归属 i18n message 还是内容资产（§2.7）按唯一判定规则执行，两个通道互斥：

- **i18n message 通道**：进入产品结构契约、被结构树文本节点以 `t` 引用、需随发布快照版本化并参与回退链与可访问性检查的文案；修订随发布快照生效；
- **内容资产通道**：需要运营侧在不产生新发布快照的前提下变更的文案（投放、公告、营销活动），由内容位容器在运行时按冻结的 `config_version` 装配（§4.5），曝光按 §24.2 标准事件族登记；
- **判定规则**：以"是否必须随下一版发布才能变更"为唯一判据——必须随发布变更的走 i18n，允许免发布运营变更的走内容资产；判定歧义时按 i18n 处理，需要免发布变更时显式迁移到内容资产通道；
- **互斥校验**：同一内容位的文案来源只能声明其一，同时声明 i18n message 与内容资产是静态错误（`mf.i18n.channel-conflict`）；i18n message 不得声明投放语义（campaign、活动归因），内容资产不得作为 `t` 引用目标，违例均为静态错误；
- **多语言**：内容资产声明多 locale 变体时，遵循 §42.1 的 locale 注册表与回退链；缺失变体按回退链解析并上报 `mf.i18n.missing-translation`，不得静默展示单一语言；
- 发布快照中的 i18n 资源摘要（§16）不包含内容资产；内容资产摘要随 `config_version` 携带（§4.5）。本节检查并入 §18.1 与 §22.4 门禁。

## 43. 发布健康度、订阅式查询与数据回流

### 43.1 发布健康度投影

发布健康度是 §24.3 事件投影中的标准投影，使用固定命名的标准指标，保证跨实现可比：

```text
release.health.crash_free_session_rate      无崩溃会话率
release.health.error_free_session_rate      无错误会话率
release.health.recovery_success_rate        恢复成功率
release.health.rollback_rate                回滚率
release.health.fact_confirmation_latency    Business Fact 确认延迟
release.health.telemetry_loss_rate          采集丢失率
```

指标口径作为版本化分析资源登记（§30.2）；框架负责数据与投影，目标值和告警策略由外部平台管理。

### 43.2 订阅式查询边界

§30.2 的查询契约是拉取式的。实时订阅、实时告警和流式分析不属于查询契约，由可选的 Subscription Contract 承接：

- `subscribe(filter, cursor)` 返回有界过滤的推送流；过滤器与 §30.2 查询过滤器同构，禁止无界订阅；
- 推送为 at-least-once，消费方按 `event_id` 去重；背压通过游标回退实现，不丢弃已确认数据；
- 订阅主体、作用域和审计遵循 §32；框架定义协议，不内置流式分析或告警平台实现。

### 43.3 数据回流闭环

观测与实验结论由业务层加工产出（基于 §24.3、§30.2 的数据支持能力），回流通过项目模型的标准入口进入下一版。

findings 注记必须符合版本化 Schema，并按 `finding_type` 分类（bug-cluster / experiment-conclusion / ops-alert / regression-key）：

```text
finding_id（稳定 id，§4.2）
finding_type
schema_version
source_ref（来源分析系统、方法与时间）
summary
target_ref（被注记的资源 id）
created_at / created_by
```

- 外部结论以结构化命令（§14）登记为资源注记，登记时按 `finding_id` 引用，不得以自由文本替代：页面、组件和交互可携带 `findings` 引用，注明来源分析、时间和结论摘要；注记只携带声明，不携带可执行逻辑（与 §24.7 同纪律）；
- 带 `findings` 注记的资源在下一版修订的校验报告中显式列出，并纳入 §18.3 回归基线；`regression-key` 类型必须绑定可执行的校验命令或用例引用，防止同类问题回归；
- findings 是版本化资源：修订产生新版本，历史 finding 保留墓碑（§22.3）；
- 回流是流程与来源标注，不自动修改模型：任何由结论触发的修改仍然走 §14 结构化命令、验证和审计。

## 44. 端到端最小规范示例与一致性基线

### 44.1 目的

本节提供一份规范性最小产品示例，作为实现合规的锚点：解释模式与编译模式（§13.3）、不同 Renderer（§38.2）和一致性回归（§18.3）都以能否正确处理本示例为最低判据。示例为精简示意，正常形态按 §15 目录组织，规范化导出以编译器输出为准。基线覆盖绑定、契约、注册、i18n、采集、布局、动效、性能与三平面分离九个领域；核心章节的每次修订必须同步基线（§44.4）。

### 44.2 示例产品

"备忘（Notes）"：一个列表页和一个编辑页，覆盖注册宿主组件（§23）、模型组合组件（§6）、数据契约（§40）、绑定映射（§39）、采集注记（§24.7）、追踪传播（§24.8）与 i18n（§42）：

```text

├── microflow.frontend.json
├── design-system/tokens.json        （采用 §36.2 Token 集，theme-light 为默认主题）

├── components/note-item.json        （模型组合组件，§6）

├── pages/notes-page.json
├── pages/editor-page.json
├── navigation/nav.json              （两个节点、push 边、权限拒绝 fallback，§9）
├── interactions/bindings.json       （§39）
├── data/notes-list.contract.json    （采用 §40.2 Data Contract）
├── data/notes-save.contract.json    （写操作契约：幂等键 noteId，确认语义对齐 Business Fact，声明追踪传播，§24.8）
```

### 44.3 一致性基线

以下行为必须全部通过，并作为 §33 测试层与 §38.2 分级声明的强制基线：

```text
1. 双实例隔离：同页两次引用 note-item，状态与数据互不影响（§2.6）；
2. guard 为假（无未保存修改）时绑定不执行且不报错（§39.1）；
3. 适配器超时进入错误边界，产生 mf.data 超时诊断，不当作未执行（§40.3）；
4. 输出 Schema 不匹配产生类型化错误，不静默截断（§40.3）；
5. 缺失 en 翻译按回退链展示并上报 mf.i18n.missing-translation（§42.5）；
6. 注册实现与契约不符是运行错误并进入错误边界（§23.3）；
7. locale/主题冻结：运行中切换只影响新建实例（§36.3、§42.5）；
8. 采集注记事件走完整校验管道，业务代码零埋点（§24.7）；
9. 解释模式与编译模式对上述行为完全一致（§13.3）；
10. 发布快照可重复构建、可回滚，诊断码可用注册表版本解释（§16、§41.3）；
11. 声明传播的适配器调用在事件与 Debug 快照中携带外部运行引用；未获得运行引用的确认进入 unknown 并记录缺失原因（§24.8）；
12. 页面未声明图层树时以隐式 ContentLayer 完成校验与渲染；首次声明显式图层后隐式图层不再生成（§7）；
13. 纯配置创建的新页面引用未注册资源时校验失败，产生静态错误；通过校验后以新发布快照进入运行（§2.7）；
14. manifest 声明的类型方言版本可解析发布快照内全部 Schema 引用；方言版本不满足时构建失败（§4.6）；
15. 统一注册：自定义元组件（kind: primitive）与数据适配器（kind: adapter）按 §23.12 注册后，纯配置构建新页面通过校验并正确渲染（§23.11、§2.7）；
16. 容器信息契约：组件声明 consumes 的信息无任何上游 provides 且作用域不可达时，校验失败产生静态错误；provides 形状变更能在影响分析中命中全部消费容器（§2.8）；
17. findings 按 schema 版本回流并可被回归基线按 finding_id 消费；自由文本替代 findings 引用是静态错误（§43.3）；
18. 布局求解确定性：同一约束输入（含固定尺寸合成元组件的内容度量）在解释模式、编译模式和不同 Renderer 上产生相同的规范化矩形集（§7.3）；
19. 不可满足约束（同轴 fill 与 fixed 并存、fixed 超出可用空间、锚定循环、冲突定位规则）产生 mf.layout 静态错误并阻止构建（§7.3、§7.5）；
20. 条件布局在命中条件时解析到声明方案；条件全不命中且无默认方案是静态错误，有默认方案时按默认方案执行（§7.4）；
21. 目标平台不支持已引用布局能力时按声明降级执行并产生诊断，禁止静默省略（§7.1、§12.1）；
22. 节点引用未声明动效面是静态错误；动效值只能解析到 motion Token，字面量动效不得进入发布快照（§36.5、§36.4）；
23. 减少动效偏好命中替代组时，运行时应用替代 motion Token 并产生记录，不静默禁用动效（§36.7）；
24. Performance Contract 预算超标时发布门禁失败并产生 mf.perf 诊断；每项指标结果附带目标设备、数据规模与网络条件（§22.2）；
25. 增量构建不重新生成无关页面，且增量产物与全量构建产物一致（§22.2）；
26. 绑定重复触发按 Action Contract 与绑定条目声明的并发策略执行（cancel-previous / supersede / queue / reject-new）；未声明并发策略的绑定拒绝重复触发；无终止条件的绑定循环是静态错误（§10.1、§39）；
27. Recovery Contract：恢复后未知结果副作用只进入 unknown 且可查询，不自动重试；快照版本不匹配时按迁移规则处理或进入错误边界，不静默丢弃快照（§16.1）；
28. Business Fact 重复提交按去重身份幂等确认，同一去重身份不产生第二次确认；提交超时进入 unknown 并可查询（§24.1、§30.1）；
29. 标准运营事件族（`ops.page.viewed` / `ops.page.left` / `ops.feature.used` 等）由运行时拦截边界零埋点产生，字段口径校验通过，可被投影与漏斗资源直接消费；业务代码手工上报标准族是静态错误（§24.2、§24.3、§24.7）；
30. 文案通道互斥：同一内容位同时声明 i18n message 与内容资产来源是静态错误；内容资产多 locale 变体按回退链解析并产生缺失诊断，不静默展示单一语言（§42.7）；
31. 三平面分离：结构树内联命令式逻辑、配置载荷携带可执行逻辑或未验证数据、实例数据回写项目模型，分别被静态或运行时拒绝，并产生 §2.9 矩阵对应诊断码（§2.9）；
32. 受控交叉：实验与运营变体改写未登记入受控交叉清单的资源面被静态拒绝；已登记改写面按声明执行并随实例冻结，清单摘要在发布快照中可校验（§2.9、§24.4）。
```

### 44.4 维护规则

- 示例与基线随规范版本一起版本化；核心章节的修改必须在同一修订中同步更新示例与基线，否则该修订不得形成新的规范基线；
- 基线用例集是 §37.3 语法基线的超集，两者冲突时以更严格者为准。
