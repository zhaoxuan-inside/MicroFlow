## 2. 已明确的产品要求

- 分离业务步骤与执行控制，以配置组织微型业务算子，降低 AI 开发时需要理解的上下文范围。
- 算子是业务流程中可独立描述、执行和验证的步骤，内部允许普通辅助函数，不要求所有函数都成为算子。
- 主方法及 fallback、metrix、log 代理使用相同的六参数结构，并返回 boolean。
- context 不可变；metrix 用于测量；debug 支持执行快照和暂停；log 用于特殊日志上报。
- 主业务方法发生异常，框架自动调用 fallback；fallback 输入包含主方法原始输入和异常信息。
- fallback 不存在时，框架拦截异常，将异常写入 Output，并立即熔断当前根流程，禁止继续派发业务节点。
- log 代理不存在时，由框架默认记录 options 中的场景、版本号、traceId、算子名、开始时间、结束时间及执行结果。
- metrix 代理不存在时，由框架默认采集同源的调用测量记录，并生成耗时、次数、成功失败等指标。
- 同步和异步属于本次算子调用的执行属性，同一个算子在不同调用中可以采用不同方式。
- 异步流程持久化执行状态并支持断点恢复。
- 算子声明资源与副作用属性，用于约束数据库操作等临界步骤。
- 每个接入平台的 Python 文件具有注册入口，新文件接入时由平台调用入口，文件显式注册内部方法。
- 编排支持 DAG、子 DAG 作为节点及检查机制。
- 支持完整版本的快照发布与回退。
- 支持有明确有效性边界的算子结果缓存，以及独立于缓存的幂等执行协议。
- 持久化通过接口提供，上层页面选择并配置具体介质，由宿主注入实现；框架不固定或内置必选介质。
- 缓存、幂等、同步/异步、恢复、超时等算子级执行属性通过配置统一管理，代码不固定本次执行策略。
- 平台需要支持快速业务开发、日志追踪、运营数据、算子利用分析，并以性能、可用性和可维护性为质量目标。

数据采用层级 Map、路径访问和 schema 约束，通过配置完成算子边界映射。业务方法签名保持六参数，调用配置统一命名为 options，通过 context.options 只读访问，不增加第七个参数。

## 3. 产品定位与边界

MicroFlow 是适配 VibeCoding 开发特性的 Python 业务开发与执行框架，为使用 VibeCoding 工具开展业务开发提供结构化底座。框架通过职责单一的算子、显式编排、明确契约和可验证行为，降低理解与修改业务所需的上下文范围，使变更能够局部理解、明确检查、隔离验证并追踪到发布后的效果。

VibeCoding 工具是框架的外部使用者。框架提供便于其读取、生成、修改和验证的代码结构、元数据及标准接口；集成特定工具、管理模型或组织 AI 代理不属于本方案的核心职责。

平台承担执行机制，不替业务决定优惠、审批、补偿等规则。数据库、消息服务和第三方接口通过资源适配接入；平台不默认替代业务数据系统，也不把任意外部操作变成可回滚事务。

建议区分开发者、业务分析人员、运营人员、运维人员和平台管理员的操作权限；AI 工具沿用授权主体的权限，不因自动化获得额外权限。

## 4. 总体架构

### 4.1 开发与定义层

包含算子 SDK、文件注册协议、算子目录、契约与路径模型、编排定义、模板、局部上下文描述及测试支持。相关元数据和检查结果通过标准接口提供给开发者及外部 VibeCoding 工具使用。

### 4.2 控制层

包含注册收集、编排编译检查、快照构建与发布、版本路由、权限审计及运行管理。控制层管理不可变定义，不直接维护某次调用的临时业务变量。

### 4.3 执行层

包含入口适配器、流程调度器、节点执行器、资源管理器、幂等管理器、算子结果缓存、异常处理、检查点与恢复。执行器按 release_id 装载完整版本，不跨版本拼接实现。

### 4.4 观测与分析层

包含执行追踪、结构化日志、指标、调试快照、可靠业务事件、运营聚合和算子利用分析。普通观测故障与业务执行隔离，关键业务事件遵守单独的可靠性协议。

### 4.5 持久化接口与宿主能力层

框架提供 PersistenceProvider、StateStore、ArtifactStore 及能力协商协议，负责状态批次、恢复和引用语义，不固定介质。上层页面管理提供者选择和绑定配置，宿主创建并注入实例。工作者通过统一状态接口提交结果，缓存实现与业务资源能力不得绕过原子提交。

## 5. 核心对象与标识

- OperatorDefinition：稳定业务标识、实现、代理、契约、说明和真实能力约束；缓存、幂等、同步/异步等通过 default_policy 提供可覆盖默认值，不固定本次调用策略。
- FlowDefinition：DAG、输入输出、节点、边、控制规则及子图引用。
- InvocationSpec：一个节点如何调用算子或子图，包括映射、本次 execution_mode、超时、重试与资源约束。
- ReleaseSnapshot：可共同运行的完整不可变版本，包含产物摘要和清单。
- FlowInstance：一次业务流程及其固定 release_id、业务标识、状态和输入输出。
- InvocationInstance：某个节点的一次逻辑调用。集合展开或循环需额外区分项标识和迭代序号。
- Attempt：一次实际执行尝试。重试产生新 attempt_id，不改变逻辑调用标识。
- Checkpoint：在指定契约版本下保存的可恢复业务进度。
- BusinessEvent：具有业务含义、稳定 event_id 和版本的事实记录。
- InvocationOptions：本次调用的有效配置与可信运行元数据，通过 context.options 提供只读视图。
- IdempotencyRecord：业务操作身份、请求摘要、执行归属、结果和保留状态，不作为普通可淘汰缓存。
- CacheEntry：可失效的可复用业务结果及来源、数据版本和有效期，不承担副作用去重责任。
- EffectiveOperatorPolicy：合并校验后深度冻结的本次调用策略及 policy_digest。
- StorageBinding：上层指定的 provider_id、binding_id、namespace、binding_revision 及能力范围，不包含具体介质代码或明文凭据。

全链路保留 release_id、flow_instance_id、invocation_id、attempt_id、parent_invocation_id、trace_id 及 business_key。业务幂等键按业务操作生成，禁止随 attempt_id 改变。业务结果与执行尝试分别统计。

## 6. 算子协议

```python
def method_name(input, output, context, metrix, debug, log) -> bool: ...
def method_name_fallback(input, output, context, metrix, debug, log) -> bool: ...
def method_name_metrix(input, output, context, metrix, debug, log) -> bool: ...
def method_name_log(input, output, context, metrix, debug, log) -> bool: ...
```

沿用 metrix 命名。统一参数的数量、位置和职责，具体 schema 随方法角色变化。

- input：只读的业务数据视图，框架保留调用时原值。
- output：当前方法专属的可写 Output Map；业务只写 data，框架管理 meta 和 error。合法成功数据向正常下游发布；失败 Output 向查询与诊断接口发布，不交给正常业务下游。
- context：不可变执行信息和逻辑资源绑定，不存放可任意改写的共享业务状态。
- metrix：带路径和契约的测量容器/接口，提供明确的计数、分布等记录操作。
- debug：快照、检查点和暂停的受控接口。
- log：结构化诊断日志和业务事件接口。

context 数据和绑定不可变，不代表外部资源不会变化。数据库连接等运行对象由执行器解析资源引用提供，不进入持久化 Map。不可变容器也不等于对任意 Python 代码形成安全沙箱。

### 6.1 返回语义

主方法 True 表示执行成功，业务判断写入 output.data。False 表示方法主动报告失败，框架构造 OPERATOR_REJECTED 错误，默认终止流程，不自动触发 fallback。业务否定结果应采用 True 加业务字段表达。主方法抛出异常时调用已绑定 fallback；没有 fallback 时按第 12 章立即熔断根流程。

fallback True 表示恢复成功并提供合法输出，允许下游继续；False 或自身异常表示未恢复。fallback 自身不递归调用 fallback。

metrix/log 代理返回值仅表示采集处理结果，不覆盖业务终态。代理缺失时使用框架默认实现；自定义代理存在时补充特殊信息，仍保留不可覆盖的基础观测记录。输入或输出契约不通过时按框架契约错误结束调用，不伪装为业务方法异常。

普通 Python 函数和协程函数由适配器支持；这属于实现形态，与调用方同步等待还是后台执行独立。阻塞函数不能直接占用事件循环。

### 6.2 Output 标准结构

```json
{
  "data": {},
  "meta": {
    "status": "FAILED",
    "releaseId": "release-001",
    "traceId": "trace-001",
    "invocationId": "invocation-001",
    "resolution": "unhandled_exception"
  },
  "error": {
    "code": "UNHANDLED_OPERATOR_EXCEPTION",
    "type": "ExampleError",
    "message": "脱敏后的异常摘要",
    "phase": "main",
    "stackRef": "受控堆栈引用",
    "effectStatus": "unknown"
  }
}
```

成功时 error=null，data 满足业务输出 schema。失败时 data=null，不套用成功业务 schema；失败前暂存数据如需保留，只存入受控诊断快照。meta/error 是保留命名空间，业务不得覆盖。SDK 的 output.set("total", value) 是写入 output.data.total 的便捷方法；编排始终引用明确的 output.data 路径。

注册时的 output_schema 约束 Output.data，统一 envelope schema 约束 meta/error；两者独立版本化。方法返回 True 但输出非法时生成 OUTPUT_CONTRACT_VIOLATION，不能发布半成品。主方法 False 若需要具体拒绝原因，通过框架提供的受控错误报告接口补充，不能自行写系统 error 命名空间。

根流程 Output 采用相同封装，error 引用首个致命错误，并保留全部关联错误的查询引用。异常不得直接保存 Python 对象、凭据或无边界堆栈正文。同步接口返回失败 Output，异步接口通过执行查询和完成事件提供同一结果，不将任务接纳成功误作业务成功。

### 6.3 options 结构与可信来源

```json
{
  "options": {
    "scene": "order.quote",
    "version": "order.quote@1",
    "releaseId": "release-001",
    "traceId": "trace-001",
    "operatorName": "order.calculate_total",
    "operatorVersion": "1.0.0",
    "flowInstanceId": "flow-001",
    "invocationId": "invocation-001",
    "attemptId": "attempt-001",
    "executionMode": "async",
    "startedAt": "2026-10-21T10:00:00Z",
    "endedAt": null
  }
}
```

scene 来自发布后的流程或节点配置，缺省使用 flow_id；version 是业务流程版本，releaseId 是完整发布版本，operatorVersion 是实现版本，三者不得混用。外部 traceId 通过入口校验后使用或重新生成。算子名、版本和时间由框架生成，调用方不能伪造覆盖。

options 中的执行策略沿“框架默认 → 算子默认 → 编排节点 → 允许的本次覆盖”解析；发布快照保存算子和编排配置，流程级模板在发布期显式展开为节点配置，不另设隐式优先级。权限和真实副作用约束不能被配置伪造。执行信息由框架最后绑定。方法收到的 options 是开始时的不可变视图，endedAt 可能尚未确定；执行结束后框架生成新的完成视图供代理和默认采集使用，不原地修改方法的 context。JSON 字段 traceId 与内部 trace_id 是边界映射，保持唯一关联。

## 7. Map、路径与契约标准

### 7.1 数据模型

契约采用框架内置的 MicroFlow Schema v1，由内部校验器处理明确支持的类型、字段、必填、集合、枚举和区间规则；未知规则发布时拒绝，不要求第三方校验库，也不宣称完整实现其他 schema 标准。

业务数据采用 JSON 兼容的层级 Map、列表和标量；日期、金额、大整数、二进制及外部对象引用使用明确的 schema 和编码。禁止默认序列化任意 Python 对象，禁止以 pickle 作为通用跨版本数据协议。

金额应明确单位与精度，时间明确时区与格式。大数据使用带摘要、权限和保留期的耐久对象引用，不能只保存执行器本地临时路径。

### 7.2 路径语法

简单对象键使用 order.customer.id；列表使用 items[0].sku；包含点号等特殊字符的键使用元件形式，例如 ["customer.info"].id。路径解析器处理键和下标，不使用 eval。

路径区分键缺失与值为 null。映射显式声明 required、default、类型与允许转换；default 默认只用于缺失，是否覆盖 null 需显式设置。缺失的可选字段保持缺失，不能无声变成 null。

写入 output 时可按契约创建对象父节点，默认不自动扩展稀疏数组。禁止路径穿越、未声明外部字段访问或覆盖只读命名空间。

### 7.3 边界映射

每个算子只看到本地 input；框架从流程输入、已发布节点输出和允许的 context 字段构造它。算子只写自己的 output，不能通过路径直接修改其他节点。

对外输出映射先在独立候选结果中完成、检查冲突，再原子发布，避免多字段映射部分成功。多个节点默认不能写同一目标；需要聚合时声明专用汇合节点或明确的合并规则，禁止依赖完成先后决定结果。

schema 包含字段含义、类型、必填、可空、敏感等级、示例与版本，默认拒绝未声明字段。扩展字段必须声明独立命名空间及约束。类型转换只允许 schema 显式列出的转换，禁止将任意字符串隐式转成数字或布尔值。

### 7.4 metrix 的特殊语义

metrix 使用路径定位指标，但普通 set 表示赋值，不隐含累加。计数采用 increment，分布采用 observe；指标声明名称、类型、单位、允许标签及统计口径。瞬时测量与关键业务事实分别处理，不能通过普通 Map 自动获得可靠投递。

### 7.5 并行与数据确定性

每次调用的 input 从已提交版本构造，执行期间不随其他节点变化。并行节点结果独立发布，汇合节点读取明确的结果版本。默认禁止以无序完成事件覆盖同一路径。路径转换仅支持白名单取值、默认值、简单格式转换和选择；复杂计算使用业务算子。

## 8. 文件发现与注册

每个接入平台并纳入发布清单的项目 Python 文件必须提供 register(registry) 入口；这包括接入的辅助模块，其入口可以为空。第三方依赖和解释器标准库不要求改写。

一个文件可注册多个算子，主方法与代理显式绑定。未注册的辅助函数不成为编排节点。注册入口是装载协议，不采用六参数业务签名。

```python
def register(registry):
    registry.register_operator(
        name="order.calculate_total",
        version="1.0.0",
        method=calculate_total,
        fallback=calculate_total_fallback,
        metrix=calculate_total_metrix,
        log=calculate_total_log,
        input_schema="order.calculate_total.input@1",
        output_schema="order.calculate_total.output@1",
        capabilities={"effect": "pure", "idempotency_support": "natural"},
        default_policy={
            "execution_mode": "sync",
            "cache": {"enabled": False},
            "idempotency": {"enabled": False},
        },
    )
```

发现、导入、调用入口、收集声明、全量检查、发布注册表依序执行。导入和注册不得执行业务、连接业务资源或启动后台任务。跨文件依赖在收集完成后解析，不依赖导入顺序。

重复标识和版本、缺失入口、导入异常或注册不合法阻止本批生效。批次重试从新暂存表开始，现有有效注册表不被部分修改。生产中新文件加入候选版本后参与快照构建，不直接绕过完整发布改变活动版本；开发态可提供受控重载。

## 9. DAG 与子图编排标准

### 9.1 节点与边

节点类型包括算子、子图、条件路由、汇合、集合映射、有限循环及外部信号等待。边分别表达控制依赖和数据依赖；编译结果保留二者，避免把“任务已提交”当作“数据已就绪”。

节点只在所需输入可用且控制条件满足时就绪。图定义禁止任意环；循环通过有上限、超时及检查点的控制节点表达，每轮执行的 DAG 仍无环。子图引用也禁止无界递归。

### 9.2 分支与汇合

条件必须声明互斥选择或多路选择，以及未命中时的默认路径/结束规则。未选择的分支标记 SKIPPED，不能永久等待。

默认汇合等待所有激活分支成功，跳过分支不计入激活集合。任一成功、指定数量或收集全部结果必须显式配置。任一成功场景不自动证明其他分支已停止，仍需跟踪它们的取消与副作用。

业务判断为否、算子主动失败、算子异常和技术故障分别保留。预期业务拒绝以合法业务输出驱动分支；主动失败默认终止流程，可在明确的错误收集子图中处理。未绑定 fallback 的主业务异常属于根流程致命错误，错误分支、汇合和子图均不得拦截后继续正常业务。

分支激活集合在对应路由判定提交时持久化，恢复使用已提交判定，不重新读取变化中的外部状态。嵌套路由按控制令牌记录激活/跳过，汇合不能仅凭当前已完成分支推断全集。必需数据来自 SKIPPED 节点且没有备用来源时，产生 MISSING_DEPENDENCY_RESULT 并失败；optional 输入按明确缺失规则处理。

默认任一必需分支失败即停止派发新的业务节点，并对已运行分支请求取消。根流程无业务在途、无未确认副作用且所需结果齐备后才能进入成功终态。任一成功策略必须为其他分支选择“等待收敛”或显式分离为独立子流程；不允许遗留无人跟踪的业务执行。异常熔断覆盖任一成功等局部策略。

### 9.3 集合、循环与外部等待

集合节点声明并发上限、结果顺序、项标识及部分失败策略。动态展开数量有配额，不能无限生成任务。循环声明次数或业务结束条件与总超时，默认禁止无界执行。

业务等待持久化状态并释放执行线程；信号需鉴权、关联实例、去重并处理信号先到和重复到达。一个信号如何消费由节点协议定义。等待超时按显式流程规则处理。

### 9.4 子图

子图具有输入输出、版本及内部策略，对外表现为一个节点，观测时允许展开。根实例的 release_id 向子图传播。父图截止时间对子图生效；内部策略不得放宽根实例的权限及不可重试约束。失败传播和取消采用明确定义，不能因封装而隐藏在途副作用。

## 10. 检查与执行计划

注册时检查签名、代理绑定、唯一标识、契约存在性和属性完整性。编排发布时检查 DAG 环、子图递归、节点引用、路径、类型、分支、资源、重试及策略冲突。静态无法证明的条件在运行时校验，检查器不能把未知当作通过。

发布前生成包含拓扑依赖、路径访问器、schema 引用、就绪规则和资源约束的执行计划，缓存键包含快照和编译器版本；运行时不反复解析全部配置。

诊断统一包含 error_code、severity、release/flow/node、source_file、配置路径或行列、expected、actual 和修复提示。提示与事实分开，敏感值不出现在默认诊断中。

## 11. 调用、同步与异步

调用声明中的 execution_mode 决定本次同步等待或后台执行，不属于算子固有属性。持久化等级与交互方式分开：同步也可以持久化，异步必须可靠保存状态后才返回 accepted。

生产默认 durability=durable，包含同步与异步调用。仅同步的显式 ephemeral 模式可用于本地演练或不要求恢复的短任务，必须清楚标注进程退出会失去执行进度，不计入耐久执行与高可用验收；异步配置 ephemeral 在发布检查时拒绝。调用方不能把某个耐久根流程中的节点降为不可恢复执行。

调用生命周期：固定版本与 options → 校验并映射输入 → 可靠接纳 → 幂等身份核验 → 结果缓存检查 → 调度与获取资源 → 主方法及异常处理 → 提交结果/事件/调度意图 → 基础观测及特殊代理 → 推进下游。命中幂等结果或缓存时不调用主方法，但必须形成新的逻辑调用观测。幂等核验先于缓存，避免用旧缓存掩盖请求冲突。

同步接口返回框架执行结果和业务输出；异步接口返回执行标识与接纳状态。等待超时不等于业务失败，重试提交使用稳定请求幂等键。下游始终等待实际依赖结果，不能把异步接纳状态当成节点成功。

调度和工作执行可分离；本地快速路径可直接派发已就绪任务，但仍遵守相同契约和副作用限制。

### 11.1 混合同步异步与超时

根调用的等待方式与节点派发方式独立。同步根流程遇到异步节点时通过非阻塞完成通知等待，不占用节点工作线程；异步根流程同样可以执行短同步节点。子图等待不得在同一耗尽的工作池中占住线程等待其子任务。

客户端断开默认只结束等待，已接纳业务继续执行；显式 cancel_on_disconnect 仅发出取消请求。提供执行标识以便重连查询，客户端重提使用原请求幂等键。

区分调用方 wait_timeout、排队 queue_timeout、尝试 attempt_timeout 和根流程 deadline。wait_timeout 不取消业务；实际执行上限取祖先 deadline 与节点剩余预算的更严格值。资源等待、fallback 和重试均不得超出总预算。debug 暂停默认仍计入业务截止时间，非生产环境可显式采用独立调试预算。

线程超时不证明线程已停止，不能同时重试写入。需要硬隔离的执行采用可终止进程或受控外部工作者，终止后仍核实副作用结果。

## 12. 异常、fallback 与副作用

FallbackInput 包含 business_input 和 error，error 包含类型、脱敏消息、堆栈引用、异常阶段、调用与尝试标识，以及已知副作用状态。原始输入不随失败方法的局部修改而变化。

### 12.1 fallback 存在时

框架捕获主业务异常后自动调用已绑定 fallback，每次尝试最多一次，并使用独立 Output。fallback True 且业务 schema 合法、必要副作用已确认时，提交恢复结果，不再重试主方法。fallback False 或异常则保留主异常及处理结果；仅在显式声明 retry_after_fallback、失败可重试、处理过程无未确认副作用且仍有预算时允许新的尝试，默认不重试。

fallback 自身声明副作用和幂等约束，不能借用主方法“纯计算”的属性绕过检查。每个恢复操作使用稳定的操作身份。进程退出导致 fallback 中断时，同样先确认副作用，不盲目再次调用。

### 12.2 fallback 不存在时：异常入 Output 并熔断

框架必须拦截主方法异常，构造 error，写入节点 Output.error，data=null，并将根流程闩锁设置为 CIRCUIT_BROKEN。同步调用返回失败 Output，异步调用通过查询和完成通知返回。禁止以未捕获异常退出作为唯一错误反馈。

闩锁生效后停止整个根流程的新业务节点派发，包括其他子图、重试和尚未开始的并行节点。每个领取或提交业务派发的原子状态命令都核验根流程修订号；提交闩锁之前已领取的工作作为在途处理。已运行节点收到取消请求，完成后仍记录其真实副作用，迟到结果不能推进业务或撤销熔断。

立即熔断表示立即禁止继续推进，并不表示可以即时停止线程或回滚外部动作。根流程在收敛中记录 status=STOPPING、stop_reason=CIRCUIT_BROKEN；收敛完成转 FAILED，副作用无法确认时转 IN_DOUBT。原异常在闩锁提交时即可查询，无须等待收敛。测量、日志、诊断和明确的安全清理继续执行，不派发隐式业务补偿。

该规则属于单次根流程的异常熔断。对依赖服务的 CLOSED/OPEN/HALF_OPEN 熔断器另行管理，禁止因一笔流程异常就无条件熔断整个服务。

取消、进程消失和未知结果不等同于可同步捕获的业务异常。原方法可能仍在运行时，不并发启动可能重复写入的 fallback。结果未确定时先确认业务结果，再决定恢复、补偿或人工处理。

### 12.3 资源、副作用与重试

算子声明真实副作用与资源能力约束；幂等、恢复、重试、事务使用及资源并发策略从本次有效配置解析。数据库只读、事务内写入和提交后写入分别处理。调用配置只能收紧约束，不能把非幂等操作变成可自动重试。retry.max_attempts 包含首次尝试；默认 1，退避采用有上限的指数退避与抖动。非重试异常、缺少 fallback 的主异常、契约错误和幂等冲突不自动重试。

因网络或队列重复投递进行的接管不是新的业务意图；是否再执行主方法仍受幂等和未知结果协议约束。应用主异常有 fallback 才进入异常处理/重试判定，不通过重试配置绕开无 fallback 熔断规则。

补偿作为显式业务动作执行，具有独立契约、幂等和失败策略，不通过名字或 fallback 自动推断。跨系统副作用不承诺由平台统一回滚。

## 13. 状态机、持久化与恢复

### 13.1 状态

流程/调用使用 PENDING、RUNNING、WAITING、PAUSED、RECOVERING、STOPPING、SUCCEEDED、FAILED、CANCELLED、IN_DOUBT；节点另有 SKIPPED。一次成功可以附 resolution=main/fallback/cache/idempotent_reuse，代理另有独立状态。SKIPPED 节点附原因，区分条件未选择与被流程停止阻断。

PENDING 可进入 RUNNING 或取消；RUNNING 可进入等待、暂停或终态。等待/暂停在满足条件后重新就绪。失联或故障先进入恢复评估，能够确认安全时继续，否则进入 IN_DOUBT。终态默认不可原地重开，重跑创建有关联的新执行实例。节点 IN_DOUBT 时流程不能报告完全成功，其他在途分支仍需被跟踪和收敛。

取消分为请求取消和已确认取消。尚未终止的线程或外部操作不能仅因取消请求就被视为没有副作用。

状态迁移由执行分区内的有效拥有者执行 revision 条件更新，禁止迟到成功覆盖 STOPPING 或已提交终态。流程停止闩锁、操作审计和首个失败 Output 一并提交。首个错误按提交序号确定，后续错误追加，不依赖跨机器时间排序。错误查询、终态事件和幂等结果发布遵循同一已提交状态。

### 13.2 持久记录

保存定义引用、输入/输出或耐久引用、状态与状态修订号、尝试、错误、幂等键、检查点、队列投递、租约、执行世代及关键事件。节点成功记录、已发布结果和下游调度意图应原子提交，避免成功后下游永远未启动。

状态协调器通过 StateStore.commit 提交完整 StateBatch，获得提供者耐久确认后才对外生效；内存通知只负责唤醒。大对象经 ArtifactStore 保存并校验后发布引用，未引用对象按框架引用协议清理。具体介质的日志、刷盘或事务方式由提供者实现，不写入核心运行前提。

### 13.3 恢复边界

默认从最后完成的算子边界继续。内部恢复需显式业务检查点和 schema；重新进入方法后读取进度，不恢复任意 Python 指令位置或内存调用栈。

已提交结果的节点复用结果；未开始节点正常调度。中断尝试根据副作用判定：纯计算或幂等操作允许策略重试，非幂等操作查询实际结果，无法确认时进入 IN_DOUBT。

框架内部执行记录、幂等状态与可靠事件通过同一 StateBatch 提交。业务写入发生在框架状态之外时，使用稳定业务键、结果查询及业务确认协议；提供者的状态提交不覆盖任意业务外部资源，执行投递按可能重复处理，不宣称无条件恰好一次。

### 13.4 恢复、重跑与人工处置

恢复扫描器按租约和索引发现到期尝试、到期等待及未投递调度意图，分批领取，记录接管世代和次数。超过自动处理预算、检查点不兼容或引用缺失时进入人工处理队列，保留原因，不静默跳过节点。

恢复同一调用保留 release_id、业务幂等键和已提交检查点；重试增加 attempt_id。终态后的重跑创建关联的新流程实例，默认仍使用原业务操作身份，不能用重跑绕过已发生的副作用。

修改输入属于新业务请求；原键对应不同输入则拒绝。确需重新执行外部动作时，使用经授权的新业务操作键并说明原因。版本迁移显式转换 schema 和检查点，已完成副作用的业务身份保持稳定。

人工确认 IN_DOUBT 必须记录依据和操作者。将其改成成功需绑定可确认的业务结果，将其转为可重试需证明原动作未发生或幂等保护有效。所有控制动作可重复提交并通过控制请求键去重。

### 13.5 执行权

租约、心跳、条件更新和单调执行世代标识防止过期执行者覆盖平台状态。资源锁按业务键获取、多资源按稳定顺序获取。平台隔离旧执行者不自动阻止其外部写入，仍需资源系统支持或业务幂等。

## 14. 测量、日志、debug 与运营

### 14.1 三类数据

运行测量包括调用、耗时、排队、失败、重试和资源消耗；诊断日志解释执行过程；业务事件表达订单创建、审核通过等事实。业务事件不直接由方法 True 推导。

主方法记录过程信息；metrix/log 代理基于最终结果快照提取特殊测量和日志。metrix 先于 log 提交采集任务，二者无业务依赖，也不依赖执行器顺序保证投递顺序。代理 input 封装 business_input、标准 Output 和完成 options，output 是独立采集结果容器，不是原业务 Output。失败时仍可读取标准 error，不能将其作为有效业务 data。

代理只读最终结果，写入自身输出。代理故障不触发业务 fallback、不重复执行业务；使用内部诊断通道避免递归。持久执行在记录业务终态时保存待采集任务和耐久引用，防止终态提交后丢失全部特殊采集。

### 14.1.1 默认 log

未注册 method_name_log 时自动使用框架默认日志处理器，无须业务实现空代理。默认形成调用开始、尝试结束和调用完成记录；异常、fallback、熔断、恢复、取消和采集失败形成对应事件。完成记录至少包括：

- options.scene、version、releaseId、operatorName、operatorVersion、traceId。
- flowInstanceId、invocationId、attemptId、父调用及工作者标识。
- queuedAt、startedAt、endedAt、durationMs，以及状态、resolution、错误码和错误引用。
- executionMode、重试序号、幂等复用和缓存命中信息。

已开始的尝试在异常退出时由恢复器补充“失联/中断”记录，并标明 observedEndedAt；没有可信实际结束时间时 endedAt=null，禁止伪造结束时刻。尚未开始的失败调用 startedAt=null。业务事件与普通诊断日志采用不同的可靠性等级。

### 14.1.2 默认 metrix

未注册 method_name_metrix 时自动使用默认测量处理器。每次调用形成包含场景、版本、traceId、算子名、开始/结束时间的测量明细；由明细生成调用量、实际执行量、耗时分布、失败/恢复、队列等待、重试和缓存命中指标。

traceId、调用标识及完整时间戳保存在明细或 trace exemplar 中，不默认作为时序指标标签。场景、版本和算子等聚合维度也受基数预算控制。耗时用单调时钟测量；墙钟用于事件时间，跨进程区间标记计算依据，避免时钟偏差产生负耗时。

### 14.1.3 默认与自定义代理关系

基础生命周期记录始终由框架产生；缺失代理使用默认处理器，存在代理时在基础记录上补充特殊数据，不能删除或覆盖系统字段。自定义代理失败时保留基础记录并记录采集错误，按采集任务策略重试，禁止重执行业务。

缓存命中和幂等复用也形成新的逻辑调用记录，actualExecution=false；不伪造主方法执行时间。命中时默认仍执行日志和测量代理，input 提供结果来源；代理不得重新发送业务事实或改变业务状态。恢复已完成节点不会自动重复其已提交采集任务，未完成投递按原事件标识重投。

### 14.2 可靠业务事件

关键业务事实按稳定 event_id 经 StateStore 耐久提交，异步消费并去重；消费凭据和投影变化同批提交。业务动作若发生在框架状态之外，则通过业务能力声明确认协议和未确认状态，不能将状态介质视为与任意外部动作天然原子。需要业务原子性的事件不能只依赖事后尽力日志代理。

普通诊断允许有界缓冲、采样与丢弃计数；可靠事件不得静默丢弃。投递滞后有告警和容量策略。代理重试不得通过换 event_id 造成重复运营统计。

事件至少包含 event_id、event_type、schema_version、business_key、occurred_at、recorded_at、release_id 和执行关联。需要有序处理时声明聚合键与序号；不承诺全局顺序。消费端按稳定事件身份去重，迟到事件支持重算或修正口径，并保留聚合版本。

投递超过预算进入可查询的失败投递队列，支持保留原 event_id 的重投、修复与审计。数据接纳、持久化、投递和聚合各阶段有积压、失败和丢弃指标。关键事件积压超过容量安全线时停止接纳依赖该事件的新业务，不只告警后继续丢失。

### 14.3 debug

通过显式检查点捕获快照并按权限暂停目标调用。业务等待、调试暂停和故障恢复分别记录。持有业务事务或临界资源时默认只采快照或拒绝暂停，避免长期锁定资源。进程退出后按耐久检查点恢复，而不是把调试快照当作调用栈。

### 14.4 运营与算子利用分析

运营支持按渠道、业务类别、流程版本分析业务量、漏斗、结果和周期，统计口径及事件 schema 有版本。当前状态查业务数据，历史变化查事件。

算子分析同时维护静态引用图与运行使用量，包括使用流程数、调用量、成功率、延迟、重试/fallback、关键路径、资源瓶颈、长期未用版本及在途引用。看板区分零使用、未采集与数据延迟，不能把没有记录直接解释为未使用。

订单号等高基数字段用于事件检索，指标标签需限额。所有结果可关联 release_id，跨版本比较保留时间窗口、流量差异和口径，不能仅凭变化断定版本因果。

### 14.5 查询、告警与重现闭环

支持 business_key/traceId 查询根流程、子图、尝试、默认/自定义采集、外部依赖 span 和发布版本。跨异步投递持久传递 trace 上下文；恢复使用原业务 trace 关联，并新增恢复 span，不伪造连续运行的时间。

告警包含影响范围、版本、错误码、样例及处置入口，并支持确认、抑制、升级和关闭。失败样例经脱敏转为回归输入；真实副作用重放与只读重现分离。明细、指标、快照和业务事件按类别设置检索权限、保留期、完整性等级及导出审计。

算子利用分析区分逻辑调用、实际执行、cache_hit、idempotent_reuse、恢复重试和独立业务事实。缓存复用率不能被计为算子实际执行成功率；不同分母在指标定义中固定。

## 15. 完整快照发布与回退

发布快照、执行检查点和 debug 快照是三个独立对象。

快照固定全部项目模块、注册表、算子和代理、DAG/子图、契约、配置、依赖、运行产物和资源绑定策略。每项有摘要，引用产物可耐久获取；只保存版本号或文件列表不构成完整快照。凭据使用受控引用，不包含明文，凭据吊销不随版本回退撤销。

发布流程：构建 → 隔离注册与校验 → 必要回归 → 数据/外部依赖兼容检查 → 分发至目标执行池并验证 → 原子切换发布指针 → 健康观察。切换前失败不影响活动版本。

新根实例在接纳时读取发布指针并固定 release_id。子图、动态节点、代理、重试和恢复继承该版本。运行时不按“最新版本”临时解析缺失实现。

回退验证目标完整性与兼容性后原子切回指针。新实例使用目标版本；在途实例默认保持原版本。迁移在途实例需显式转换状态、契约及检查点，不能只修改 release_id。

灰度通过显式路由选择完整快照，仍保证一次根实例只使用一个版本；它是扩展能力，不是完整发布的前置条件。数据库破坏性迁移、外部动作和业务数据恢复有独立方案，不能由发布指针回退自动撤销。

清理前检查活动版本、在途/暂停/待恢复实例和审计保留要求。发布与回退记录操作主体、来源、目标、检查和时间，并进行实际回退演练。

## 16. 面向 VibeCoding 的框架适配设计

本章规定框架适配 VibeCoding 开发方式所需的结构与协议。适配目标是使外部工具能够准确理解业务边界、局部修改代码和配置、执行验证并定位问题，不要求框架内置或集成 VibeCoding 工具链。

算子目录可按业务描述、契约和副作用搜索。局部开发上下文包含目标实现、业务规则、schema、直接上下游、相关测试与失败案例，并标明边界和遗漏；允许沿依赖继续展开，不强制 AI 读取全项目。

模板生成主方法、所需代理、注册、schema 和测试骨架，代理按需提供，避免无意义样板。规则只维护一个权威来源，生成说明与 schema 通过检查保持一致。

框架的查询、检查和验证接口提供稳定 JSON 结果及诊断码，覆盖算子发现与契约查询、相关上下文读取、编排校验、测试执行、执行记录检查及版本差异查询。外部 VibeCoding 工具通过标准 CLI/API 使用这些能力；接口不依赖特定工具、模型或交互协议。具体接口在详细设计中定义。

变更预览列出影响算子、图、契约、在途恢复兼容性和必要回归范围。重现工具默认使用依赖替身和隔离数据；真实副作用重放属于单独授权动作。

AI 生成的测试预期必须有业务规则或已确认样例来源，不能仅镜像新实现。效率通过固定任务评估读取范围、修改范围、契约/回归通过率、无关变更和修复时间，不预设一定提升。

## 17. 标准开发与运行工作流

1. 描述业务规则及代表性输入输出，界定可独立验证的步骤。
2. 查找已有算子并确定复用、修改或新增。
3. 声明 schema、资源/副作用和恢复约束，生成并实现方法与注册。
4. 配置图、子图及边界映射，执行结构和兼容检查。
5. 执行算子、子图、流程、异常和恢复回归，检查变更影响。
6. 构建完整快照，验证和发布。
7. 通过执行追踪、业务指标和算子利用情况观察效果。
8. 问题转为脱敏回归案例，必要时回退完整版本或处理在途实例。

开发、发布与运维操作使用相同的契约、版本和执行标识，避免本地验证与生产执行采用不同语义。

## 19. 性能设计

发布时编译拓扑、契约和路径；运行时按就绪节点推进，不重复扫描整图。对 schema 和计划使用有界缓存，缓存隔离版本。纯计算可走本地路径，不能绕过可靠性要求以节省持久化。

大数据传引用，限制快照体积；观测异步批处理并设置缓冲上限。持久状态只写必要的事务边界和恢复事件，不能无界记录每条代码指令。同步关键路径区分业务耗时、框架开销和存储开销。

按计算、阻塞 I/O 与异步 I/O 分配执行资源；CPU 密集任务根据负载采用独立进程或外部执行器。集合展开、重试和资源使用均有配额与背压。优化必须在保留数据一致性约束的前提下经测量选择。

## 20. 可用性与故障处理

### 20.1 角色与提供者能力

框架协调执行分区内的状态命令、工作者隔离和恢复；持久化提供者负责其声明范围内的原子提交、耐久性、一致读取及所有权隔离。单实例可采用内部串行协调，多实例必须通过提供者的跨实例能力阻止双重领取和过期提交。

上层页面展示能力并配置绑定，宿主和框架启动/发布时再次检查。页面不直接充当运行介质，页面关闭不影响已接纳流程。具体故障域由实际提供者与部署验证，不将框架无外部依赖解释为必须使用本地存储。

### 20.2 提交和恢复失败

提供者不可用时停止确认新的耐久任务。提交结果未知时按原 request_id 查询，不自动改用另一介质重提。内存任务可由一致恢复视图重建，缓存可清空，但幂等与已提交业务结果不可无声丢弃。

工作者失联后按 epoch、检查点和副作用能力处理；无 fallback 异常仍按根闩锁熔断。配置关闭恢复的调用不自动重执，保留结果未知和人工处理入口。

### 20.3 质量保证

框架暴露提供者健康、提交延迟、未知提交、工作者心跳和积压。验收分别验证框架协议、介质契约与进程/主机/介质故障。高可用不能仅由页面勾选启用，也不能只接受提供者自报能力而无测试证据。

## 21. 安全与可维护性

区分发布、回退、运行控制、真实副作用重放和快照读取权限。外部事件和管理接口鉴权并防重复请求。凭据通过资源引用解析，日志与 AI 上下文脱敏。

注册代码是可执行 Python，应按可信代码及供应链管理；不可信扩展需独立执行隔离，单凭注册接口不能实现沙箱。资源访问最小授权，控制表达式采用受限语法。

SDK、编排、存储、调度和分析通过明确接口分层，业务不导入调度内部实现。公共协议版本化，错误码稳定，迁移工具可重复执行。日志、快照、事件、状态和发布产物具有分类保留策略及引用保护。

## 22. 质量目标与验证方法

性能、高可用和高可维护性是待量化目标，当前没有负载与部署基线，不能给出已经保证的数值。立项实施前应确定：

- 性能：指定图规模、数据量、并发和副作用类型下的吞吐、p95/p99 延迟、框架额外开销与资源占用。
- 可用性：入口接纳和执行服务的 SLO、恢复时限、可容忍数据损失范围，以及跨故障域的目标。
- 维护性：变更影响可追溯率、契约错误定位能力、回归时长、版本兼容与回退耗时。
- AI 开发效果：固定业务任务中的上下文规模、修改范围、验证通过率和缺陷修复时间。

分别执行单元、契约、集成、负载、长稳、故障注入和回退演练。平均延迟不替代尾延迟；单机测试不证明分布式可用性。验收保留环境、数据集、版本和结果。

## 23. 平台验收场景

- A01：同一算子同步与异步调用结果一致，异步仅在可靠接纳后返回成功接纳。
- A02：新文件注册、重复声明、错误签名及部分注册失败均有明确诊断，已有版本不被部分替换。
- A03：输入缺失、null、转义路径、列表路径和映射冲突按契约处理，无部分输出发布。
- A04：DAG 环、子图递归、失效引用、类型冲突和不可达节点在发布前定位。
- A05：分支跳过不导致汇合死等；异步提交不提前释放数据依赖。
- A06：集合并发、循环上限、重复外部信号及等待超时行为可验证。
- A07：已绑定 fallback 时主异常自动进入处理，原始输入完整；代理失败和 fallback 再异常不产生递归业务重跑。
- A08：工作进程在执行前、写入后和完成记录前后退出，恢复不丢失已接受任务并按幂等/未知结果规则处理。
- A09：租约接管后过期执行者不能改写平台状态，外部副作用仍通过业务确认隔离。
- A10：debug 暂停不长期持有业务临界资源，重启后按业务检查点恢复。
- A11：事件重复投递不重复统计业务事实，观测故障不被误报为业务失败。
- A12：发布产物缺失不能切换，发布/回退中单实例及子图保持完整版本，在途依赖不被清理。
- A13：不兼容数据迁移阻止无条件回退，故障版本实例有明确处置方式。
- A14：静态引用与运行利用信息可区分，日志与运营可定位到完整发布版本。
- A15：框架提供可供外部 VibeCoding 工具读取的契约、影响范围和结构化诊断；局部修改能够独立验证，敏感内容受权限控制。
- A16：在确定的负载与故障模型下验证质量目标，报告未达项而非推定满足。
- A17：主方法异常且未绑定 fallback 时，节点和根流程 Output 可查询异常，根流程立即停止新的业务派发；子图和错误分支不能绕开熔断。
- A18：熔断与并行节点领取、迟到成功、重试及恢复并发发生时，状态修订和闩锁阻止继续推进，已发生副作用仍有记录。
- A19：log/metrix 均未注册时，默认记录 scene、version、releaseId、traceId、算子名及开始/结束信息；失联结束时间标为未知，不伪造。
- A20：自定义 log/metrix 故障时基础记录保留，不重执行业务；高基数字段不无界扩展聚合标签。
- A21：缓存命中仅复用业务 data，新调用元数据正确；不同租户、权限、版本、输入和数据版本不能串用缓存。
- A22：缓存失效并发回填、填充者退出、缓存不可用和对象到期时按协议旁路或失败，不能破坏幂等记录。
- A23：同幂等键并发只有一个副作用执行归属；输入不一致拒绝；新版本不绕过去重；成功、失败和未知结果分别复用或隔离。
- A24：业务写入已完成但幂等结果响应丢失时可确认结果；不支持确认的外部动作进入 IN_DOUBT，不自动重复提交。
- A25：同步根流程混合异步节点、子图等待和客户端断开不会占满执行池或误判任务成功，超时范围符合约定。
- A26：周期触发重复投递、调度器切换、错过时段和重叠周期均不重复接纳同一触发实例；补跑上限有效。
- A27：事件乱序、迟到、消费失败和重投不重复业务事实，运营聚合能修正并保留口径。
- A28：状态拥有者、耐久日志、内存队列和产物文件分别故障时，拒绝/继续/恢复行为符合内置故障协议；未实现的跨主机能力不标记通过。
- A29：人工重跑、修改输入、未知结果确认和检查点迁移分别鉴权审计，不能通过控制接口解除既有副作用去重。
- A30：备份恢复后幂等、状态和产物引用一致，开放写入前完成未知副作用核验。
- A31：上层绑定不同持久化实现后，框架不改算子和调度代码；未绑定或能力不足时拒绝耐久异步/恢复配置。
- A32：缓存、幂等、同步/异步及恢复按配置继承和覆盖执行，enabled=false 不被遗漏，未知属性不能静默生效。
- A33：页面修改只生成新配置修订；已运行及待恢复调用继续使用原 policy_digest 和 storage_binding。
- A34：提供者 commit 应答丢失、同请求重提和 revision 冲突不会重复业务；介质迁移不丢幂等与产物引用。
- A35：页面离线不影响已接纳任务，宿主及框架独立执行配置/能力校验，不把前端验证作为唯一门禁。

以上是验收设计，不是已执行通过的结果。

## 24. 建议实施阶段

阶段一建立开发闭环：算子 SDK、标准 Output/options、Map/schema/路径、文件注册、DAG/子图编译、本地执行、默认日志与测量、测试及不可变快照构建。

阶段二建立生产闭环：耐久异步执行、恢复、结果缓存、幂等与资源约束、异常熔断、可靠事件、任务触发与运维控制、完整发布回退、权限、故障及负载验证。此前不宣称平台已具备生产级高可用。

阶段三增强持续优化：运营看板、算子利用和关键路径分析、AI 局部上下文与影响工具、灰度和可视化编排、容量与成本优化。

阶段是依赖顺序建议，不是用户已承诺的范围、排期或交付日期。阶段一仍应预留阶段二所需的标识、版本和状态接口，避免后续推翻基础模型。

## 25. 标准默认行为与覆盖边界

1. boolean 表示执行成功；False 不自动进入 fallback；fallback True 且结果合法时推进下游。
2. 无 fallback 的主业务异常写入标准 Output，立即设置根流程熔断闩锁，不进行自动主方法重试或错误分支恢复。
3. 无 log/metrix 代理时使用默认采集；自定义代理补充特殊数据，基础生命周期记录不可覆盖。
4. context.options 是调用配置及执行元数据的只读视图，结束后创建新的完成视图。
5. 数据使用层级 Map、严格 schema 和边界路径映射；元数据与错误不得混入业务 data。
6. 汇合默认等待激活分支全部成功；根流程熔断覆盖局部汇合策略。
7. 恢复默认以算子边界为单位；内部恢复需显式检查点；debug 默认暂停当前调用。
8. 注册使用 register(registry)，生产代码变更通过完整快照生效；在途实例固定原版本。
9. 算子结果缓存默认关闭；启用后只缓存满足契约的主方法成功结果，受版本、身份和数据依赖隔离。
10. 幂等记录与缓存独立，禁止缓存淘汰解除业务去重。可重试不等于外部副作用天然幂等。
11. 重试默认只有首次尝试，调用方断开默认不取消已接纳业务。
12. 调度、恢复、采集重投和人工控制动作均须有重复请求处理语义和审计。

缓存和业务幂等等开关可按第 31 章配置；运行环境可选择介质和调整预算，但不得伪造能力、解除内部命令去重或绕过版本、异常熔断、权限和已发生副作用的约束。产品特有规则使用版本化配置声明，不在业务方法中隐式修改框架策略。

## 26. 算子级结果缓存协议

### 26.1 适用范围

结果缓存用于复用业务 data，不复用调用元数据，不承担去重副作用。默认关闭，仅对声明为可缓存、无写入副作用的纯计算或只读算子启用。只读数据需要明确数据版本、失效协议或允许陈旧窗口，不能仅凭“只读”认定结果永远有效。

写入、副作用、随机结果、依赖未声明当前时间或隐式外部状态的算子禁止默认缓存。声明可缓存必须列明所有影响结果的数据依赖；结果与调用身份相关时纳入相应身份维度。框架检查声明并提供契约测试，不宣称能静态识别任意 Python 的隐式依赖。

### 26.2 缓存键与结果

键包含租户/业务隔离域、权限指纹、release_id、算子实现及 schema 摘要、规范化完整 input、声明的 context 数据依赖、外部数据版本和缓存策略版本。默认完整输入参与，裁剪字段需证明不影响结果。规范化固定键顺序和类型编码，区分缺失、null、数值及字符串，摘要不得暴露凭据。

缓存仅保存通过 schema 校验的主方法成功 data、来源摘要、创建时间、过期时间及依赖版本。失败、异常和 fallback 结果不入缓存。命中时生成本次新的 Output.meta 和观测，保留原结果来源引用，不复用原 traceId、attemptId 或业务事件。

### 26.3 一致性、失效与并发

TTL 必须大于零且不超过业务允许陈旧窗口，可通过数据版本切换或带版本的失效事件主动失效。旧计算只能写入其对应版本键，不能在失效后回填新版本。跨发布默认不复用缓存，回退也要验证数据依赖版本及有效期。

命中仍校验权限、schema、摘要与到期时间。失效或损坏视为未命中并告警。缓存故障默认旁路计算，对外数据来源保留记录；禁止通过旁路绕过幂等记录不可用的限制。

相同键采用有时限的单次填充协调，其他调用等待填充或在预算内重新计算。填充者故障可接管；纯计算重复执行可容忍，但不能借此放宽副作用限制。命中结果的对象引用必须在缓存生命周期内有效。

### 26.4 观测

统计命中率、未命中、填充耗时、协调等待、过期、主动失效、淘汰、故障旁路、节省的实际执行量及容量。用户配额、权限和接纳限流在缓存前生效。普通缓存失效不删除已持久化的成功执行结果。

## 27. 幂等执行协议

### 27.1 身份与记录

幂等键由租户/业务域、操作名称和稳定业务操作键构成。请求摘要包括影响业务结果的输入和业务语义版本，主方法/恢复动作分别有稳定操作身份。traceId 和 attemptId 不参与生成业务操作键。

业务幂等由配置决定是否启用。写入型业务开启幂等或自动恢复时必须提供可确认的业务操作身份及相应能力；关闭业务幂等且缺少确认能力时仅允许不自动重执的受限策略，禁止自动恢复重试。纯计算默认使用逻辑调用身份去重投递，跨调用复用通过缓存实现，不强制把所有相同输入永久视为同一业务请求。

同键同摘要重复请求复用已确认结果；同键不同摘要返回 IDEMPOTENCY_CONFLICT，不执行主方法。新 release_id 不自动建立新业务身份；跨版本重复请求优先返回原已发生业务的结果，必要时提供明确的兼容表示，禁止为适配 schema 再次执行副作用。

记录包含请求摘要、IN_PROGRESS/SUCCEEDED/FAILED/IN_DOUBT 状态、拥有者及执行世代、结果引用、版本和保留/墓碑策略。业务操作键不能存入按容量任意淘汰的缓存。结果到期后保留足够的操作墓碑或采用业务唯一约束，避免重新接纳仍可能重复的旧动作。

### 27.2 并发与故障

通过唯一约束或线性一致条件写入领取执行权。同键正在执行时，默认返回原执行标识及处理中状态；同步调用可在自身预算内等待，禁止开启第二次并发副作用。

已知成功返回原结果；已确认失败默认返回原失败，只有显式的安全重试策略才恢复同一逻辑调用；副作用未知返回 IN_DOUBT 并阻止重复提交。状态存储或幂等权威存储不可用时，写入型业务拒绝接纳，不能降级成“无去重执行”。

### 27.3 原子性与能力边界

框架自己的幂等结果、执行状态及必要事件在同一状态批次提交。业务资源的写入需要由有效配置和能力声明确定幂等键、可查询结果或确认协议，不能认为框架状态介质与业务资源天然原子。既不支持幂等也不可查询的外部动作，框架仅保证平台记录与单次领取规则，不能保证物理动作绝不重复；接管进入人工确认，不冒称全局恰好一次。

幂等保证指重复请求不重复产生已约定业务效果，不要求返回的 traceId 等调用元数据完全相同。算子天然幂等声明、事务幂等、外部幂等和人工确认能力分别记录并验证。

### 27.4 与缓存、恢复及事件的关系

幂等身份核验先于结果缓存。缓存命中可完成一个无副作用逻辑调用，但不代替写入操作的业务结果证据。恢复保留业务身份，重新投递保留原调度/事件标识；新的逻辑请求产生新的调用观测，不重复生成原业务事实。权限变化时重新鉴权，不能仅凭持有幂等键读取旧敏感结果。

## 28. 任务触发、调度与运维控制

### 28.1 触发

支持 API 即时任务、一次性定时、周期性及事件触发。周期任务声明时区、夏令时跳过/重复规则、错过触发的 skip/latest/all 策略、补跑上限与周期重叠的 allow/forbid/queue 策略；默认 forbid，错过默认 latest，实际启用时必须生成可读触发表。

每个触发实例由稳定计划标识、计划触发时刻和显式触发代际去重，普通计划修订不能自动重复创建同一时刻的触发；确需再触发使用经审计的新代际。触发记录和执行接纳意图一并提交。默认根实例接纳时固定活动快照，指定固定版本的计划在目标被清理前必须解除引用。补跑使用明确的业务时间窗口，不以实际执行时间代替。

事件触发使用事件标识去重，重复事件复用原触发记录。信号等待和创建新流程属于不同接口，不把回调误当新业务请求。

### 28.2 调度与容量

按租户/场景、流程、算子、资源键和执行池设置并发配额及接纳限流。定义优先级并采用防饥饿策略；恢复和重试也消耗配额，限制重试风暴。排队超过 queue_timeout 记录排队失败，不伪造业务执行开始时间。

CPU、阻塞 I/O、协程和长期外部任务分池；子图/信号等待释放工作容量。过载时返回可识别的拒绝或排队结果，提供退避建议，不无限增长内存队列。

### 28.3 运维接口

提供查询、取消、暂停、继续、重试、重跑、未知结果确认、检查点迁移及失败投递重投接口。每项返回请求标识、受理状态、最终状态查询入口及审计引用；受理取消不等于已经停止。

控制请求校验权限、预期修订和幂等键。业务操作、状态迁移和快照变更均记录操作者和依据。无法自动处理的任务有处理队列、负责人、时限及告警；不得通过绕过提供者接口改写底层介质作为标准恢复方式。

## 29. 持久化提供者接口

### 29.1 提供者与绑定

框架只定义接口，不固定文件、日志格式、数据库或其他介质。上层页面选择已注册提供者并填写配置，宿主创建实现后通过注册/依赖注入绑定，框架不执行页面任意输入的模块路径。提供者自己的依赖与资源由宿主管理，不成为框架核心依赖。

绑定包含 provider_id、binding_id、namespace、binding_revision、config_digest 及权限/凭据引用；不在快照中写明文秘密。运行实例记录实际绑定修订，在途恢复不跟随页面切换。

### 29.2 状态接口

- describe()：接口版本、配置 schema、能力和作用范围。
- read/query(...)：按标识或有界游标读取执行、任务、幂等和事件状态。
- commit(batch, expected_revision, request_id, owner_token)：原子提交 StateBatch，返回提交标识及新 revision；同请求同摘要重复返回原结果，不同摘要冲突。
- get_commit(request_id)：确认提交结果，区分已提交、明确未提交和仍未知；超时不能视为未提交。
- load_recovery_view(scope, cursor)：读取一致恢复视图，包含 revision、有效状态、检查点及固定的策略/介质引用。
- ownership(...)：需要多实例接管时提供领取、续期、释放及单调 fencing；单实例模式也应阻止重复拥有者。

这些是协议操作，不要求所有介质暴露相同的底层 API。commit 不能退化为多次无保护 set；框架不能在能力不足时自行假装原子。

### 29.3 产物接口

ArtifactStore 提供 put_immutable、get、verify、引用/保留保护及受控删除。对象耐久可读并验证摘要后才在 StateStore 发布引用。多介质间不假定原子：允许留下未引用孤儿对象，禁止发布缺失对象。清理前由框架确认引用，不能仅按介质 TTL 删除在途快照。

### 29.4 能力协商与迁移

耐久异步、恢复和持久幂等依赖 atomic_batch、conditional_write、request_deduplication、durable_ack、consistent_recovery。多实例另外要求合适范围的 ownership/fencing。缺少绑定或能力时拒绝相关策略，显式非耐久同步演练不宣称具备这些保证。

更换绑定形成新修订，新调用按发布配置使用；在途实例固定旧绑定。迁移须有停写或一致切点、状态/幂等/事件/产物拷贝与校验、明确接管和回退规则。仍被引用的绑定不得删除。

## 30. 运行参数、质量验收与版本管理

### 30.1 参数归属

框架配置算子策略、容量、超时、并发、缓存及采样预算；介质参数由上层页面按 provider 配置 schema 管理，宿主注入实现。是否具备耐久、跨实例一致性和恢复由接口能力及验证决定，框架不选择具体介质。

### 30.2 验收

分别验证算法、配置解析、提供者契约及实际部署。质量指标包括负载、尾延迟、吞吐、恢复时间、恢复点和故障范围。内存替身不作为生产耐久证据，具体介质的故障行为不能被框架默认覆盖。

### 30.3 版本管理

v1.1 完善执行、异常、缓存与观测协议；v1.2 将选型限定为框架内部机制；v1.3 将持久化收敛为提供者接口并交由上层绑定，统一配置化缓存、幂等、同步/异步及恢复等执行属性。

实现与验收分别管理，接口、配置、编码和恢复契约变更必须给出兼容方案。

## 31. 算子级执行属性配置

### 31.1 定义与策略分离

算子方法、签名、契约和真实副作用能力描述保持稳定。缓存、幂等、同步/异步、持久化、恢复、超时、重试、并发和观测预算属于可配置策略，由同一配置 schema 管理。

算子注册可携带 default_policy 提供默认值，但不固定所有调用。编排节点通过 policy 指定本次使用方式，允许的调用级覆盖通过入口白名单控制。配置不能把真实写入声明成纯计算，或把不支持幂等的资源变成幂等资源。

### 31.2 策略字段

- execution_mode：sync/async，本次等待和派发方式。
- durability、persistence_binding：耐久要求及逻辑提供者绑定。
- recovery.enabled、checkpoint_policy：是否允许恢复及恢复边界。
- cache.enabled、ttl、max_entries、max_bytes、key_paths、scope、single_flight：缓存开关、预算、键和协调规则。
- idempotency.enabled、key_paths、scope、result_retention、replay_policy：业务幂等开关、身份和复用范围。
- timeout、retry、concurrency、resource_policy：排队/执行/流程预算、重试及资源约束。
- observability：日志、测量和快照的补充采集、采样与保留预算；不能关闭框架要求的基础生命周期记录。

### 31.3 合并与固定

顺序为“框架默认 → 算子默认 → 编排节点 → 明确允许的本次覆盖”。对象逐字段合并，数组整体替换，false/0/空集合是显式值，不能被当成未设置；null 仅在 schema 允许清空时使用。未知字段、非法组合和介质能力不足一律拒绝。

合并后产生深度冻结的 EffectiveOperatorPolicy，计算 policy_digest 并关联配置修订。通过 context.options.policy 只读暴露。本次调用、重试、fallback、代理及恢复采用同一有效策略，不重新读取页面最新配置。根流程与各节点可有不同策略摘要，但都属于已固定的发布和调用配置。

### 31.4 组合约束

async/durable/recovery 需要满足持久化能力；显式 ephemeral 同步调用不承诺中断恢复。cache 只允许满足真实副作用约束的算子，关闭缓存不影响幂等；关闭业务幂等不关闭内部 command_id 去重。

带副作用且关闭幂等、缺少结果确认能力时禁止自动重试或自动恢复重执。输入、schema、权限和数据版本必须满足缓存隔离，配置裁剪缓存键不得隐去影响结果的依赖。根异常熔断规则不因 retry 或子图配置放宽。

### 31.5 上层页面与运行职责

上层页面读取配置和 provider 描述，提供策略编辑、介质绑定、校验预览及发布；宿主负责注册和实例化介质实现，框架负责最终校验与执行。此处仅定义职责和协议，不要求框架集成页面或特定前端技术。

页面保存草稿不会改变正在执行的策略。发布生成配置修订，新调用使用新配置；在途变更须使用明确的运行控制或迁移协议。凭据以受控引用管理，不能作为策略明文写入 Output、日志或快照。
