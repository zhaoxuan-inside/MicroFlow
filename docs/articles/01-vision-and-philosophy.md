# 给 VibeCoding 修一条轨道：MicroFlow 的愿景、原理与设计思想

> 本文是 MicroFlow 系列第一篇（愿景与思想）。系列目录：
> ① 愿景与设计思想（本文）② [Python 后端使用指南](02-python-usage.md) ③ [Flutter 前端使用指南](03-flutter-usage.md)

## 一、从一个所有人都遇到过的场景说起

你对接手 AI 说：「把这个页面接上真实数据。」

三秒后它回答：「已完成 ✅」。

你打开代码一看——一个写死的 JSON 数组，变量名甚至叫 `mockData`。功能"看起来"完成了：页面渲染正常、接口签名存在、甚至有测试通过。但你知道，这叫**假完成**。

这不是段子，是每个认真使用 VibeCoding 的人的日常。更隐蔽的变体包括：测试断言被悄悄改成迁就错误实现、异常处理被 `try: pass` 静默吞掉、你三小时前定的架构约束在第五轮对话里被遗忘得一干二净。

很多分析把原因归结为"模型能力不足"。用了大半年 AI 编程之后，我的结论不太一样：**能力不是主要瓶颈，接口才是**。AI 工具面对一个模糊需求时，不会像资深工程师那样停下来追问，而是自行脑补一个最短路径的解释然后直接实现——因为它的世界里没有任何结构告诉它"业务边界在哪里、什么算完成、什么不许做"。

二义性不会凭空消失。你不说清楚，它就替你决定。

## 二、核心论点：二义性无法消除，但可以转移和压缩

这是整个 MicroFlow 框架的原点命题。

工程师和 AI 协作时，系统里总得有人持有"业务到底是什么"的完整语义。传统开发里，这些语义散落在代码的每个角落——每一行业务逻辑都是一次潜在的二义性。而 MicroFlow 做的事情是：**把业务语义从"散落在代码里"压缩为"集中在少数几个设计决策里"**。

具体说，一条业务链路被拆成两种东西：

1. **算子（Operator）**：契约明确、副作用如实声明、行为边界固定的业务步骤。比如"从关系数据库提取结构化数据"、"按会员等级计算折扣"。它是业务无关的能力件。
2. **编排配置（Orchestration）**：一份标准的、结构化的 JSON。它声明用哪些算子、按什么数据流连接、什么条件下走哪个分支。

这个拆分的妙处在于双方各取所需：

- **人**只守少数高价值的设计决策：算子怎么划分、粒度多大、暴露哪些端口；
- **AI** 只做两类它极其擅长的事——实现算子（模式高频、契约明确），和生成/修改编排配置（Schema 可校验、无二义性）。

当你告诉 AI「下单时会员打九五折」，它不再是"自由发挥"，而是在一个封闭的契约体系里填空：折扣逻辑属于某个纯计算算子，配置声明它在哪个节点生效。**业务边界由此锁定。**

顺带收获一个副产品：影响分析从"经验题"变成"图查询"。改一个算子会影响哪些流程？反向索引一查便知——框架里的 `impact` 命令返回的是确定性的引用图，而不是开发者的直觉。

## 三、四个设计支柱

### 支柱一：编排配置即数据，表达力刻意做小

编排配置是结构化数据，发布前经过静态检查：环检测、引用校验、路径与类型检查、策略组合校验，未知规则一律拒绝。一个关键决策是：**表达式采用受限白名单语法，禁止 eval、禁止脚本模板**。

为什么？因为编排配置的表达力一定会被业务演进诱惑着朝图灵完备漂移——今天加个条件，明天嵌个循环，后天塞段脚本。一旦漂移过去，"配置"就变成了"一门用 JSON 写的糟糕编程语言"，可校验、可静态分析的全部优势瞬间归零。

所以 MicroFlow 的纪律是：表达不了的逻辑，答案是**新增算子**，永远不是**增强表达式**。这条守不住，整个模式破产。

### 支柱二：层次分解——子图即复合算子

流程图画大了必然爆炸成不可读的巨型状态机。经典解法是子图，但子图有个著名的失败模式：切错位置时，你只是把巨型流程图换成了巨型节点，展开一看，里面还是巨型流程图。

MicroFlow 的处理是让子图和原子算子遵守**同一套契约纪律**：类型化的输入输出端口、固定的错误语义、独立版本、独立测试。子图以"复合算子"的身份参与编排，于是校验、渲染、影响分析、执行追踪全部递归复用同一套机制。配套三条治理纪律：接口预算（端口建议不超过 8 个，超限就是切错的信号）、目录可读性（父图不展开子图就能读懂业务步骤）、引用而非复制（防止同一能力三处副本各自漂移）。

### 支柱三：观测分层——给 AI 一个反馈闭环

现代应用开发绝不只是编码。调试、采集数据指导修复、采集数据指导优化——这些数据**采集**应该是框架的职责，而**汇聚、分析、展示**应该是上层的职责。

编排架构在这里有一个结构性红利：所有执行都必须经过解释器这一个咽喉。算子的开始/结束/失败/重试/恢复，全是天然的结构化事件。框架在运行时拦截边界统一发事件，**业务代码一行埋点都不写**，采集就完整了——采集不是成本，是副产品。

而这个观测层还有一层更深的意义：结构化事实流人能读，**AI 也能读**。修 bug 时把查询结果作为证据喂给工具，"采集数据指导修复"就有一部分是自动化的。还记得第一节的"假完成"吗？它的解药不是更强的模型，而是一条**机器可验证的证据链**：门禁不通过就是不通过，没有解释空间。

### 支柱四：零依赖内核 + 端口注入

框架核心不依赖任何第三方包——只依赖语言运行时和标准库。持久化介质、遥测接收、授权、事件投递，全部以框架定义的端口接口由宿主注入。

这不只是工程洁癖。框架位于依赖图最底层，它引入的任何传递版本约束都会传导给所有下游应用；框架要活十年，而依赖会废弃、会投毒。更现实的一层是：**零依赖意味着 AI 面对的是一个封闭的、全部可读的、项目自有的 API 面**——它不需要回忆任何外部包的版本细节，而第三方 API 恰恰是 AI 幻觉最严重的区域。内核越小越封闭，AI 的出错面越小。

注意精确形态：**零依赖 ≠ 零接口**。不依赖别人的实现，但要给别人留出实现的位置——适配包可以携带依赖，依赖方向永远单向。

## 四、一条贯穿一切的底线：诚实边界

最后说一个不太"技术"但可能最重要的设计原则。

AI 生成物的最大风险，是**用伪造的完成度替代真实的完成度，且汇报语气永远自信**。MicroFlow 把对抗这条风险写进了协议层：

- 设计基线、实现状态、验收证据**分别管理**——文档修订不等于实现完成，测试通过不等于验收通过；
- 内存替身与本地演练**不冒充**耐久与高可用证据，返回值明确打上 ephemeral 标记；
- 未知结果进入**可判定状态**（IN_DOUBT / unknown），而不是静默降级；
- 框架核心零第三方依赖（Python 实现经独立 wheel 安装验证），验收场景 A01～A35 逐项挂账，未验收的能力显式拒绝而不是假装支持。

给 AI 修轨道，本质上是把"信任"从模型的能力转移到流程的结构上。

## 五、总结

回到最初的问题：VibeCoding 工具的局限怎么解？

MicroFlow 的答案是四个字：**职责重分**——目标定义和架构决策给人，长期记忆给文档，通过性验证给机器门禁，真实环境的最终验收给人的业务判断。二义性被压缩到少数几个设计决策处，而这几个决策恰好是人应该亲自占守的位置；剩下的全部工作，都落在 AI 的能力区间内。

框架的代码在 GitHub 上（后端 Python 实现与前端 Flutter 实现，均零第三方依赖）。下一篇讲怎么用 Python 后端从零攒出一个交易平台——从算子定义到影响分析，全程走框架 CLI，每一步都有机器可验证的证据。
